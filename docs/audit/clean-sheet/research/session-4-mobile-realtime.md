## §2 Techniques radar (Lanes R + A)

Guardrail from §1 (shared method): every card names a rollback and a way to measure success; every mobile card states how the flag reaches the device and what an old build does, per `08-hostile-review.md`'s correction that mobile "rollback: revert" is not a real rollback — it's an OTA republish, effective on next launch/update-check, not instantly. Where no server flag is involved (pure native-app-store binary behaviour, e.g. `expo-updates`' own error recovery), that is stated instead.

### 2.1 Offline-first trip state

### Queue the trip-completion mutation the same way location fixes are already queued — TRIAL
- What it is: extend the existing durable SQLite outbox pattern (MR-1) to the completion event itself — when `POST /complete` fails with no HTTP response, write a `pending_completion` row (ride id, completion fix, idempotency key) instead of only showing a "check your connection" banner, and auto-retry it from a background task the moment `NetInfo` reports connectivity (the listener already exists, `useDriverDashboard.ts:1727-1796`), with the same UI still visible in the meantime so the driver isn't misled into thinking nothing is happening.
- Who uses it / source: general offline-first mobile pattern — local persistence + idempotent sync queue, described generically in ride-hailing engineering write-ups ([Combating Offline Trips, Medium/Incognia-style summary](https://oyelabs.com/handling-network-drops-mid-ride-without-losing-trip-data/), snippet, read 2026-09-25, INFERRED — not a primary vendor source, treated as a description of a well-known pattern rather than a citation of authority). The idempotency-key discipline itself is Spinr's own existing pattern (CLAUDE.md; the 409-then-check-terminal-state handling already in `driverStore.ts:857-861` is most of the hard part already built).
- Spinr today: MR-2 (VERIFIED) — no queue for the completion call itself; the driver must physically regain signal and keep retrying.
- Benefit for Spinr at our scale: closes the driver-side half of RIDERJ-002/edge-case-matrix Flow 3's reddest row (rural-SK network loss, explicitly named "High" dispute risk there) at moderate cost, because the hard idempotency plumbing already exists. Cost/effort: **M**. Risk: a completion that queues locally and is later submitted with a stale `completion_fix` (GPS drifted while parked waiting for signal) needs the same distance-at-completion plausibility check the edge-case matrix already flags as unread/unverified (Flow 3 "duplicate tap" row, `ride_complete.py`'s validation, RED-leaning Unknown) — **this TRIAL should not ship ahead of that check being confirmed**, or a queued-but-stale completion could under/over-charge silently.
- How it fails or gets gamed: a driver who genuinely never returns to signal (phone dies in the dead zone) still needs the existing admin-alert path (`stale_in_progress_ride_alerter.py`) as the backstop — this card shortens the *common* dead-zone case (temporary signal loss), it does not replace the backstop for a permanent one.
- False-positive cost: none directly (it only helps a stuck completion succeed sooner); the risk is entirely in the fare-accuracy question above, not in a false action against a person.
- Appeal path: n/a (this is reliability plumbing, not an enforcement action); a mis-priced queued completion goes through the existing rider dispute path once RIDERJ-003 ships a rider-facing one.
- First step behind a flag: this is a client-app change, so there is no server `app_settings` flag to gate it — the delivery mechanism is **an app-store/OTA release**, and an old binary simply keeps today's behaviour (blocking call, "check your connection" banner) until it updates. Ship the completion-queue behind a client-side feature constant that defaults off, flip on for an internal test cohort, then OTA-republish to 100%. Rollback: **OTA republish of the previous bundle — effective on each device's next update check, not instant** (per `08-hostile-review.md` §1.3's correction; this is not a config toggle). Measure success by: count of trips completed via the queued-retry path vs. the direct path, and the confirmed-correct-fare rate on queued completions once the plausibility check above exists.

### Rider-facing escalation once staleness crosses the backend's own threshold — ADOPT (RIDERJ-002's own recommendation, restated for this session's flag/rollback framing)
- What it is: cited from `rider-journey.md` (VERIFIED there) — once `DriverLocationStatus` staleness crosses the same ~8–10 min the backend's `stale_in_progress_ride_alerter.py` uses, switch the passive banner to an actionable one with a support deep-link (mirroring `topic=payment_failed`).
- Spinr today: passive-only banner forever (RIDERJ-002).
- Benefit: turns the rider-side half of the same offline/dead-zone scenario from "silently wait forever" into "get help," without touching ride-state legality. Cost/effort: **S**.
- First step behind a flag: pure client copy/UI change, no backend flag — delivery is an **OTA republish** (JS-only change, no native code), effective on next update check for devices with connectivity to check; a device that is itself offline obviously won't fetch the update until it reconnects, which is an acceptable bound (nothing meaningfully worse can happen to an offline device from a delayed UI improvement). Rollback: OTA republish of the previous bundle. Measure success by: count of support contacts tagged `stuck_ride` before/after.

### Local dead-reckoning distance estimate while queued (do NOT build yet) — HOLD
- What it is: while a completion is queued (per the TRIAL above), estimate trip distance client-side from accelerometer/step data as a cross-check against the last GPS fix, in case the final leg happened in a total dead zone.
- Why HOLD: this duplicates territory the edge-case matrix already flags as unread/unverified server-side (`ride_complete.py`'s own distance-at-completion validation) — building a second, client-side estimate before the server-side one is even confirmed to exist risks two disagreeing numbers with no reconciliation rule. Revisit only after that server-side check is read and, if it's missing, built first.

### 2.2 Adaptive GPS sampling, on-device smoothing & map-matching

### Add a speed-gated cadence multiplier on top of the existing state-keyed table — ADOPT
- What it is: keep `LOCATION_CONFIGS`' per-state base cadence (MR-3, already good) and add one more axis: when reported speed is near zero for N consecutive fixes (stopped at a light, waiting in a queue) within `navigating_to_pickup`/`trip_in_progress`, widen the interval toward the `arrived_at_pickup` cadence; snap back to the tight cadence the instant speed resumes.
- Who uses it / source: Android's own Fused Location Provider guidance recommends pairing location priority with the Activity Recognition API so requests relax when the device isn't moving, and generally ties priority/interval choice to accuracy-vs-battery need per scenario ([Android Developers: Optimize location use for real-world scenarios](https://developer.android.com/develop/sensors-and-location/location/battery/scenarios), fetched in full, read 2026-09-25, VERIFIED).
- Spinr today: state-keyed only (MR-3, VERIFIED); speed is read for the sensor-fusion plausibility check (`checkMovementConsistency`) but never used to throttle cadence.
- Benefit for Spinr at our scale: real battery savings on the case that matters most for a winter driving market — idling with the engine running at a stop, or waiting at a pickup that hasn't quite reached `arrived_at_pickup` state yet — at essentially zero added complexity, since the state table and the speed value are both already in hand. Cost/effort: **S**. Risk: a false "stopped" read from a bad fix widening the interval right before the vehicle actually moves — bound the widening to a capped multiplier (e.g. 2×, not 4×) and require several consecutive low-speed fixes, not one.
- How it fails or gets gamed: n/a — this is a battery/ops optimization, not a trust boundary (billing distance is computed server-side from the full fix stream per CLAUDE.md, so a wider client sampling interval doesn't change what's chargeable, only what's *sampled*).
- First step behind a flag: this changes a constant inside `LOCATION_CONFIGS`, shipped as an app update — **OTA republish**, effective next update check; an old build simply keeps the current, slightly more battery-hungry, state-only cadence, which is safe (not a regression, just not yet optimized). Rollback: OTA republish of the prior bundle. Measure success by: driver-app battery-drain-per-hour-online telemetry (if it exists — not confirmed this pass) or, absent that, a driver-reported battery-complaint rate before/after.

### On-device map-matching (snap the smoothed fix to the road graph) — ASSESS
- What it is: after the Kalman smoothing (MR-4) already dampens fix noise, project the resulting point onto the nearest plausible road segment using a small local road graph, so the marker never renders in a parking lot or on the wrong carriageway of a divided road.
- Who uses it / source: Hidden-Markov-Model map matching (the Newson & Krumm approach) is the standard technique, with lightweight-mobile-device variants reported to cut road-network storage by roughly 75% versus the naive approach at a 3–5% runtime cost ([springer.com summary via search snippet](https://link.springer.com/article/10.1007/s10619-013-7138-2), snippet, read 2026-09-25, INFERRED — an academic paper abstract, not fetched in full).
- Spinr today: not present client- or server-side live (MR-4, VERIFIED absence of a live path; the only related code, `route_validation.py`, scores a completed trip after the fact and only logs the result — session 3's CS-5, cited).
- Benefit for Spinr at our scale: a real visual-quality improvement (a car icon floating off-road is the single most visible "this app is glitchy" signal a rider can see), but the good-enough alternative is cheap: bias the smoothed point toward the last dispatch-computed route polyline (already fetched for ETA/fare) rather than building a general road-graph matcher from scratch. Cost/effort: **M** for the route-bias version, **L** for a general HMM matcher. Risk: biasing toward a stale route when the driver genuinely deviates (a real detour, not noise) would visually "snap" the marker to the wrong path — needs a deviation-distance cutoff, which overlaps with `route_deviation_alerter.py`'s existing logic (not re-read this pass).
- How it fails or gets gamed: n/a — cosmetic, no money or safety action rides on it. If it *were* ever wired into a fare or safety decision, that would need the same rigor as `route_validation.py` already has.
- First step behind a flag: pure client math (like MR-4's existing modules) — an **OTA republish** once built; no server flag. Cheapest first step: prototype the route-polyline-bias version (reuses data already on the device) before considering a standalone road-graph matcher. Measure success by: a manual visual QA pass (no visual-regression tooling exists for either app — stated per the session guardrail) at a handful of known problem intersections/interchanges, before/after.

### 2.3 WebSocket efficiency

### Enable `permessage-deflate` on the WS server, negotiated per-connection — TRIAL
- What it is: turn on WebSocket compression so repetitive JSON payloads (ride-state events with mostly-fixed field names, location updates with slowly-changing coordinate digits) shrink in transit.
- Who uses it / source: `websockets` (the library `uvicorn` already pins, MR-6) documents `permessage-deflate` support and the memory/CPU-vs-bandwidth tradeoff directly ([websockets: Compression](https://websockets.readthedocs.io/en/stable/topics/compression.html), snippet, read 2026-09-25, INFERRED — page title strongly suggests this is the library's own doc, not independently fetched). General guidance: compression cuts bandwidth and, by shortening radio-on time, mobile battery draw, at a CPU cost on both ends (search-snippet synthesis across several results, INFERRED).
- Spinr today: not configured (MR-6, VERIFIED absence).
- Benefit for Spinr at our scale: real for riders/drivers on weak rural cellular where every byte and every extra radio-on millisecond costs battery and money (data caps), but Spinr's per-connection message rate (driver location at a few Hz, not thousands) means the CPU cost per backend replica is modest, not the "flood of tiny 1 Hz-per-vehicle Kafka fan-out" scale where compression tuning becomes its own project. Cost/effort: **S** (library-level config flag, no protocol change). Risk: added CPU per connection on the backend; needs a quick load-test at Spinr's actual concurrent-connection count (a handful of hundred, not thousands) before flipping on for all traffic — not free but cheap to verify.
- How it fails or gets gamed: n/a, not a trust boundary.
- First step behind a flag: this is a server-side, non-behavior-changing wire-format change — no client app code changes at all (`websockets`/browsers negotiate the extension automatically if the server offers it), so **no OTA republish is needed** and old app binaries are unaffected either way (a client that doesn't support the extension simply doesn't negotiate it, per the WS protocol's own extension-negotiation design). Ship behind an env var / feature flag on the backend deploy, verify payload-size and CPU deltas in staging, then enable in production. Rollback: flip the flag off, no client involvement, no redeploy of mobile apps. Measure success by: `spinr_ws_fanout_duration_ms` p95 (should not regress) and outbound bandwidth per connection (should drop).

### Quantized/rounded coordinates on the high-frequency location broadcast — ASSESS
- What it is: round lat/lng to a fixed number of decimal places (e.g. 6 decimals ≈ 11cm, more than enough for a map marker) before broadcasting over WS, and consider a delta-from-last-fix encoding for the hottest path.
- Who uses it / source: delta encoding of quantized vertices is a documented general compression technique for arrays of nearby values ([search-snippet synthesis across patent/game-dev sources](https://www.gamedev.net/forums/topic/713576-delta-compression-precision/), INFERRED, not a primary standards source); one search result estimated 60–80% payload reduction for moving-asset fleets at a scale far larger than Spinr's (thousands of vehicles/second) — treated as directionally suggestive, not a number Spinr should plan around at six service areas' worth of concurrent trips.
- Spinr today: full-precision floats broadcast on every fan-out (MR-7, VERIFIED absence of rounding).
- Benefit for Spinr at our scale: modest — Spinr's concurrent-ride count is nowhere near where per-message byte-shaving matters more than `permessage-deflate` (above), which gets most of the same win for less engineering (compression already collapses repeated-digit precision reasonably well) and needs no schema/client change at all. Cost/effort: **S**, but touches a schema both `shared/types/api/wsEvents.ts` and both apps' location-consuming code read — a coordinated change, not a pure server toggle. Risk: rounding before storage (as opposed to only before broadcast) would need care not to degrade the billing-relevant distance calculation, which must stay on full precision.
- How it fails: n/a.
- First step: **do `permessage-deflate` first and re-measure** — quantization is very likely redundant with it at Spinr's scale. Only pursue this if bandwidth is still a measured problem after compression is on.

### Distinguish "delivered locally" from "lost to a Redis outage" in the fan-out metric — ADOPT (REL-005's own recommendation, restated for this session)
- What it is: cited from `reliability.md` (VERIFIED there) — emit `spinr_ws_fanout_pubsub_unavailable_total` at the `False`-return branch in `socket_manager.py:373`, instead of letting a genuinely-local delivery and a cross-replica-lost delivery both show as `path=local`.
- Spinr today: REL-005 (VERIFIED).
- Benefit: this is the prerequisite for any of the efficiency work above to matter during an actual Redis blip — compression and quantization are irrelevant to a message that never left the wrong replica. Cost/effort: **S** (one counter at an existing branch). Risk: none.
- First step behind a flag: backend-only metric addition, no client involvement, no flag needed (additive observability). Rollback: remove the counter. Measure success by: the counter itself becoming visible and alertable during the next Redis blip (staging or production), closing the detection gap `reliability.md` names.

### Full binary WS protocol (protobuf/msgpack framing) — HOLD
- What it is: replace JSON WS frames with a binary schema.
- Why HOLD: this is the Uber-global-scale move (millions of concurrent location streams), not a six-service-area operator's bottleneck. `permessage-deflate` plus the existing seq/replay and REL-005's metric fix address the real gaps at far lower engineering cost and lower risk to a live-tested product (a binary protocol change touches every WS message shape at once, the opposite of the "surgical changes" principle). Revisit only if bandwidth cost or CPU at the JSON-parse layer is measured as a real bottleneck after the cheaper wins above are shipped.

## §3.1 What not to build

- **A general on-device HMM map-matcher from scratch, before trying the cheap route-polyline-bias version.** Spinr already has the route polyline on-device for ETA/fare; use it before building a road-graph matcher.
- **A full binary WS protocol (protobuf/msgpack).** Uber-global-scale territory; `permessage-deflate` plus the existing seq/replay mechanism and REL-005's metric fix cover the real gaps at Spinr's scale for far less risk to a live product.
- **Client-side dead-reckoning distance estimation** as a second, independent distance source before the server-side `ride_complete.py` validation this session (and two prior lanes) flagged as unread is actually confirmed to exist and work.
- **A fully-unattended, auto-triggered crash-rate rollback** on day one. Ship the Sentry-crash-rate automation in human-review-required mode first; only remove the human once its false-positive rate is measured.
- **A monorepo/workspace re-tooling for the shared mobile core.** `04-blueprint.md`'s H5 verdict stands: `@spinr/shared` is the right shape already; the work is parity enforcement, not a rewrite.
- **Shipping the reduce-motion fix for `CarMarker.tsx` as a silent default-on change** ahead of the essential-motion product decision in §5 — the code is cheap; shipping it without that decision recorded risks a safety-adjacent UX call being made by omission.
- **Treating any of this session's design-blog/secondary-source claims (thumb-zone percentages, delta-encoding bandwidth-reduction percentages, Hermes cold-start-improvement percentages) as settled numbers.** Every one is INFERRED from a search snippet, not fetched or independently measured against Spinr's own code — re-verify against Spinr's own telemetry before using a specific percentage in a roadmap commitment.
