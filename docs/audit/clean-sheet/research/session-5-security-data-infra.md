### 2.1 Tokens

### `kid`-tagged dual HS256 secrets + a separated `OTP_PEPPER` and rate-limiter key — ADOPT (Next, already the corrected plan)
- What it is (plain language): give every JWT a `kid` header naming which of two currently-valid HS256 secrets signed it, so rotation becomes "accept both keys for one window, then retire the old one" instead of a single global logout; stop reusing that same secret as the OTP pepper or the rate-limiter's decode key.
- Who uses it / source: this is Spinr's own already-corrected plan, not an external pattern — `04-blueprint.md`'s Authentication & Authorization epic (its "Clean-sheet Spinr would" paragraph, re-worded by `08-hostile-review.md` correction 15) names it explicitly as the **Next** step, promoted specifically because the asymmetric-mint alternative below was found to not deliver its claimed benefit without a redesigned issuer boundary.
- Spinr today: one shared `JWT_SECRET` is the verify key, the mint key for three token classes, the OTP pepper fallback, and the rate-limiter's decode key, on every replica of both deploy providers (SEC-A2-001, VERIFIED).
- Benefit for Spinr at our scale: high, cheap. Turns a rotation from a global-logout incident into a routine two-key window; separates the pepper so an `otp_records` leak and a token-forgery leak are no longer the same failure. Cost/effort: **S**. Risk: low — `kid`-based dual verify is additive (both keys accepted during the window) and reversible.
- How it fails or gets gamed: it does not reduce the "leaked replica env mints a token" blast radius, because every replica still runs the issuing routes under this model — that reduction needs the asymmetric-mint + separate-issuer redesign below, which is why this card and that one are ranked differently.
- First step behind a flag: `JWT_KEYS` map `{kid: secret}` with dual-HS256 verify, dark-launched; set `OTP_PEPPER` explicitly in the **same** maintenance window (SESS5-01); separate the rate-limiter's decode key next. Measure success by: a rotation completes with `spinr_auth_token_verify_failed_total{reason}` (a metric that must exist *before* rollout — `08-hostile-review.md` U-14's own correction to the blueprint's unmeasurable "zero forced logouts" exit criterion) staying at pre-rotation baseline.

### Asymmetric JWT (ES256/EdDSA) + JWKS with a separate issuer boundary — HOLD → Later
- What it is: mint with a private key that exists only on the token-issuing path; every other replica and future partner/edge verifier holds only the public key, published at a `/.well-known/jwks.json`-style endpoint.
- Who uses it / source: industry pattern for services that verify tokens minted elsewhere (INFERRED — no primary source fetched this session; `security.md` §5 cites the same pattern as INFERRED). PyJWT already supports ES256 in this codebase for the unrelated APNs provider-token path, so the library dependency is not new (VERIFIED, `utils/apns_client.py`).
- Spinr today: every backend replica on both Fly and Railway runs the same process, including the routes that mint tokens — there is no separate "issuer" process today. `08-hostile-review.md` row A-1/I-10 found the earlier blueprint draft's benefit claim ("a leaked replica env no longer mints") false under this topology: since minting and verifying happen in the same process everywhere, asymmetric keys alone do not shrink the blast radius until issuance is pulled into its own boundary.
- Benefit for Spinr at our scale: **currently low** — the claimed edge requires a redesign Spinr has not scoped or costed, and the dual-HS256 card above gets most of the operational benefit (routine rotation) for a fraction of the cost. Cost/effort: **M**, but understated until an issuer-separation ADR exists. Risk: a broken dual-verify during cutover logs everyone out — must be dark-launched behind `JWT_HS256_ACCEPT=true` the whole way.
- How it fails or gets gamed: none of this closes the "one process, many secrets" problem by itself; it only reduces the *verify*-side exposure once mint is actually separated, which nothing in the current architecture forces.
- First step (when this is revisited, not now): write a superseding ADR to ADR-005 first, naming who runs the issuer, before any code. Measure success by (once that ADR exists): the same `spinr_auth_token_verify_failed_total{reason}` metric, plus a named owner for the issuer process.

### DPoP — sender-constrained refresh tokens (RFC 9449) — ASSESS
- What it is: the client proves possession of a private key on every request using that token, so a refresh token copied out of a device backup or intercepted in transit is useless without the matching key.
- Who uses it / source: [RFC 9449, "OAuth 2.0 Demonstrating Proof of Possession (DPoP)"](https://datatracker.ietf.org/doc/html/rfc9449), read 2026-09-25, INFERRED (structure only, not a full read). `security.md`'s own A2 research table already rates this ASSESS, worth doing only after asymmetric keys land.
- Spinr today: refresh tokens are random bytes, SHA-256 hashed at rest, rotated on use, with reuse-as-theft-cascade detection (VERIFIED, `security.md` §1 SEC-A2-001 table row). This already covers the "stolen from the database" case; DPoP additionally covers "stolen off the wire or off a device backup, used before rotation is detected."
- Benefit for Spinr at our scale: moderate, narrow. Cost/effort: **M** (a per-request proof JWT on mobile plus a nonce store). Risk: mobile clients (React Native/Expo) need a DPoP-capable HTTP layer; this is not a drop-in library today (UNKNOWN — not checked this session).
- How it fails: a compromised device with the key material intact defeats DPoP the same as any other control; it only raises the bar for a copied-token-without-the-device attack.
- First step: revisit only after the dual-HS256/separated-pepper step lands and the SEC-R10-004 grace-window ordering fix (below) ships — DPoP is a stronger version of the same "who actually holds this token" question that fix already targets more cheaply.

### Refresh-token benign-replay window made possession-aware — ADOPT (already filed, restated here as the token-binding answer to the research question)
- What it is: the existing 600-second "replay of a just-rotated parent is probably the same device retrying" grace window currently classifies *whichever side replays first* as benign, regardless of who holds the successor token — so a thief who replays before the legitimate device does keeps the session, and the legitimate device's own later retry is what gets flagged.
- Spinr today: exactly this, VERIFIED (`security.md` SEC-R10-004, `utils/refresh_tokens.py`).
- Benefit: this is the cheapest available device-binding-style fix and does not require DPoP's client-side work — it only requires checking that the replaying caller also holds (or plausibly is) the same device as the successor, before calling a replay benign. Cost/effort: **S–M**. Risk: low, behind a flag.
- First step: as already recommended — require the caller to present the successor token or a matching device signal for the benign branch, and bump `token_version` on every *interactive* login so a victim's next sign-in always kills a thief's chain. Measure success by: the specific regression test named in SEC-R10-004 ("attacker-first sequence ends with attacker's T1 rejected after victim re-login").

### 2.2 Admin passkeys / WebAuthn

### WebAuthn passkeys as a second enrolment path for `super_admin`, alongside existing TOTP — TRIAL
- What it is: phishing-resistant, hardware-bound sign-in credentials (a platform authenticator like a laptop's fingerprint reader, or a security key) as an additional factor admins can enrol, not a replacement for the password+TOTP path on day one.
- Who uses it / source: OWASP classes FIDO2/WebAuthn as the most phishing-resistant authenticator class available ([OWASP MFA Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html), read 2026-09-25, INFERRED — cited already in `A2-security.md`'s own research table, re-confirmed this session). Python/FastAPI WebAuthn server libraries exist and are maintained (`py_webauthn` was named repeatedly across independent search results as the standard low-level Python WebAuthn server library; several higher-level passkey-as-a-service options also exist), read 2026-09-25, INFERRED (search-summary, not a fetched library page).
- Spinr today: admin auth already has TOTP enforced by default (`ADMIN_MFA_ENFORCED`), a fail-closed break-glass path, and per-account + TOTP lockouts (VERIFIED, `security.md` §1 SEC-R10-006 evidence). No passkey/WebAuthn code exists anywhere in the repo (VERIFIED absence, grep — consistent with `A2-security.md`'s finding).
- Benefit for Spinr at our scale: real but narrow — Spinr has exactly 2 `admin_staff` rows today (VERIFIED-LIVE, `security.md` §1.1 context), so the population this protects is tiny, but so is the cost of protecting it, and admin is the surface that can move money and see every rider/driver's PII. Cost/effort: **M** (server library + two enrolment/verify endpoints + an admin-dashboard UI flow — no existing UI to extend). Risk: passkey recovery is itself a hard problem (a lost device with no backup key locks an admin out) — needs a documented recovery path (support-mediated re-enrolment with the existing TOTP/break-glass as the fallback), or this just adds a new way to get locked out without removing any risk.
- How it fails or gets gamed: passkeys do not stop a compromised admin laptop (the passkey's private key lives there); they stop credential phishing and password reuse specifically, which is exactly the gap TOTP does not close (TOTP codes can still be phished in real time; WebAuthn's origin-binding cannot).
- First step behind a flag: `admin_passkey_enrollment_enabled` (default off), super_admin only, TOTP stays required in parallel (defense in depth, not a replacement) until the recovery path is proven. Measure success by: both admin accounts successfully enrol and complete one login with a passkey in staging before any production flip; zero support tickets for passkey lockout in the first enrolment month.

### Passkeys as the *only* second factor (removing TOTP) — HOLD
- Why HOLD: removes a working, already-enforced control (TOTP) for a two-person admin population before the passkey recovery path has been proven even once. No forcing function exists to justify the removal at this scale; keep both, as above.

### Application-layer envelope encryption with a Canadian-region KMS, dual-read alongside Vault — TRIAL
- What it is: encrypt each sensitive value with a random per-value data key (AES-256-GCM), wrap that data key with a key-encryption key held in a cloud KMS, and store the ciphertext with a key-id prefix so the decrypting service knows which KEK version to ask the KMS for. Key rotation becomes "re-wrap the data keys with a new KEK," not "re-encrypt every row."
- Who uses it / source: standard envelope-encryption pattern (INFERRED — industry pattern, no vendor page fetched). Regional availability confirmed by search: AWS KMS is offered in essentially all AWS regions including `ca-central-1` ([AWS KMS region availability](https://awsfundamentals.com/regions/service/aws-key-management-service-kms), read 2026-09-25, INFERRED), and GCP's Montreal region (`northamerica-northeast1`) is a standard GCP region that carries the full regional service catalogue including Cloud KMS per GCP's own regional-availability model (INFERRED — not independently re-confirmed against a fetched GCP KMS availability page this session; treat as ASSUMED for a build decision until that page is read).
- Spinr today: the crypto boundary for the driver licence-number field, the driver SIN field (write-only, no app read path), and emergency-contact fields is a Postgres extension (pgsodium) the vendor's own docs (per search snippet) say not to build new usage on — Vault itself is said to be unaffected by the pgsodium deprecation, which is exactly the unverified claim SEC-A2-002/SEC-R10-010 already flag (VERIFIED extension state; INFERRED vendor-migration-safety claim).
- Benefit for Spinr at our scale: moderate-high for exactly three column families (driver licence number, driver SIN, emergency-contact fields) — these are 7-year-retention, regulator-facing values where "the vendor deprecated our crypto primitive out from under a 7-year-retention record" is the specific harm to avoid. It does **not** need to extend to the rest of the schema (most PII at Spinr is plaintext-at-rest by design, per the data-classification matrix, gated by application-level authz rather than column encryption — that is a separate, larger decision this card does not recommend). Cost/effort: **M** (one module, three columns, a backfill job, a KMS account). Risk: low-medium — dual-read (a `enc:v1:<kid>:` prefix vs. the existing Vault-UUID shape) means no destructive step until the new path is proven; region choice must be pinned and documented the same way the existing SES client already pins `ca-central-1` for email.
- How it fails or gets gamed: envelope encryption does not change *who* can call decrypt — that access-control question is separate and should be paired with an audit row per decrypt call (the current Vault RPC path has no such row either — this is a shared gap, not new to this design).
- First step behind a flag: build `utils/envelope.py`, dual-read against the existing Vault UUID column, migrate the driver licence-number field first (lowest-churn of the three). Measure success by: 100% of new writes go through envelope encryption with zero read-path regressions over one release cycle before touching the SIN/emergency-contact columns.

### Tokenising SIN and driver licence numbers (replace the value with a non-reversible or vault-referenced token everywhere except the one decrypt path) — HOLD, mostly already true
- What it is: instead of storing an encrypted value that *can* be decrypted, store only an opaque reference token and keep the real value in a single, narrowly-accessed vault service, so a database leak yields tokens, not decryptable secrets.
- Spinr today: the driver SIN field is **already** stored this way — write-only via the Vault RPC, with **no app-layer decrypt path found** (VERIFIED, `security.md` SEC-R10-010 evidence; `data-classification.md` §2). The driver licence-number field, by contrast, **does** have an app-layer decrypt path (admin/self viewing, a licence export) because the product needs to show it back to a human.
- Why mostly HOLD: for the SIN field, tokenization would add a new vault service without removing any exposure that does not already exist — the field has no read path to protect further (A2's own research table already reaches this conclusion). For the licence-number field, the product's own requirement (drivers and admins need to *see* the number, not just prove it matches) is incompatible with one-way tokenization — envelope encryption (above) is the right shape there, not tokenization. Revisit tokenization only if a future feature needs to *match* SIN/licence values without ever displaying them (e.g. a cross-driver duplicate-SIN check) — that is a narrower, legitimate use tokenization is well suited to, and does not exist today.

### SLSA Build provenance attestation (reach L2) — ADOPT
- What it is: a signed statement from the CI system itself, attached to the built image, saying which source commit, which workflow, and which build steps produced it — verifiable independently of trusting the registry.
- Who uses it / source: [SLSA v1.0 specification](https://slsa.dev/spec/v1.0/levels), read 2026-09-25, INFERRED (search-summary of the spec's own level definitions, not a full read). SLSA v1.0's Build track runs L0–L3: L1 is "provenance exists," L2 adds a hosted build platform and tamper-resistant signing, L3 adds platform isolation and confidentiality guarantees between builds.
- Spinr today: hosted build (GitHub Actions), cosign keyless signatures on sha-tagged images, and a signature-verification gate before Fly deploy already exist — this is most of L2's *mechanism* already in place, but no actual SLSA provenance predicate is attached; the existing "BUILD PROVENANCE (CLOSED)" marker in `deploy-fly-signed-image.yml` refers to a separately stamped build-info file, not a SLSA provenance predicate that a tool like `cosign verify-attestation --type slsaprovenance` would recognise (VERIFIED, SEC-R10-017).
- Benefit for Spinr at our scale: this closes the gap between "we believe we're at L2" and "a tool can verify we're at L2" for close to zero additional infrastructure — Spinr already has the hosted-build and signing prerequisites L2 needs; it is missing only the provenance-generation step itself. Cost/effort: **S** (one more CI step, same PR as the SBOM step above). Risk: none.
- How it fails or gets gamed: provenance attestation proves *what* built the artefact, not that the source itself is trustworthy — it does not replace code review or dependency pinning, both of which Spinr already has (246/253 SHA-pinned actions, `--require-hashes` in the Dockerfile).
- First step: add a provenance-attestation step to the same CI job as the SBOM step. Measure success by: `cosign verify-attestation --type slsaprovenance` passes on a `main` image (SEC-R10-017's own verification-to-close criterion).

### SLSA L3 via a fully isolated, ephemeral, ambient-credential-free builder — HOLD
- Why HOLD: L3 adds build-platform isolation and confidentiality guarantees between concurrent builds, aimed at defending against an attacker who can influence *other* tenants' builds on a shared build service, or extract build-time secrets from a running build. GitHub Actions' hosted runners already give reasonable isolation for a single-tenant OSS-style pipeline; the realistic threat at Spinr's team size is a compromised dependency or a leaked CI secret, both of which L2 plus existing hash-pinning already address. Revisit only if Spinr's build pipeline starts running third-party or untrusted code as part of the build itself.

### 2.7 Data — partitioning, tiered retention, data contracts

### Native declarative partitioning (range, by month) for `driver_location_history` and GPS-bearing ride columns — ADOPT
- What it is: instead of one large table with an application-level purge loop deleting old rows, the table is declared as a set of monthly (or weekly) child partitions; dropping a partition for data past its retention horizon is a metadata operation (`DROP TABLE`), not a row-by-row `DELETE` that has to scan and lock a large table.
- Who uses it / source: PostgreSQL has supported declarative partitioning natively since version 10; range partitioning by a time column is the standard default for time-series-shaped data, and "retention becomes `DROP TABLE`" is repeatedly named as the main operational win over an application purge loop across independent sources ([PostgreSQL partitioning strategies](https://dev.to/finny_collins/postgresql-partitioning-4-strategies-for-managing-large-tables-416d), [Postgres time-series partition maintenance](https://medium.com/@philmcc/postgres-time-series-partition-maintenance-guide-1d4302792197), read 2026-09-25, INFERRED). A hard constraint search results repeatedly flagged: every unique index/primary key on a partitioned table must include the partition key column, which affects schema design, not just the retention job.
- Spinr today: `driver_location_history` (90-day retention), the GPS columns on `rides`/`ride_routes` (3-year anonymisation / 7-year hard delete), and the regulatory append-only tables (`driver_insurance_periods` and its siblings, 7-year retention, append-only, UPDATE/DELETE blocked by trigger) are all governed by the migration-296-step purge model today — an application-level job, not native partitioning (SESS5-04, this session's own cross-read of `data-classification.md` §3/§4; not independently re-verified against the purge job's actual SQL this session — UNKNOWN whether it already uses a `WHERE created_at < ...` batched delete or a naive full scan).
- Benefit for Spinr at our scale: real, and grows with data volume — `driver_location_history` is the table most likely to be large enough that a purge loop's row-by-row delete becomes a lock-contention or replication-lag risk before anything else in the schema does, given every online driver writes to it continuously. Cost/effort: **M** (a genuine schema migration: create the partitioned table, backfill, cut over writes, verify the append-only triggers and RLS carry over to each partition — Postgres does not automatically apply a parent's RLS policy semantics identically to every partition without care). Risk: medium — this touches a live-written, regulator-relevant table; needs a dual-write or shadow-table cutover, not an in-place `ALTER`.
- How it fails or gets gamed: partition pruning only helps if queries actually filter on the partition key (the time column) — a query that scans by driver_id without a time bound gets no benefit and could regress if partition-exclusion planning adds overhead on a query pattern the current single table didn't have.
- First step behind a flag: pilot on `driver_location_history` only (highest write volume, shortest retention, least regulatory sensitivity of the three families) — monthly partitions, dual-write to old and new for one retention cycle, verify the 90-day drop-a-partition path against the existing purge job's output before touching the 7-year regulatory tables. Measure success by: the 90-day purge step's wall-clock time and lock duration before vs. after (a metadata-only `DROP TABLE` should be near-instant regardless of row count, vs. a `DELETE` that scales with rows deleted).

### Explicit, documented data contracts between the mobile apps / admin-dashboard and the backend API — TRIAL
- What it is: a machine-checked producer–consumer agreement on schema, semantics and (where relevant) an SLA for a data flow — not just an OpenAPI shape, but an explicit statement of what changes are breaking, who owns the schema, and what a consumer can rely on.
- Who uses it / source: "a data contract is a machine-checked producer–consumer agreement on schema, semantics, quality, and SLAs... producers own their contracts... the team that produces data is responsible for its quality, freshness, schema stability" ([Atlan: Data Contracts Explained](https://atlan.com/data-contracts/), [IBM: What Is a Data Contract?](https://www.ibm.com/think/topics/data-contract), read 2026-09-25, INFERRED).
- Spinr today: `04-blueprint.md`'s own H6 hypothesis ("Contract-first API with generated clients") already names the gap this maps to, and the blueprint's §7 build order treats an OpenAPI snapshot diff as one of the cheap "static conventions as tests" wins (bundled with INT-001/SKB-001/the loop-threshold test). This card does not propose new scope beyond H6/the existing OpenAPI-diff plan — it reframes it as "data contracts," which is the standards-mapping vocabulary this research question asks for, and adds one extension: the WebSocket event inventory (`matrices/event-ws-inventory.md` already exists, per the repo listing) is exactly the kind of schema surface a data-contract discipline should also cover, since it is not caught by an OpenAPI diff at all (WS payloads are not part of the REST OpenAPI spec).
- Benefit: low incremental cost over what is already planned (H6/OpenAPI-diff) — mostly a documentation and CI-check framing, not new infrastructure. Cost/effort: **S** incremental (on top of H6, already scoped). Risk: none.
- First step: when the OpenAPI-snapshot-diff CI check (already in the blueprint's build order) ships, add a second, parallel diff over the WS event-type literal set (already inventoried at `matrices/event-ws-inventory.md`) so a breaking WS payload change fails CI the same way a breaking REST response shape would. Measure success by: a deliberately breaking WS payload change in a test branch fails the new check.

### 2.8 Resilience — priority load shedding, per-vendor isolation, error budgets

### Named criticality tiers for load shedding, starting from ADR-011's existing per-flag semantics — TRIAL
- What it is: when the system is under load or a dependency is degraded, shed the least-important work first and keep the most important work flowing — "least/most important" decided in advance, per request type, not improvised during the incident. Google's SRE practice frames this explicitly: request criticality is orthogonal to latency requirements, and a well-designed system propagates a criticality label through its call chain so a backend three hops deep still knows whether the original request was sheddable ([Google SRE: Handling Overload](https://sre.google/sre-book/handling-overload/), [Google SRE: Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/), read 2026-09-25, INFERRED).
- Spinr today: no explicit criticality-tiered shedding scheme exists. The closest existing primitive is ADR-011's **per-flag** fail-open/fail-closed/last-known-good semantics for money-path kill switches (VERIFIED, read in full this session) — which is the same underlying judgement ("which direction of failure is worse for *this* specific thing") applied one flag at a time, not yet generalised into a named tier system. CLAUDE.md's own guardrail language ("shedding load by priority — SOS and payments first") is a stated goal with no implementing mechanism found this session.
- Benefit for Spinr at our scale: Spinr does not need Google's full RPC-criticality-propagation machinery — that is explicitly HOLD-scale (a two-person team, one backend process type, no service mesh). What is directly applicable and cheap: (1) name three tiers explicitly in a shared module — **Tier 0** (SOS send, payment settlement, ride-state transitions), **Tier 1** (dispatch offers, location writes), **Tier 2** (everything else — analytics, AI assistant, marketing, non-critical background loops); (2) when a shared resource is saturated (DB connection pool exhaustion is the most likely real trigger, given Spinr's single-Supabase-project topology), degrade or pause Tier 2 work first, via the *same* `app_settings` kill-switch pattern ADR-011 already establishes and CLAUDE.md already documents as supporting flag-without-redeploy. Cost/effort: **M** (naming the tiers and wiring 2–3 existing Tier-2 loops to a shared "backpressure" flag is small; a real automatic trigger off connection-pool saturation is the harder, optional half). Risk: low if done additively — start with a manual/documented tier list and a kill switch operators can flip by hand during an incident, before automating the trigger.
- How it fails or gets gamed: a tier list that is never rehearsed decays the same way the SOS runbook decayed (per the trust-safety-fraud session's own finding on an unimplemented runbook promise) — this must ship with at least one documented drill, not just a doc.
- First step behind a flag: write the three-tier list as a short doc (no code), citing which existing background loops/routes fall in each tier; add one `app_settings`-gated "pause Tier 2 loops" switch reusing the existing kill-switch pattern (`dispatch_direct_pool_enabled`-style, per `reliability.md` §8's own citation of that pattern working well). Measure success by: the switch is exercised at least once in a staging drill before being relied on in a real incident.

### Per-vendor circuit breakers and failure-rate isolation, closing the two already-filed gaps — ADOPT (Now)
- What it is: each third-party dependency should fail in a way that does not block or slow down requests that do not need it, and a *slow* vendor should be detected and isolated the same way a *down* vendor already is.
- Spinr today: this is a mixed picture, already mapped in detail by `matrices/integration.md` (read in full this session, not re-derived): **Supabase** has "the best-built breaker in the codebase" (half-open, single-probe recovery, fails fast after 5 failures/30s) — a strong existing pattern to copy from, not a gap. **Twilio** has **no timeout at all** on its client construction, so a slow-not-down Twilio incident *hangs* rather than fails fast, and because it runs on the shared default thread-pool executor, a Twilio slowdown can starve unrelated calls (INT-001, VERIFIED, rated CRITICAL and unfixed — already independently prioritised in the blueprint's §7 build order as a bundled "cheap static-conventions" fix). **Google Maps** has per-call-site timeouts but no failure-rate breaker on Places/Autocomplete/Geocode/Static (only OSRM→Google→haversine ETA has a real fallback chain) — a Google 5xx incident is a hard "can't search a destination" outage that fails slow, not fast (INT-004, VERIFIED). **LLM providers** (Anthropic/OpenAI/Gemini/OpenRouter) have no timeout either (INT-005, VERIFIED) — lower stakes since the AI assistant is explicitly off the critical path, per the integration matrix's own framing.
- Benefit for Spinr at our scale: the fixes are small, independent, and already scoped by an existing lane (§2.4/API Top 10's API10 row cites the same three IDs) — this card's contribution is framing them explicitly as the "per-vendor isolation" half of this research question, and sequencing them: Twilio first (CRITICAL, blocks OTP send — a life-cycle-critical path), then Maps (fare-estimate-path, already has a partial fallback chain to extend rather than build from scratch), then the LLM providers (lowest stakes). Cost/effort: **S** each (add a timeout; add a failure-rate breaker using the same pattern `repositories/_base.py`'s Supabase breaker already implements, rather than inventing a new one). Risk: low — additive, and Twilio specifically needs a timeout regardless of the breaker question, since "hangs forever" is strictly worse than "fails fast" no matter what wraps it.

## §3.1 What not to build

- **Asymmetric JWT before a superseding ADR exists.** `08-hostile-review.md` already found this exact mistake once (the earlier blueprint draft claimed a security benefit the architecture cannot actually deliver without a separate issuer) — do not repeat it by shipping the code before the design decision.
- **A full SLSA L3 isolated builder.** No threat model finding here implicates cross-tenant build isolation as a realistic risk at Spinr's scale; L2 (already nearly built) covers the realistic attacker.
- **A bespoke SIEM, an in-house 24/7 security operations centre, or a dedicated key-management team.** All HOLD by the scale screen — a two-person part-time security/infra function cannot staff any of these, and each has a managed, lower-operational-cost equivalent already named above (managed KMS, existing Sentry/Prometheus pipeline once C11 ships).
- **Full OpenTelemetry tracing before ADR-014's own trigger fires.** This would duplicate an already-made, reasoned decision. Revisiting it is explicitly welcomed by the ADR itself, but only against the real pain point at the time, not preemptively.
- **Tokenising the SIN field.** It is already stored in the token-shaped form (write-only, no app decrypt path) that tokenization would produce — building a second vault service to do the same job adds cost with no reduction in exposure.
- **Removing TOTP when admin passkeys ship.** Two factors, kept in parallel, is the correct posture for a two-person admin population until passkey recovery is proven at least once.
- **A universal "fail every money-path flag closed" rule.** ADR-011 already tried and rejected this — the six unrelated platform-availability kill switches it surveyed would take down all new bookings platform-wide on a single settings-read blip if forced closed uniformly. Any criticality-tier work (§2.8) must extend ADR-011's per-flag judgement, not replace it with a blanket rule.
- **Automatic error-budget-driven load shedding before metrics are actually flowing.** Building the automation on top of C11's still-unmeasured SLA rows would automate a decision made from no data.
- **A device-fingerprinting or third-party attestation SDK reused for anything beyond its stated purpose.** Not this session's own scope (the trust-safety-fraud session owns GPS-spoofing/App-Check-as-signal in depth), but worth restating here since several of this session's own cards (Play Integrity/App Attest, mentioned only in passing via SEC-A2-005) touch the same surface: any device signal stays signal-only, never a hard gate, consistent with CLAUDE.md's contractor-classification guardrail.
