## Decision: Write a config-only rollback (UPDATE, not DROP/DELETE) for migration 354
**Stage:** Development
**What was decided:** Resolving the flag Stage 3-4 raised (see the decision above), the rollback comment in `backend/migrations/354_kyb_documents_bucket_private.sql` does not offer `DROP TABLE`, `DELETE FROM storage.objects WHERE bucket_id = 'kyb-documents'`, or `DELETE FROM storage.buckets WHERE id = 'kyb-documents'` as options at all — the only rollback given is `UPDATE storage.buckets SET public = false WHERE id = 'kyb-documents'` plus `NOTIFY pgrst, 'reload schema'`, with an explicit inline warning against the destructive alternatives.

**Reversible?** Yes — this is comment text, not executable schema; if a future stage determines the bucket genuinely needs to be dropped (e.g. the feature is fully decommissioned and all documents are confirmed migrated/deleted through the proper PIPEDA retention process), that would be its own new migration with its own justification, not a retroactive edit to this one's rollback comment.
