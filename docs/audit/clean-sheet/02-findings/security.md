## 1. Steelman — what the current design gets right (and why it was built this way)

Everything in the rapid baseline's §(d) re-verified; additions from the deeper read:

1. **The admin pipeline is genuinely layered and the docs under-sell it.** `_verify_admin_payload` (`dependencies/__init__.py:262-450`) enforces `aud=spinr:admin`, a jti denylist, `admin_staff.is_active`, `token_version` re-read from the DB, and a 30-min idle timeout; `get_admin_user` (`:800-818`) gates on a private `_admin_verified` marker that only that function can set and that is stripped from every DB-sourced row (`:568,:730`). A role/modules change on a staff row bumps `token_version` **and** revokes every refresh token (`routes/admin/staff.py:369-373`) — so SEC-A2-008's "modules only take effect at token expiry" is narrower than stated: the claim is trusted, but the claim cannot outlive a change. CLAUDE.md "admin JWTs are fully trusted" is wrong in the safe direction.
2. **Every principal path converges on one verifier.** HTTP (`get_current_user`), WebSocket (`routes/websocket.py:742-749`) and MCP (`ai/mcp_server.py:185-197`) all call the same `_verify_admin_payload`/`get_current_user`; the WS heartbeat re-checks `token_version`/`sessions_invalid_before` every 10 s and force-closes with 1008 on revocation (`:520-560`). Three copies of the check would have been the Spinr-typical failure (W0 §2); here there is one.
3. **OTP brute-force posture is fail-closed where it matters.** `_check_otp_lockout` and `_enforce_otp_send_cap` both raise 503 on a Redis error (`routes/auth.py:213-277`); only the failure *counter* is best-effort. The keyed-HMAC pepper (`utils/crypto.py:11-56`) removes the offline 10,000-entry rainbow table, and the legacy unsalted fallback was deliberately deleted with a dated rationale.
4. **Refresh tokens follow RFC 9700 §4.14.2** (rotation, reuse-as-theft cascade, hashed at rest, 384-bit entropy, `revocation_reason` so an explicit logout replay is not mis-classified as theft, one-cascade-per-row so a stale install cannot log a driver out repeatedly — `utils/refresh_tokens.py:300-345`). This is better than most production OAuth servers.
5. **RLS is enabled on 100 % of public tables live** (VERIFIED-LIVE: `list_tables` shows `rls_enabled: true` on every one of the 131 public tables; `get_advisors` reports zero `rls_disabled_in_public`). With no anon-key client anywhere in shipped code (VERIFIED: `@supabase/supabase-js` is in `rider-app/package.json:40` and `driver-app/package.json:26` but **nothing imports it** — grep for `from '@supabase` returns no hits) and a separate custom `JWT_SECRET`, the "dormant" RLS layer is a deny-all wall behind a door nobody has a key to. That is the right default.
6. **PII scrubbing is defence-in-depth with one definition of PII.** `utils/pii.py` key-name denylist is shared by the Sentry `before_send`/`before_breadcrumb` hooks, the loguru sink guard, and the AI egress (`utils/sentry_scrub.py:30-45`); `pipeda_sentry_options()` sets `send_default_pii=False` and `include_local_variables=False` (`:116-140`). The AI path scrubs on ingest, on stream, on persist, and re-scrubs STRICT on the third-party MCP egress (`ai/mcp_server.py:126-137`).
7. **Production fail-fast is broad** (`core/config.py:366-432`, `core/middleware.py:725-760`): weak `JWT_SECRET`/`ADMIN_PASSWORD`, placeholder Supabase key/URL, missing Firebase audiences, non-Canadian region, wildcard CORS all refuse startup.
8. **Supply chain is better than average for a team this size:** `requirements-locked.txt` carries 3,391 `--hash=` pins and `backend/Dockerfile:49` installs with `--require-hashes`; base images are digest-pinned; 246 of 253 `uses:` lines are SHA-pinned (the 7 unpinned are local `./.github/...` paths — C18 is effectively closed); sha-tagged images are cosign-signed keyless (`ci.yml:1218-1262`) and the Fly deploy verifies the signature before rollout (`deploy-fly-signed-image.yml:139-165`); Gitleaks/Semgrep/Bandit/pip-audit/npm-audit/ZAP-baseline all run.
9. **The MCP surface is a model of least privilege:** read-only tool subset, staff tokens rejected fail-closed via both the marker and a role backstop, two independent kill switches, per-user daily cap with a bounded local fallback, and identity taken from the verified token — never from an MCP parameter.

### SEC-R10-004 — The refresh-token reuse grace window lets an attacker who uses a stolen token *first* stay logged in undetected; the victim's own retry is what gets classified as "benign"
- Hierarchy: L2 Authentication & Authorization › L3 JWT/session › L4 S-auth-03 › L5 refresh-token theft
- Severity: MEDIUM   Priority score: 3×4×2 = 24
- Status: VERIFIED (code path) / INFERRED (client behaviour after a 401)   Existing item: new — the window's growth 60 s → 600 s is documented as deliberate in `utils/refresh_tokens.py:57-79`; no ACTION_ITEMS entry weighs the security cost
- Adversary: account-takeover attacker holding a refresh token from a device backup / malware / a shared device
- Evidence: `utils/refresh_tokens.py:122-134` `_is_benign_rotation_replay` returns True for any replay of a `replaced_by` row within `REFRESH_REUSE_GRACE_SECONDS = 600`; `:300-315` returns a clean 401 and **no cascade** in that case. The logic gap (described at fix level, not as a procedure): the benign branch keys only on *how recently* the parent was rotated, not on *who* holds the successor. When the legitimate device is the second presenter rather than the first, its replay is the one classified as benign — so the cascade that RFC 9700 §4.14.2 relies on never fires, no audit row is written (`_record_post_revoke_race` only runs on the non-rotated branch `:308-311`), and the other holder's chain survives. A subsequent interactive re-login does not repair this because login does not bump `token_version` (INFERRED from `_make_auth_response`; not exhaustively traced). The X8 committed-successor recovery (`:355-420`, default off) is orthogonal: it proves possession of a successor, which the legitimate device in this case does not have.
- What happens: a compromised driver/rider session can persist (30-day refresh, rotating) while the account owner experiences one "please sign in again" and nothing else. The design comment ("a replay within the window yields NOTHING to the attacker") holds only for the replay-second ordering.
- Root cause: the window was widened for mobile UX (lost-response retries after minutes) without distinguishing "the parent is being replayed by the same device that holds the successor" from "someone else holds the successor".
- Recommendation: keep the window but make the benign branch **conditional on proof**: treat a replay as benign only if the caller also presents the successor it should hold (`proposed_refresh_token` / X8 shape, `:184-190`) or a matching `user_agent`+device id to the successor row; otherwise fall through to the cascade. Additionally, bump `users.token_version` on every *interactive* login (OTP/Firebase exchange) so a victim's re-login always kills the attacker's chain — the cost is that other legitimate devices also re-login, which is the standard "new sign-in signs out old sessions" behaviour and is already what `logout-all` does.   Alternative considered: shorten the window to 60 s — rejected: it re-creates the mid-shift all-device logout incident (CRIMSON-SMOKE-7445) the widening fixed.
- Blast radius: `lookup_refresh_token` (one caller: `routes/auth.py:1951`), `_handle_refresh_token_reuse`, `test_refresh_token_reuse*.py`; `_make_auth_response` for the login bump (rider, driver, Firebase, reactivate, portal OTP paths).
- Rollout: flag `REFRESH_GRACE_REQUIRES_PROOF` default off → on; login bump behind `LOGIN_BUMPS_TOKEN_VERSION`.   Rollback: flags off; no data change (token_version only grows).
- Verification to close: new test — attacker-first sequence ends with attacker's T1 rejected after victim re-login; existing benign-race tests still pass.

## 3. BOLA/IDOR sweep — every `{…id}` path parameter and body-supplied id on non-admin routes, and how ownership is enforced
**Method (VERIFIED, 2026-09-24):** static sweep script over `backend/routes/**` (admin router excluded — every `/api/admin/*` router is mounted behind `get_admin_user`/`require_module`, see `backend/server.py:581` and `routes/admin/__init__.py`). For each route decorator whose path contains an `{…id}` segment, the first ownership-style check within 70 lines of the decorator is recorded. 102 routes swept. **Result: no route trusts a path/body id without scoping it to the caller.** Pattern families found:
1. **Filter-at-query** — `{"id": <id>, "user_id"|"rider_id"|"driver_id": caller}` (favorites, notifications, addresses, emergency-contacts, safety-checkin, scheduled-ride delete, driver arrive/start/verify-otp). A foreign id yields 0 rows → 404. Strongest form: cannot be forgotten on a later write.
2. **Fetch-then-compare** — `ride.get("rider_id") == current_user["id"]` and/or `ride.get("driver_id") == driver["id"]`, admin bypass only via the private `_admin_verified` marker (queries, tracking, chat, receipts, sharing, stops, tips/process-payment, rating, lost-found, disputes, wallet pay, promo apply). Weaker: a future branch that skips the compare is a silent IDOR.
3. **Dependency guard** — `require_company_admin` / `require_company_member` (`backend/dependencies/company_guard.py:27,47`) and `_ensure_member` (corporate_rider) for every corporate `{company_id}` route.
4. **Capability token instead of identity** — `GET /offer-cards/{ride_id}.png` (`routes/offer_card.py:72`, short-TTL HMAC bound to ride+driver) and `GET /rides/track/{share_token}` (`routes/rides/sharing.py:229`, 32-byte random, 24 h expiry). Correct design for OS/browser fetches that cannot carry a JWT.
5. **Env-gated test hooks** — `POST /rides/{ride_id}/simulate-arrival` refuses in production (`routes/rides/lifecycle.py:50-51`) and still checks `rider_id`.

**Body-supplied ids (Pydantic fields named `user_id`/`ride_id`/`driver_id` on non-admin routes, VERIFIED):** `wallet.py:117` `WalletPayRequest.ride_id` → `:240` rider check; `disputes.py:43` → `:64-72` rider-or-assigned-driver check; `payments.py:97/120/127` → `_authoritative_ride_charge(ride_id, rider_id=current_user)` `:64` and `:632`; `promotions.py:49/54` → `:205` query-scoped and `:418` rider check; `support.py:68` `ChatRequest.driver_id` is accepted but **unused** by the handler (legacy field — harmless, but a reviewer might assume it scopes something; recommend deleting). `users.py:771` is a response model, not an input.

**Residual weaknesses (not IDORs today):**
- 3 driver-side handlers (`drivers/ride_flow.py:79` accept, `:653` decline, `drivers/ride_reads.py:274` offer) scope via the offer/`driver_id` on the ride rather than a query filter — correct, but they depend on `claim_driver_atomic`'s `{'status':'searching'}` CAS (R8's domain). 
- `GET /drivers/{driver_id}` (`drivers/status.py:268-300`) has a **third** branch: a rider with an *active* ride assigned to that driver receives a "safe public projection" — this is the one place a rider can read another principal's row; the projection is allow-listed, and PII decrypt (`_decrypt_driver_pii`) only runs on the admin/self branch. Reviewed, acceptable; add to the response-schema regression test.
- Family 2 (fetch-then-compare) is ~55 of the 102 routes. No lint/test enforces it. Recommendation SEC-R10-011 (below) proposes a single `load_ride_for(caller, ride_id, roles=…)` helper + a static test that fails on any `get_ride(ride_id)` call in `routes/` not followed by a membership check — the same static-test mechanism that closed the loguru class (C60/C65/C69).

## 5. Rebuild pass — §7.3 Rebuild Delta cards

### Epic: Authentication & Authorization — asymmetric JWT + `kid`
- Verdict per inherited pattern: **MODIFY** (HS256 single shared secret → ES256/EdDSA with `kid` + in-process JWKS). Evidence: `dependencies/__init__.py:50` `JWT_ALGORITHM = "HS256"`; the same secret is verify key, mint key for three token classes (mobile, admin, reactivation), the rate-limiter's decode key (`utils/rate_limiter.py`), and the OTP pepper fallback (`utils/crypto.py:29`).
- Keep (already best-in-class): audience separation (`spinr:rider`/`spinr:admin`), `token_version` DB revocation, 15-min/1-h TTLs, refresh rotation with reuse detection, `algorithms=[...]` pinned on every decode.
- Uber/Lyft do: asymmetric tokens verified at the edge/gateway with rotating key sets; services never hold the mint key (industry pattern; no primary source fetched — INFERRED). Spinr today: every replica on both providers holds the mint key; rotation = global logout (`secret-rotation.md:42`).
- Clean-sheet Spinr would: mint with a private key that exists only on the token-issuing path (`routes/auth.py`, `routes/admin/auth.py`), verify everywhere with the public key, publish `/.well-known/jwks.json` for future partners/edge; `kid` in every header; two keys live during rotation. Why (the edge it creates): a leaked replica env, heap dump or backup no longer mints super-admin tokens; rotation becomes routine instead of an incident.
- How: PyJWT already supports ES256 (used for APNs, `utils/apns_client.py:107`); keys in Fly/Railway secrets as PEM; `JWT_KEYS` map `{kid: (alg, public_pem, private_pem?)}`; verify loop tries the `kid` named in the header, falls back to HS256 while `JWT_HS256_ACCEPT=true`.   Who: backend owner + whoever runs secret rotation.   When: **Next** (after SEC-R10-001 rotation, before any partner/edge verifier exists).
- Incremental path: 1) add key loading + dual-verify (accept HS256 and ES256), ship dark → 2) flip mint to ES256 behind `JWT_ASYMMETRIC_MINT` for admin audience first (2 users) → 3) mobile audience after one access-token lifetime + one refresh cycle → 4) set `JWT_HS256_ACCEPT=false` → 5) rotate `JWT_SECRET` to a value used only as `OTP_PEPPER` fallback until SEC-R10-005 lands, then delete.
- Cost/effort: **M** (≈ 8 decode sites listed in SEC-A2-001 blast radius, WS + MCP + rate limiter + middleware; tests) · Risk: medium (a broken dual-verify logs everyone out — hence dark launch) · Reversibility: high while HS256 accept is on · Build (PyJWT) — no buy.
- Advantage type: **trust/operational** — not customer-visible, defensible only as reduced breach blast radius.
- "Why not?": ADR-005 chose HS256 for simplicity when there was one process; nothing forced the change because no verifier outside the backend exists yet. Something simpler that gets most of the result: keep HS256 but stop using it as the pepper and rotate on a schedule with a 15-min dual-secret window — gets rotation, not the mint-anywhere reduction.

### Epic: Platform Foundation & Schema — envelope encryption vs Vault-only for PII at rest
- Verdict per inherited pattern: **MODIFY** (Vault-only via pgsodium SECURITY DEFINER RPCs → application-layer envelope encryption with a KMS-wrapped data key, Vault retained for secrets-that-are-secrets). Evidence: `list_extensions` VERIFIED-LIVE `pgsodium 3.1.8` + `supabase_vault 0.3.1`; encrypted columns are only `drivers.license_number`, `drivers.sin`, `emergency_contacts.*` (migrations 32/289/357); VIN was un-encrypted by operational request (244); the rotation runbook calls `pgsodium.*` directly and has never been run.
- Keep: fail-closed encrypt / fail-open-to-token decrypt contract (`utils/vault_pii.py:24-93`) — right shape; SIN write-only with no app read path (289) — right minimisation; REVOKE EXECUTE from anon/authenticated on the RPCs (32:87-89).
- Uber/Lyft do: field-level encryption in the service layer with keys in a KMS/HSM, region-pinned, with per-field key ids and audited decrypt calls (INFERRED — industry pattern, no source fetched). Spinr today: crypto boundary is a Postgres extension the vendor says not to build on (Supabase pgsodium page, search snippet — INFERRED); key = one named pgsodium key; decrypt is any service-role caller of the RPC; no per-read audit row.
- Clean-sheet Spinr would: `utils/envelope.py` — AES-256-GCM per value with a random DEK, DEK wrapped by a KEK in a Canadian-region KMS (AWS KMS ca-central-1 or GCP KMS northamerica-northeast1); ciphertext stored as `enc:v1:<kid>:<b64>`; decrypt calls logged to `audit_logs` with actor + field + reason. Why: PIPEDA data-residency stays provable, key rotation is a KEK re-wrap (no data rewrite), vendor extension churn cannot make 7-year records undecryptable, and decrypt becomes an *audited* application action rather than a DB privilege.
- How: dual-read (`enc:` prefix → envelope; UUID → Vault) with a backfill job; Vault stays for `settings`-class secrets (Stripe/Twilio/Maps/LLM keys), where SEC-R10-002 shows the bigger exposure actually is.   Who: backend owner + compliance (residency sign-off).   When: **Later** for SIN/licence (three columns, low churn) — but **Now** for the *runbook*: execute it once on a branch (SEC-R10-010).
- Incremental path: 1) run the existing rotation runbook on a Supabase branch and record it → 2) move the four `settings` secret columns to Vault (they are plaintext today per C43 "NOT verified" note — UNKNOWN, first thing to check) → 3) envelope module + dual-read for `license_number` → 4) SIN, emergency contacts → 5) drop direct `pgsodium.*` references.
- Cost/effort: **M** (module + 3 columns + backfill) · Risk: low-medium (dual-read; no destructive step until proven) · Reversibility: high · Build + Buy (KMS).
- Advantage type: **trust** (regulator-defensible) — not a product edge.
- "Why not?": the Vault path was the fastest thing that satisfied "encrypted at rest" in April; the deprecation signal is newer than the design. Simpler alternative: stay Vault-only and just rewrite the runbook against `vault.*` primitives — acceptable if Supabase's "Vault is unaffected" holds, which is exactly what has not been verified.
