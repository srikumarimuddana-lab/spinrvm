## §1 Current state — what the money-domain audit already established (cited, not re-derived)

This section summarises `money-cra.md`, `strategy.md`, `corporate.md`, `admin-ops.md`, `04-blueprint.md` H2, `08-hostile-review.md` and `ROADMAP.md` for readers who have not read them, and adds only what this session independently re-checked in code. Nothing here is a new finding unless marked **New this session**.

### 1.1 The fare/ledger/payment core (VERIFIED, `money-cra.md` §1, §3)

- `calculate_fare` is a pure Decimal function; `platform_share` does not exist as a variable anywhere — 0% commission is structural, not a policy switch (`fare_service.py:184-237`, `money-cra.md` §1.1).
- Surge is clamped at every fare-persisting call site (9 sites catalogued, `money-cra.md` §3.1); corporate and scheduled rides are exempt (§3.2).
- Stripe idempotency is three layers deep (SDK keys embed amount, `claim/unclaim_stripe_event`, DB CAS) and the cumulative-refund RPC is atomic (§3.10, N4).
- Pre-auth holds are sized to exactly the quote (`RIDE_AUTH_BUFFER_CAD = 0.00`); tip/overage is collected by incremental authorization or a second PaymentIntent, never silently dropped (§3.9).
- The ledger (`financial_events`) is single-entry, append-only, and never fails a payment by design (`record_event` never raises) — this is the steelman's #5 and, per H2 below, also the reason it cannot be the money-truth boundary yet.
- Trust-first absorption policy is explicit and documented: uncollected fares, lost disputes and absorbed tips are platform-funded so the driver is always kept whole (`docs/change-log/2026-09-21-uncollected-rides-stay-payable.md`, §1.6 steelman) — the right call for a 0%-commission brand, but **unmeasured** (MONEY-010).

### 1.3 The write-site inventory the money guard must start from (VERIFIED, `08-hostile-review.md` U-1, `04-blueprint.md` H2, re-confirmed this session)

`04-blueprint.md` H2's own first draft claimed "every writer passes through `repositories/_base.py`, so the guard sees all." `08-hostile-review.md` refuted this (U-1: **Refuted, VERIFIED**) and the blueprint's changelog corrected it: about 71 direct `.table()` writes bypass `_base.py`, and about 90 `supabase.rpc(` calls carry arguments the guard never sees. This session independently re-read the two named files:

- `backend/repositories/ride_repo.py:264-274` (`update_ride`) — a direct `supabase.table("rides").update(updates).eq("id", ride_id).execute()`, confirmed by reading the function this session (the line numbers in the blueprint/hostile-review, 260/276, land inside `insert_ride`/`update_ride`; both write `rides` directly, bypassing any column-level guard `_base.py` might hold).
- `backend/services/stripe_payout_sync_service.py:453-465` — a direct `supabase.table("payouts").insert(chunk)` / row-by-row fallback insert, confirmed this session; `payouts.amount` is exactly the column MONEY-006's class already broke once (B28/331).

Any money-column write guard (H2's "Now" step) that is scoped only to `repositories/_base.py` gives false assurance on precisely the two tables — `rides` and `payouts` — that carry the fare and the payout amount. This is why the build order below (§3) puts the write-site inventory *before* the guard, matching `04-blueprint.md`'s own corrected "First reversible step."
