# Run: Audit and remediate corporate KYB document Storage bucket RLS/access scoping

Security-focused pass on the corporate KYB (Know Your Business) document Storage bucket, the item ACTION_ITEMS.md's B12 explicitly left open ("flagged not confirmed by the audit; needs its own security-focused pass, not attempted here").

## Stage 1-2: Ideation & Requirements

**What I did.** Read `agents/GUARDRAILS.md`, `agents/roles/leadership.md`, `agents/roles/product-design-engineering.md`, `agents/PIPELINE_DESIGN.md`, and the root `CLAUDE.md` first, as instructed. Then traced the real KYB document flow end to end, code-only (no live Supabase access attempted — see "what I could not verify" below):

- `backend/routes/corporate_company_kyb.py` — company-portal endpoints (`GET /kyb`, `POST /kyb/upload-url`, `POST /kyb/submit`), all gated by `require_company_admin` (`backend/dependencies/company_guard.py`), which resolves the caller's active memberships and 403s unless `company_id` in the path matches a membership with role `owner`/`admin`. `GET /kyb` deliberately never returns the storage key — the docstring says the document "is only reachable via the staff-side streaming endpoint."
- `backend/routes/corporate_accounts.py` — staff/admin endpoints (`POST /{id}/kyb-upload-url`, `POST /{id}/kyb-document`, `GET /{id}/kyb/view`), all gated by `get_current_admin`. `kyb/view` streams the object server-side using the service-role Supabase client and returns raw bytes — the browser never receives a Supabase Storage URL for KYB documents (unlike `driver-documents`, which does hand out 1-hour signed URLs).
- `backend/repositories/corporate_repo.py` — `create_kyb_upload_url` (signs a single-object, write-only upload URL scoped to `kyb/{company_id}/{uuid4}.{ext}`), `kyb_object_exists` (lists the company's own storage prefix to confirm an upload landed before persisting it), `set_kyb_document` (persists the raw storage key, never a URL, onto `corporate_accounts.kyb_document_url`).
- `backend/supabase_client.py` — confirmed the backend's `supabase` client is constructed with `SUPABASE_SERVICE_ROLE_KEY`, not the anon key, for every one of the calls above. This matters: it means the backend's own storage access always bypasses Postgres RLS on `storage.objects`, so the real access-control boundary for KYB documents today is the FastAPI route guards (`require_company_admin` / `get_current_admin` + the tenancy-prefix/path-traversal checks in `kyb/submit` and `kyb-document`), not Storage-layer RLS.
- `admin-dashboard/src/lib/companyApi.ts` + `.../company-portal/[id]/verification/page.tsx` — confirmed the browser only ever does a raw `PUT` to the short-lived signed **upload** URL (write-only, single object). No `supabase-js`/`createClient` usage exists anywhere in `admin-dashboard` — the frontend never talks to Supabase Storage directly for reads, only through the backend's authenticated proxy endpoints.
- `backend/docs/STORAGE_BUCKETS.md` and `backend/migrations/` — found that `kyb-documents` (like `driver-documents`) is **not provisioned by any migration**. The docs file says to create it "once via the Supabase dashboard... then the app writes to it at runtime." Compare with `vehicle-illustrations`/`audio-assets` (migration 202), `ride-snapshots` (migration 236), `lost-and-found` (339), and `safety-evidence` (340) — all of which declare their bucket's `public` flag, size limit, and allowed MIME types as an idempotent `INSERT ... ON CONFLICT DO UPDATE` in a migration, with an explicit comment that no RLS policy is granted to `authenticated`/`anon`. `kyb-documents` has no such artifact anywhere in source control.
- Checked existing test coverage (`backend/tests/test_corporate_company_kyb.py`, `test_corporate_kyb_upload.py`, `test_corporate_admin_routes.py`): the tenancy/path-traversal guard (`path` must start with `kyb/{company_id}/`, no `..`) is already tested on both the portal submit endpoint and the staff `kyb-document` endpoint, for both the allowed and the rejected-path cases. What is **not** tested anywhere: a cross-tenant case where an authenticated admin of company A calls company B's `kyb/upload-url` or `kyb/submit` and gets denied by `require_company_admin` itself (as opposed to the path-string guard).
- Noted (but treated as out of scope) `routes/corporate_accounts.py`'s own documented "OWNERSHIP ASSUMPTION" comment (lines 85-90): all Spinr admins are currently global staff, so `get_current_admin`-gated endpoints — including `kyb/view` — do not further scope by which admin "owns" which company. This is a pre-existing, already-acknowledged, file-wide design decision unrelated to KYB storage specifically; I did not treat it as a finding of this pass.

**What I decided.** The application-layer access control for KYB documents is already sound: company-portal access is correctly scoped per company via `require_company_admin`, the company portal never receives the storage key at all, staff access is server-proxied through the service-role client with no public/anon path ever existing, and the tenancy/traversal guards on both submission paths are already covered by tests. There is no confirmed broken-access-control bug here — the earlier "not confirmed by the audit" wording turns out to be literally accurate: nobody had checked, and having now checked, the application layer holds up.

The real, fixable gap is narrower than "access control is broken": it's a **verifiability/drift gap**. Because `kyb-documents`' bucket-level configuration (`public` flag, size limit, allowed MIME types, and the "no RLS for authenticated/anon" posture) is only ever set by hand in the Supabase dashboard and is not expressed anywhere in this repo, nobody can confirm from source control that the live bucket actually matches the private, service-role-only posture the code assumes — and there is no automated guard against someone flipping it to public later. That gap, plus the missing cross-tenant regression test, are what this run recommends fixing. See `decisions.md` for the full reasoning on why this was framed as "fix the verifiability gap" rather than "no fix needed" or "assume something is broken and patch it."

Everything above is inferred from source code and `backend/docs/STORAGE_BUCKETS.md`'s documentation of intent, not from a live read of the Supabase project. - I did not review `driver-documents`' bucket posture even though it has the identical "not migration-provisioned" gap — it is a different, lower-sensitivity-tier bucket (per the repo's own framing: KYC/photo documents, not incorporation/identity documents) and was not named in this task's scope.

**Candidate approaches considered:**

- **A — No-op, close B12 as verified-sound.** Just record the application-layer finding in ACTION_ITEMS.md, no code change. Fastest, zero regression risk — but leaves the storage-layer half of the original "not confirmed" question exactly as unconfirmed as before, and gives the next audit nothing new to check against.
- **B — Migration only.** Add the idempotent `kyb-documents` bucket-provisioning migration (mirrors migration 340) with no test changes. Closes the source-control/drift gap cheaply and safely (additive `ON CONFLICT DO UPDATE` upsert, no destructive change). But doesn't add coverage for the boundary that's actually doing the protecting today (the route guards), so a future regression there wouldn't be caught.
- **C — Regression tests only.** Add the missing cross-tenant denial tests, skip the migration. Directly exercises the real enforcement layer at low cost and no deploy coordination — but leaves the bucket's live `public`/RLS posture just as unverifiable from the repo as B12 originally found it.
- **D — Both B and C (recommended).** Slightly more surface area (one new migration file, one new/extended test file) than either alone, but each piece is small, additive, and independently low-risk, and together they close both halves of the original "not confirmed" finding — the storage-layer posture becomes version-controlled and drift-resistant, and the application-layer boundary gets explicit allowed/denied regression coverage.

**Chosen: Option D**, because the investigation found no actual broken access control to fix — manufacturing an application-layer "fix" for code that already scopes correctly would violate CLAUDE.md's "don't manufacture a fix for a problem that doesn't exist." What genuinely was missing were (1) a source-of-truth for the bucket's intended posture, and (2) coverage of one denial path (cross-tenant) that the existing test suite doesn't exercise. D closes exactly those two gaps and nothing more, at minimal, additive risk.
