[17-1] MEDIUM | Admin Playwright E2E only runs on main, not PRs
File: .github/workflows/ci.yml:261-303
Finding: `if: github.ref == 'refs/heads/main'` gates Playwright E2E to
post-merge runs. Lint, Vitest, and `next build` run on every PR, but the
E2E suite — the only layer that exercises real navigation flows — does not
block a bad merge. Regressions land first, are caught second.
Fix: Move E2E to PR checks as a non-blocking job at first; promote to
required-status after stabilization. Effort: 2-3 h
Risk score: 12 (MEDIUM × org × likely)
Regulations: SOC2 (Change Management)
Owner: ci · Sprint: P2

[17-2] HIGH | deploy-admin needs only backend-test, not backend-deploy
File: .github/workflows/ci.yml:362
Finding: `deploy-admin` has `needs: [backend-test]` but not `[backend-deploy]`.
A backend that passes tests but fails deploy still releases the admin to
Vercel — admin frontend can hit a stale or unavailable backend version.
Fix: Re-chain to `needs: [backend-deploy]` (or whichever job represents
backend-on-prod). Effort: 1-2 h
Risk score: 18 (HIGH × org × possible)
Regulations: SOC2 (Change Management)
Owner: ci · Sprint: P1

[17-3] MEDIUM | npm ci runs without explicit audit gate; security-gates audit non-blocking
File: .github/workflows/ci.yml:242, security-gates.yml:73
Finding: CI uses `npm ci` (deterministic). However, `npm audit` in
security-gates runs with `continue-on-error: true`. A high-severity CVE
landing in dependencies will be a green build.
Fix: Set `continue-on-error: false` for `npm audit --audit-level=high` after
a baseline-clean window. Add `audit=true` to `.npmrc`. Effort: 0.5 h
Risk score: 12 (MEDIUM × org × likely)
Regulations: Supply Chain, SOC2
Owner: ci · Sprint: P2

[17-4] MEDIUM | No required-status-check / branch protection on Vercel deploy
File: .github/workflows/ci.yml:383-388
Finding: Vercel deploy fires once the build job exits zero — no gate on
security-gates results, no documented rollback runbook. A late-arriving CVE
or a Sentry release-tracking failure does not stop the rollout.
Fix: Add GH branch protection requiring security-gates checks; document a
1-page rollback runbook (`docs/runbooks/admin-rollback.md`). Effort: 1-2 h
Risk score: 12 (MEDIUM × org × possible)
Regulations: Change Management, SOC2
Owner: ci/ops · Sprint: P2

[17-5] LOW | Build output not scanned for secrets pre-deploy

Risk score: 6 (LOW × org × possible)

[17-6] PASS | Lint + Vitest + next build run on every PR

Finding: The three fastest checks (ESLint with `--max-warnings 600`, Vitest,
`next build`) execute on every PR. This is the correct pattern — fast checks
gate, slow checks (E2E) follow.

TASK 18 — SECRETS MANAGEMENT (admin-specific)
================================================================================

[18-1] HIGH | Cookie SameSite=Lax — should be Strict for admin-only UI
File: admin-dashboard/src/store/authStore.ts:25
Finding: Token cookie sets `SameSite=Lax`, which permits cross-site GETs
(e.g. an attacker-controlled site framing the admin). Strict eliminates the
cross-site request entirely. Pairs with admin-v1 [02-2] (sessionStorage
removal) — that fix moves the token to a cookie; this fix tightens it.
Fix: Set `SameSite=Strict`. The admin has no cross-site nav use case. The
audit-v1 P0-1 fix should land with `Strict` from the start. Effort: 0.5 h
Related to: admin-v1 [02-2]
Risk score: 18 (HIGH × org × possible)
Regulations: OWASP A01
Owner: admin-dashboard · Sprint: P1

[18-2] MEDIUM | Client-side cookie can't enforce HttpOnly; backend must set it
File: admin-dashboard/src/store/authStore.ts:18-28
Finding: Client checks `window.location.protocol === 'https:'` and
conditionally adds `Secure`. JavaScript can never set `HttpOnly` — only the
backend `Set-Cookie` response header can. Today the cookie is JS-readable.
Fix: Backend `/admin/auth/login` and `/admin/auth/refresh` must emit
`Set-Cookie: admin_access=...; HttpOnly; Secure; SameSite=Strict; Path=/admin`
unconditionally in production. Frontend stops setting cookies entirely.
Pair with admin-v1 [02-2] (the P0 work). Effort: 1 h verification +
backend wiring covered by admin-v1 [02-2]
Related to: admin-v1 [02-2]
Risk score: 12 (MEDIUM × org × possible)
Regulations: OWASP A02
Owner: backend · Sprint: P0 (covered by admin-v1 [02-2])

[18-3] MEDIUM | Refresh token persisted to sessionStorage is XSS-stealable
File: admin-dashboard/src/store/authStore.ts:65, 194
Finding: `partialize` correctly excludes the access token from storage but
*includes* `refresh_token`. An XSS payload that steals the refresh token can
mint new access tokens for the refresh-TTL window (currently 30d).
Fix: Move refresh token to a separate HttpOnly cookie (`admin_refresh`) with
`Path=/admin/auth/refresh` and the same Secure + SameSite=Strict flags. The
refresh endpoint is the only consumer; no JS needs the value. Effort: 4-6 h
Related to: admin-v1 [02-2]
Risk score: 12 (MEDIUM × org × possible)
Regulations: OWASP A01
Owner: admin-dashboard + backend · Sprint: P1

[18-4] LOW | NEXT_PUBLIC_API_URL has localhost fallback in production code path
File: admin-dashboard/next.config.ts:3-6, admin-dashboard/src/lib/api.ts:5
Finding: `process.env.NEXT_PUBLIC_API_URL ?? "http://127.0.0.1:8000"` —
if the prod env var is misconfigured, the admin silently calls localhost.
The dev fallback should not be a runtime safety net.
Fix: At build time in production, throw if `NEXT_PUBLIC_API_URL` unset:
`if (process.env.NODE_ENV === 'production' && !process.env.NEXT_PUBLIC_API_URL)
  throw new Error('NEXT_PUBLIC_API_URL must be set in production');`
Effort: 1 h
Risk score: 4 (LOW × self × possible)
Regulations: Configuration Management
Owner: admin-dashboard · Sprint: P3

[18-5] PASS | Access token stored in memory only
File: admin-dashboard/src/store/authStore.ts:63-64, 199
Finding: Zustand `partialize` excludes `token` from persisted state. On
reload, silent refresh exchanges `refresh_token` → fresh access token before
the first API call. XSS cannot read the access token from storage.

[18-6] LOW | No .env.example in admin-dashboard
File: admin-dashboard/ (no .env.example)
Finding: The admin-dashboard relies entirely on Vercel's env var UI; there
is no `.env.example` listing required variables. New contributors discover
required variables only when something breaks at runtime.
Fix: Add `admin-dashboard/.env.example` listing every `NEXT_PUBLIC_*` and
`SENTRY_*` variable with a one-line purpose comment. Effort: 0.5 h
Risk score: 3 (LOW × self × possible)
Regulations: Documentation
Owner: admin-dashboard · Sprint: P3

TASK 21 — OBSERVABILITY (admin-specific)
================================================================================

[21-1] MEDIUM | Sentry session replays may capture admin PII despite maskAllText
File: admin-dashboard/sentry.client.config.ts:16-29
Finding: `replaysSessionSampleRate: 0.1` + `replaysOnErrorSampleRate: 1.0`
with `maskAllText: true, blockAllMedia: false`. Admin views render rider
phone numbers, driver licences, payout amounts, and Stripe IDs. `maskAllText`
masks DOM text but does not mask media or canvas; `blockAllMedia: false`
means uploaded ID images on document-review pages can be captured.
Fix: Set `blockAllMedia: true` for admin (document images > replay value);
add `mask: ['[data-pii]', 'input']` selector list and tag PII-bearing
elements with `data-pii`. Document the masking contract in
`docs/runbooks/sentry-pii.md`. Effort: 2-3 h
Risk score: 12 (MEDIUM × org × possible)
Regulations: PIPEDA, OWASP A09
Owner: admin-dashboard · Sprint: P2

[21-2] MEDIUM | tracesSampleRate=0.2 in prod misses 80% of perf incidents
File: admin-dashboard/sentry.client.config.ts:13, sentry.server.config.ts:9
Finding: 20% trace sampling on a low-traffic admin surface (estimated <5k
admin requests/day) means most performance regressions never reach Sentry.
The admin is the surface where staff diagnose payouts and dispatch issues —
slow loads here are operationally expensive and rare enough that 100%
sampling is tractable.
Fix: Raise to `tracesSampleRate: 1.0` for admin in production; the comment
already acknowledges "raise to 1.0 in staging" — same rationale applies to
admin in prod. Effort: 0.25 h
Risk score: 8 (MEDIUM × org × likely)
Regulations: SOC2 (Monitoring)
Owner: admin-dashboard · Sprint: P2

[21-3] HIGH | No Sentry beforeSend filter — full URL + query strings leak
File: admin-dashboard/sentry.client.config.ts:8-31 (no beforeSend)
Finding: Default Sentry transport sends the full request URL including
query strings. Admin URLs include `?driver_id=`, `?ride_id=`, `?phone=` and
search filters with PII. CLAUDE.md PIPEDA section forbids exact addresses,
phone numbers, names, and emails in Sentry payloads.
Fix: Add `beforeSend` hook that scrubs query params matching
`(driver_id|rider_id|ride_id|phone|email|address|name)` and replaces with
`[redacted]`. Apply same hook in `sentry.server.config.ts`. Effort: 2 h
Risk score: 18 (HIGH × org × likely)
Regulations: PIPEDA, OWASP A09
Owner: admin-dashboard · Sprint: P1

[21-4] MEDIUM | Sentry tags missing required `domain` and `surface`
File: admin-dashboard/sentry.client.config.ts (no setTag in init)
Finding: CLAUDE.md observability section requires every captured event to
carry `domain` (one of: dispatch/payments/auth/...) and
`surface=admin`. Admin Sentry init sets neither, so cross-surface
dashboards group admin errors with rider/driver errors.
Fix: Add `Sentry.setTag('surface', 'admin')` after init; wrap each route
group with a domain tag (e.g., `/dashboard/payments/*` → `domain=payments`).
Effort: 1-2 h
Risk score: 8 (MEDIUM × self × possible)
Regulations: SOC2 (Monitoring)
Owner: admin-dashboard · Sprint: P2

[21-5] MEDIUM | No structured logging — only console.* and Sentry capture
File: admin-dashboard/src/**/*.ts (grep: `console.(log|error|warn)`)
Finding: Admin uses bare `console.error` for client-side error paths. There
is no structured logger (pino, bunyan) emitting JSON to a sink. Vercel
captures stdout/stderr, but the lines are unstructured strings — hard to
query, no correlation ID across requests.
Fix: Adopt `pino` (or Vercel's built-in logger primitives) for SSR/route-
handler code paths. Add request-correlation header propagation. Effort: 4-6 h
Risk score: 8 (MEDIUM × self × possible)
Regulations: SOC2 (Monitoring)
Owner: admin-dashboard · Sprint: P2

[21-6] LOW | No release tag in Sentry init — release-tracking degraded

Risk score: 4 (LOW × self × possible)
Regulations: SOC2 (Change Management)
Owner: admin-dashboard · Sprint: P3

[23-1] HIGH | No Content Security Policy header on admin pages
File: admin-dashboard/next.config.ts:8-22 (no `headers()` block)
Finding: `nextConfig` defines `rewrites()` but no `headers()`. Admin
responses ship with zero `Content-Security-Policy`. Any reflected XSS or
compromised dependency runs with full DOM access. Pairs with [19-1]
(dompurify CVE) — CSP is the second line of defence when sanitization
fails.
Fix: Add `headers()` returning a strict CSP: `default-src 'self';
script-src 'self' https://va.vercel-scripts.com;
connect-src 'self' ${BACKEND_URL} https://*.sentry.io;
img-src 'self' data: https:; style-src 'self' 'unsafe-inline';
frame-ancestors 'none'; base-uri 'self'; form-action 'self'`. Roll out via
`Content-Security-Policy-Report-Only` first; capture violations; then enforce.
Effort: 4-6 h
Duplicate of: admin-v1 [07-2] (broader security-headers gap)
Risk score: 18 (HIGH × org × likely)
Regulations: OWASP A05, A03
Owner: admin-dashboard · Sprint: P1

[23-2] HIGH | No X-Frame-Options / frame-ancestors — clickjacking exposure
File: admin-dashboard/next.config.ts:8-22 (no security headers)
Finding: An attacker page can iframe `/dashboard/*` and trick a logged-in
admin into clicking destructive actions (refund, ban driver, suspend
account). No `X-Frame-Options: DENY` and no CSP `frame-ancestors 'none'`.
Fix: Set `X-Frame-Options: DENY` on every admin response; CSP
`frame-ancestors 'none'` provides modern equivalent. Effort: 0.25 h (lands
with [23-1])
Duplicate of: admin-v1 [07-2]
