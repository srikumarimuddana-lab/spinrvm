## §1 Steelman

1. **The lifecycle model in `domain-corporate.md` is not aspirational — it's what the code does today.** Company suspend/close cancels pre-pickup rides via an atomic conditional claim (`{"status": {"$in": _PRE_PICKUP_STATUSES}}` filter, 0-rows-matched = ride already progressed = skip) in both `corporate_suspension_service.py` and `corporate_member_offboarding_service.py`; in-progress rides are deliberately grandfathered per the ride state machine's "never cancel after trip start" invariant. VERIFIED.
2. **The "two independent booking paths" trap (domain-corporate.md's headline lesson) has visibly been internalized as a review discipline, not just documented.** `routes/rides/booking.py`'s `company_allowance` block (~line 1007) and `work_profile` block (~line 1197) both call the same `require_company_bookable(company_id, settings=...)` helper, both use `grand_total` (not the fee/tax-excluding `total_fare`) for the pre-auth headroom check, and the `work_profile` block's inline comments explicitly cite "the company_allowance path above" and "gap #39" reconciliation work (`#4602`) — i.e. someone deliberately re-synced the two blocks after finding a drift, rather than fixing one and shipping. VERIFIED, `routes/rides/booking.py:1007-1113,1193-1287`.
3. **A genuine allowance-cap-race regression was self-caught and fixed with an unusually complete paper trail** (see Finding CORP-002 below) — the fix, the regression, the re-fix, and a real-Postgres regression test all exist and are individually dated. This is the audit process working as intended, not a gap.
4. **The two corporate background loops that domain-corporate.md flagged as inconsistently guarded (`corporate_autotopup_loop` had a company-status check, `corporate_low_balance_loop` didn't) are now both guarded** — `corporate_low_balance.py:106` checks `company.get("status") == "active"` before notifying, matching `corporate_autotopup.py:120`. VERIFIED.
5. **Tenant scoping on every rider-/company-admin-facing corporate route is derived server-side from the caller's own membership, not trusted from the URL.** `require_company_admin`/`require_company_member` (`backend/dependencies/company_guard.py`) take `company_id` from the path but only succeed if `list_active_memberships_for_user(current_user["id"])` contains a row for that exact company (and, for the admin guard, an owner/admin role); rider-only endpoints (`corporate_rider.py`) additionally derive `member_id` from `_ensure_member`, so a rider can never read another rider's statement via a crafted `company_id`. See §5.
6. **Money math on the allowance/master-wallet RPCs is Decimal-typed at the DB layer (`NUMERIC(12,2)`)**, and every settlement-path caller of `corporate_wallet_apply_delta`/`corporate_allowance_apply_delta` passes a `Decimal`-derived amount — no float leakage found in the corporate wallet write path itself (float issues found elsewhere in the fare pipeline are R9's territory, already filed as MONEY-006).

## §2 Findings

### CORP-001 — Corporate wind-down ledger debit is not idempotent, and the status-flip guard that would normally prevent a retry has a TOCTOU race
- Hierarchy: L2 Corporate / B2B Billing › L3 Membership lifecycle (wind-down) › L4 S-corp-05 › L5 "company closed, wallet balance refunded"
- Severity: HIGH   Priority score: S×B×L = severity HIGH × blast radius (1 shared money function, terminal/irreversible state) × likelihood LOW-MEDIUM (needs a genuine double-click/timeout-retry within one request's async window)
- Status: VERIFIED (root cause + code path traced); Existing item: money-cra.md §3.13 already flags `corporate_wallet_winddown_service.py:164`'s `apply_adjustment` call as having "no `ride_id`, no client key" — **not yet in `ACTION_ITEMS.md`** (grepped: no hit for `winddown`/`corp-close` as an item id)
- Adversary: malicious insider with admin access (double-submit "Close Account" to force a ledger/Stripe divergence and obscure a self-dealing refund); auditor/finance team (books show a wallet debit larger than Stripe's actual refund total on a company that can never be reopened to reconcile against)
- Evidence: `backend/routes/corporate_accounts.py:850-858` — the only guard against re-running the close flow is `if current.get("status") == CompanyStatus.CLOSED.value: raise 409`, checked against a row fetched via a plain `get_corporate_account_by_id` read (no lock). `backend/repositories/corporate_repo.py:216-221`'s `update_corporate_account_status` is an **unconditional** `UPDATE ... WHERE id = company_id` — no `WHERE status != 'closed'` compare-and-swap, unlike the ride-acceptance race guard CLAUDE.md documents elsewhere in this codebase (`{'status': 'searching'}` filter) or the pre-pickup-ride cancellation claims in this same corporate module (`corporate_suspension_service.py`, `corporate_member_offboarding_service.py`, both of which DO use a conditional `update_one` filter). Two concurrent `PATCH .../status {closed}` requests that both read the pre-update row therefore both pass the 409 check, both flip status to `closed`, and both call `refund_wallet_balance_on_close` (`corporate_accounts.py:906-925`). Inside that function, the Stripe side IS idempotency-keyed per topup (`corp-close-refund-{wallet_id}-{topup_id}`, `corporate_wallet_winddown_service.py:135`), so Stripe itself never moves money twice for the same topup — but the local ledger debit, `apply_adjustment(wallet_id=..., amount=-refunded_total, ...)` at `corporate_wallet_winddown_service.py:164`, passes no `ride_id` and no `client_idempotency_key`, so `corporate_wallet_apply_delta` cannot dedupe it (money-cra.md §3.13's table confirms this is the one non-idempotent row among all listed callers).
- What happens: a second concurrent close reruns the whole refund loop, recomputes `refunded_total` from the topups list, and re-debits the wallet by that amount via a second, undeduped `apply_adjustment` call — even though Stripe's own ledger only moved money once (the second `stripe.Refund.create` call for each topup returns the same, already-completed refund object via Stripe's idempotency key). The `corporate_wallets.balance` row (and the `financial_events`/`corporate_wallet_transactions` ledger) ends up debited for more than Stripe actually refunded, on an account that is terminal and can never be reopened to correct it in-app.
- Root cause: the close endpoint's replay-safety was designed at the *status* layer (409 on re-close) rather than the *money* layer (idempotency key on the wind-down debit), and the status check itself is not atomic against a concurrent request in the same narrow window before the first request's `UPDATE` commits.
- Recommendation: (1) give `refund_wallet_balance_on_close`'s `apply_adjustment` call a stable `client_idempotency_key=f"corp-close-{wallet_id}"` (the RPC already supports this parameter per migration 376 — this is a one-line caller change, not a schema change); (2) separately, make `update_corporate_account_status`'s close transition conditional (`.eq("status", <current>)`/equivalent optimistic check) so a genuinely concurrent second request 409s instead of re-entering the wind-down path at all — belt-and-suspenders, since (1) alone already makes a double wind-down safe. Alternative considered: rely on the Stripe-side idempotency key alone — rejected, because it protects Stripe's ledger but not the local `corporate_wallets.balance`/ledger row, which is exactly what an auditor or the company's own accountant would reconcile against.
- Blast radius: `apply_adjustment` (`corporate_wallet_service.py`) is also called by the admin ad-hoc wallet-adjustment route (`corporate_wallet.py:285-291`, which already passes its own `client_idempotency_key`) — adding a key to the winddown caller doesn't change that route. No other caller of `refund_wallet_balance_on_close` exists (grepped: only `corporate_accounts.py:911`).
- Rollout: additive (pass a new kwarg at an existing call site; no migration, no flag needed — `client_idempotency_key` is already an optional RPC parameter). Rollback: revert the one-line change; no data migration.
- Verification to close: unit test constructing two sequential (or concurrent, via the existing `test_money_rpc_races.py` real-Postgres harness pattern) calls to `refund_wallet_balance_on_close` for the same company/topup set and asserting the wallet balance only moves once.

### CORP-002 — Allowance per-member cap race: fixed (mig. 258), silently regressed (mig. 277), caught and re-fixed (mig. 297/319) — currently SAFE, but the failure mode can recur
- Hierarchy: L2 Corporate / B2B Billing › L3 Allowance cap & ledger › L4 S-corp-03 › L5 "two concurrent corporate rides for the same member both fit under a per-employee allowance cap"
- Severity: RECOMMENDATION (current state is safe) — was CRITICAL for the window it was live
- Status: VERIFIED. Existing item: `docs/change-log/2026-07-26-corporate-allowance-cap-race-fix.md`; regression + re-fix fully self-documented in migration 297's own header ("REGRESSION FOUND AND FIXED") and `backend/tests/test_corporate_allowance_cap_race.py`'s 2026-08-11 update note — not filed in `ACTION_ITEMS.md` as its own id (it's fully closed, not open backlog)
- Adversary: fraudulent corporate rider (two devices/sessions settling two rides for the same member near-simultaneously to push `used` past the per-employee `amount` cap, over-spending the employer's intended limit)
- Evidence: `backend/migrations/258_corporate_allowance_cap_in_rpc.sql` introduces `v_cap` (read alongside `used` under the `FOR UPDATE` lock) and `RAISE EXCEPTION 'allowance_cap_exceeded'` when `v_used_new > v_cap` for `ride_debit`. `backend/migrations/261_...` (later) preserves it. **`backend/migrations/277_corporate_allowance_grant_no_master_debit.sql`** — a legitimate, well-reasoned fix for a *different* bug (grant-then-ride double-debiting the master wallet) — redefines `corporate_allowance_apply_delta` via `CREATE OR REPLACE` with a function body that has **no `v_cap` declaration, no `SELECT ... amount`, and no cap check at all**; its own header text states "last defined in `248_corporate_allowance_ride_debit.sql` (originally 29)" — it never mentions migration 258, i.e. it was authored against a stale copy of the function that predates the cap fix and silently reverted it. `backend/migrations/297_corporate_rpc_ride_idempotency.sql:67-190` explicitly documents this ("guard ... that migration 258 added ... has been dead code" / "Fix: restore the v_cap read + 'allowance_cap_exceeded'") and restores it; `backend/migrations/319_late_tip_debit_types.sql:186-293` (the current, most-recent redefinition — confirmed no migration after 319 touches this function) carries the restored guard forward, extended to `late_tip_debit`.
- What happens (during the regression window, between migrations 277 and 297): the per-employee allowance ceiling was silently unenforced — `settle_corporate`'s application-side non-locking read/fallback logic (`payment_service.py:1387` catching `allowance_cap_exceeded`) never fired because the RPC never raised it, so two concurrent corporate rides for the same over-committed member could both post against the allowance and push `used` above `amount` with no fallback to the master wallet and no policy-violation flag. `backend/tests/test_corporate_allowance_cap_race.py` — the unit-level regression guard — kept passing the entire time, because (as its own 2026-08-11 update note says) it tests a hand-ported copy of the locking algorithm, not the real deployed SQL function; it gave false assurance during the exact window the real function was broken.
- Root cause: `CREATE OR REPLACE FUNCTION` versioning (the established pattern for these RPCs per multiple migrations' own comments) has no mechanism to detect that a new migration's function body was derived from a stale prior version rather than the actual current one — a `git diff` on the migration file looks like a normal, reviewable change and doesn't surface that an unrelated invariant from three migrations back silently disappeared.
- Recommendation: this specific regression is closed. Systemic fix (RECOMMENDATION, not a blocker): a real-Postgres test asserting the *invariant* ("a `ride_debit` that would push `used` above a non-null `amount` always raises `allowance_cap_exceeded`") already exists in `test_money_rpc_races.py:73-82` — good — but there is no CI check that a `CREATE OR REPLACE FUNCTION corporate_allowance_apply_delta`/`corporate_wallet_apply_delta` migration is diffed against the *actual last-applied* body (not just the previous migration file that happens to touch the same function name) before merge. Consider a pre-commit/CI check that greps prior migrations for the same function name and warns if the new body doesn't reference the immediately-preceding one's distinguishing comment/guard names.
- Blast radius: `corporate_allowance_apply_delta` — every caller is already catalogued in money-cra.md §3.13 (`corporate_allowance_service.py:68`, `settle_corporate`, `charge_late_corporate_tip`). No new callers found beyond that table.
- Rollout/Rollback: N/A — already shipped and verified current.
- Verification to close: already closed; recommend only the systemic CI-check RECOMMENDATION above, filed as new backlog (no matching `ACTION_ITEMS.md` id found).

### CORP-003 — `update_corporate_wallet_config` is an unguarded generic column patch; only the caller's Pydantic schema currently prevents a `balance` bypass
- Hierarchy: L2 Corporate / B2B Billing › L3 Allowance cap & ledger › L4 S-corp-03
- Severity: LOW (RECOMMENDATION-adjacent; no live bypass found)   Priority score: low likelihood, but blast radius is the wallet-balance invariant itself
- Status: VERIFIED
- Adversary: N/A today (defense-in-depth gap, not an active exploit) — relevant to a future malicious-insider or careless-refactor scenario
- Evidence: `backend/repositories/corporate_repo.py:601-607` — `update_corporate_wallet_config(*, wallet_id, patch: Dict[str, Any])` does a raw `supabase.table("corporate_wallets").update(patch).eq("id", wallet_id)` with **no column allow-list**. Its only two callers today are `routes/corporate_wallet.py:353` (patch built from `WalletConfigPatch`, a Pydantic model whose only fields are `auto_topup_enabled/threshold/amount/daily_cap` — no `balance` field exists on the model, so `body.model_dump()` cannot smuggle one in) and `routes/corporate_accounts.py:882` (a hardcoded `{"auto_topup_enabled": False}` literal). Both are safe today.
- What happens: this function is one future caller away from becoming a silent `corporate_wallet_apply_delta` bypass — e.g. a well-intentioned admin feature that reuses this helper for "bulk-fix a wallet's `low_balance_notified_at`" and is later extended to also let an admin "just patch the balance directly for a one-off correction" would write straight to `corporate_wallets.balance` with no row lock beyond Supabase's own per-statement atomicity, no `corporate_wallet_transactions` ledger row, and no idempotency key.
- Recommendation: add an explicit column allow-list inside `update_corporate_wallet_config` (e.g. `{"auto_topup_enabled", "auto_topup_threshold", "auto_topup_amount", "auto_topup_daily_cap", "low_balance_notified_at"}`) and raise if `patch` contains anything outside it — cheap, additive, and turns this from "safe by caller discipline" into "safe by construction," which is the standard this audit's own non-negotiable #1 asks for.
- Blast radius: 2 callers, both listed above.
- Rollout: additive, no migration. Rollback: revert.
- Verification to close: unit test asserting `update_corporate_wallet_config(patch={"balance": 999})` raises.

## §8 Rebuild Delta card

## Epic: Corporate / B2B Billing
- Verdict per inherited pattern: **MODIFY** — the two-RPC (`corporate_wallet_apply_delta` / `corporate_allowance_apply_delta`) row-locked design is sound and should be kept; the wind-down idempotency gap and the "no allow-list on a generic column patcher" pattern should be fixed, not rebuilt around.
- Keep (already best-in-class for this codebase's constraints): the row-locked, `SECURITY DEFINER`, `CREATE OR REPLACE`-versioned RPC pair as the single writer for corporate money; the atomic-claim (`update_one` with a status-`$in` filter, 0-rows = skip) pattern used consistently across both suspension and offboarding cascades; the `_ensure_member`/`require_company_admin` membership-derived tenant scoping.
- Uber/Lyft do: Uber for Business and Lyft Business both model corporate spend as a **credit-limit-per-employee against a company payment method**, functionally the same shape as Spinr's allowance→master-wallet fallback (INFERRED from public product documentation, not independently fetched this pass — mark ASSUMED if cited as fact). Spinr today: same shape, implemented as two Postgres RPCs instead of a third-party expense-management integration.
- Clean-sheet Spinr would: keep the RPC-pair architecture, but (1) make every RPC caller pass a `client_idempotency_key` unconditionally (not optionally) — the wind-down gap exists precisely because the parameter is optional and one caller forgot it; (2) add a migration-linter check that a `CREATE OR REPLACE FUNCTION` touching one of these two RPCs must diff against the actual last-applied version (via `schema_migrations`) rather than whichever prior migration file the author happened to branch from — this is the exact mechanism that let migration 277 silently regress migration 258's fix. Why (the edge): CORP-002 proves the failure mode is real and has already happened once; a linter turns "caught by luck during a later unrelated migration" into "caught by CI before merge."
- How (architecture/pattern): a `scripts/lint_rpc_migrations.py` pre-commit/CI check that extracts the current DB-side function definition (from a throwaway Postgres apply of all migrations in order, which `run_migrations.py --dry-run`-adjacent tooling could support) and asserts each named guard/exception string from the *previous* version is still present in the new one, or requires an explicit `# regression-ok: <name> intentionally removed because <reason>` comment. Who: whoever owns migration review (per CLAUDE.md, currently no single owner — `docs/PRD.md`/`ACTION_ITEMS.md` migration-owner question is one of W0's carried-forward human-only questions). When: Now (cheap, mechanical, directly prevents a recurrence of a real incident).
- Incremental path from today (no big-bang): step 1 → add `client_idempotency_key` to the wind-down caller (CORP-001, small, no migration). step 2 → add the column allow-list to `update_corporate_wallet_config` (CORP-003, small). step 3 → build the migration-diff linter as a new CI check, opt-in/advisory first (given this repo's pattern of advisory-then-blocking gates, per `00-history.md`'s finding #1 about the merge gate being advisory in practice — don't repeat that pattern here; make it blocking from day one for this specific, narrow check).
- Cost/effort: S (steps 1–2), M (step 3, the linter). Risk: low (all three are additive). Reversibility: full (git revert, no data migration for any of the three). Build (not buy/partner) — this is Spinr-specific migration tooling.
- Advantage type: operational (fewer double-spend incidents) and trust (an auditor or corporate customer's finance team can be shown "every money-moving RPC caller is idempotency-keyed, provably" rather than "we believe so").
- "Why not?": the reason this doesn't already exist is that CI-based Postgres-function-diffing tooling doesn't ship out of the box with `supabase-py`/FastAPI stacks, and the repo's existing migration runner (`run_migrations.py`) is a straightforward ordered-apply tool, not a schema-diffing one — building step 3 requires standing up a throwaway Postgres instance in CI (this repo already needs one for the RLS test tier, so the marginal cost is a second job reusing the same fixture, not a new capability).
