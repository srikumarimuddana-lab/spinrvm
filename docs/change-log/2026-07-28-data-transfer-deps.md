# Change Impact & Risk Log — Data Transfer module: dependencies (Phase 1.4)

## Issue/gap identified
`tabular_writer.py` (Phase 1.3) imports `openpyxl` for its Excel writer, and
the upcoming SGI PDF form-fill (Phase 5) needs `pypdf` to fill real AcroForm
PDFs — neither package is in `backend/requirements.in`/`requirements.txt`, so
`write_excel()` currently raises `ModuleNotFoundError` if called.

## Root cause
Sequenced dependency addition (CLAUDE.md's ≤3-file subtask rule) — the writer
code shipped in 1.3 before its dependency landed in 1.4, by design.

## Fix/remediation
Added to `backend/requirements.in`:
- `openpyxl>=3.1.5` — Excel export in `tabular_writer.py`.
- `pypdf>=6.0.0` — fills the real SGI government AcroForm PDFs (D00032/D00033)
  in the upcoming Phase 5; `fpdf2` (already a dependency, used by
  `t4a_pdf.py`) generates PDFs from scratch and cannot fill an existing
  fillable form, so it isn't a substitute.

**Deviation from the original plan**: the plan called for adding
`python-docx` too (optional Word summary export). I did NOT add it — no code
in this module (or anywhere else in the repo) imports it yet, and CLAUDE.md's
working-style guidance is against speculative additions ("don't design for
hypothetical future requirements"). If a Word-format export becomes an actual
requirement in a later phase, it'll be added in that phase's own subtask
alongside the code that uses it.

Regenerated `requirements.txt` via `pip-compile requirements.in
--output-file requirements.txt --strip-extras --no-header
--annotation-style line --no-upgrade --quiet` (the exact command the
`pip-compile-check.yml` CI workflow's header comment specifies) and
`requirements-locked.txt` via `pip-compile --generate-hashes
--output-file=requirements-locked.txt --strip-extras requirements.txt`
(matching its own auto-generated header). Diffs are minimal and additive:
`openpyxl`, `pypdf`, and their sole new transitive dependency `et-xmlfile`
(pulled in by `openpyxl`).

## Risk & impact on existing functionality
Blast radius: `requirements.in`/`.txt`/`-locked.txt` are shared build inputs
for the entire backend — but `--no-upgrade` was used exactly as CI's own
regeneration command specifies, so every existing pin is untouched; the diff
is purely additive (3 new lines total: `openpyxl`, `pypdf`, `et-xmlfile`).
No existing package version changed. This is the same file every other
backend dependency addition touches, so the blast radius is "the whole
backend build," but the change itself carries the lowest possible risk shape
for that file (additive-only, generated by the tool the repo already trusts
for this file, using the exact flags CI expects).

## User experience effect
None — build-time dependency change only, no runtime behavior for any
existing route.

## Rollback plan
Revert the three files to their prior committed state (`git revert` is safe
here — pure dependency addition, no data or running-service state involved).
If only the pin needs backing out without reverting other work in this PR,
remove the two lines from `requirements.in` and re-run the same `pip-compile`
commands.
