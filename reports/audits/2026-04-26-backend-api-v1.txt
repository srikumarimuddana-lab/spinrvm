TASK 2 — STATE MACHINE & RACE CONDITIONS (DIM-07)
================================================================================

[TASK-2-1] CRITICAL | /wallet/top-up — TOCTOU Race Condition (Balance Corruption)
File: backend/routes/wallet.py (top_up endpoint, ~lines 124–136)
Finding: The top-up flow reads the wallet balance into a Python variable
  (old_balance), computes new_balance = old_balance + amount, then writes it
  back with update_one(). There is no row-level lock between the read and the
  write. Two concurrent top-up requests that both read the same old_balance
  will each compute new_balance = old_balance + X, and the second write will
  silently overwrite the first — one top-up is lost. The @idempotent_endpoint
  decorator only protects against the same idempotency key being replayed,
  not against two distinct concurrent requests.
Fix: Replace the read-compute-write pattern with an atomic Postgres operation.
  Option A: a Supabase RPC that executes
    UPDATE wallets SET balance = balance + $amount WHERE id = $id RETURNING balance.
  Option B: SELECT FOR UPDATE inside a transaction.
  Effort: 3–4 hours.

[TASK-2-2] CRITICAL | /wallet/pay — TOCTOU Race Condition + Non-Atomic Dual Update
File: backend/routes/wallet.py (pay endpoint, ~lines 173–191)
Finding: Same read-compute-write race as TASK-2-1 — concurrent payments both
  pass the sufficiency check on a stale balance, producing overdraft.
  Additionally the wallet balance update (~line 180) and the ride payment_status
  update (~line 187) are two separate, non-atomic DB calls. If the second call
  fails, the rider's balance is debited but the ride is never marked paid.
Fix: Wrap both updates in a single Postgres function or use SELECT FOR UPDATE
  to hold the row lock across both writes. Effort: 4–5 hours.

[TASK-2-3] CRITICAL | /wallet/transfer — TOCTOU Race Condition (Multi-Party)
File: backend/routes/wallet.py (transfer endpoint, ~lines 269–298)
Finding: Transfer reads sender balance (no lock), checks sufficiency, debits
  sender (~line 279), then credits recipient (~line 294) — four steps with no
  transaction boundary. Three races:
  (1) Two concurrent transfers from the same sender both pass sufficiency →
      overdraft.
  (2) Sender debit succeeds; recipient credit throws → sender loses funds,
      recipient receives nothing. Money disappears.
  (3) Two concurrent inbound credits to the same recipient race on the
      recipient balance read → one increment is lost.
Fix: Single Postgres function that locks both rows (in key order to avoid
  deadlock), performs both credits/debits atomically, and returns an error if
  sender balance is insufficient. Effort: 5–6 hours.

[TASK-2-4] HIGH | Loyalty Points Award — Non-Atomic Idempotency Check
File: backend/routes/loyalty.py (earn_points_for_ride, ~lines 123–165)
Finding: Double-award prevention queries for an existing transaction; if absent,
  awards points and inserts a new ledger row. Between the SELECT and the INSERT,
  a second concurrent request for the same ride also finds no row and also
  awards points. Without a unique constraint on (user_id, ride_id), both
  succeed — points are awarded twice for one ride.
Fix: (1) Add UNIQUE constraint on loyalty_transactions(user_id, ride_id).
  (2) Catch unique-constraint violations at the INSERT and treat as a
  successful no-op. Effort: 2–3 hours.

[TASK-2-5] HIGH | Promo Redemption — Non-Atomic Uses Counter
File: backend/routes/promotions.py (apply_promo, ~lines 205–247)
Finding: Flow is: validate promo (checks uses < max_uses) → insert application
  → increment uses in a separate UPDATE. Steps 1 and 3 are not atomic. Two
  concurrent requests for a max_uses=1 promo will both see uses=0, both insert
  applications, then both increment — final uses=2 when max_uses=1.
Fix: Atomic conditional update:
  UPDATE promotions SET uses = uses + 1 WHERE id = $id AND uses < max_uses
  RETURNING id. Zero rows → promo exhausted → 409. Effort: 2–3 hours.

[TASK-2-6] MEDIUM | Fare Split Payment — Non-Atomic Wallet Debit + Status Update
File: backend/routes/fare_split.py (participant_pay, ~lines 298–334)
Finding: Wallet debit (~line 298) and participant status update (~line 314)
  are two sequential DB calls with no transaction. If the status update fails
  after the wallet debit, the participant's balance is reduced but their split
  status remains "accepted" — they appear to still owe money.
Fix: Wrap both writes in a Postgres function or compensate by re-crediting
  the wallet on status-update failure. Effort: 2 hours.

TASK 3 — PAYMENTS (DIM-08)
================================================================================

[TASK-3-1] HIGH | Dispute Refund — No Stripe Idempotency Key
File: backend/routes/disputes.py (admin_resolve_dispute, ~line 188)
Finding: The Stripe refund is created with stripe.Refund.create(payment_intent=...)
  but no idempotency_key is passed. If the HTTP connection drops after Stripe
  processes the refund but before the server receives the response, an admin
  retry (or a network-level retry) will create a second refund against the same
  PaymentIntent. The rider receives double the money; the platform takes the loss.
Fix: Pass idempotency_key=f"refund-dispute-{dispute_id}" to stripe.Refund.create().
  Effort: 15 minutes.

[TASK-3-2] MEDIUM | Dispute Refund Amount Not Bounded by Original Charge
File: backend/routes/disputes.py (admin_resolve_dispute, ~line 169 / ResolveDisputeRequest)
Finding: The refund_amount field in the resolution request is an optional Decimal
  with no upper-bound validation. An admin can submit a refund_amount larger than
  the original ride fare, causing a net payout to the rider at Spinr's expense.
  Stripe itself will reject refunds that exceed the original charge, but only at
  the API call — no guard exists in the application layer.
Fix: After fetching the ride, validate:
  if refund_amount > ride.get("fare_total"):
      raise HTTPException(400, "Refund cannot exceed original fare")
  Effort: 30 minutes.

[TASK-3-3] MEDIUM | Corporate Wallet Top-Up — No Stripe Idempotency Key
File: backend/routes/corporate_wallet.py (topup endpoint, ~line 116)
Finding: stripe.PaymentIntent.create() is called without an idempotency_key.
  A network timeout after Stripe accepts the charge but before the server
  receives the response will result in a duplicate PaymentIntent on retry.
  Mitigated partially by the caller-side @idempotent_endpoint decorator, but
  Stripe-side idempotency is an independent requirement.
Fix: Pass idempotency_key=f"corp-topup-{wallet_id}-{timestamp_bucket}"
  (e.g., rounded to 1-minute windows) to stripe.PaymentIntent.create().
  Effort: 30 minutes.

[TASK-3-4] MEDIUM | Loyalty Redemption — Float Used in Dollar Conversion
File: backend/routes/loyalty.py (redeem_points, ~line 196)
Finding: round(req.points / REDEMPTION_RATE, 2) uses Python's built-in round()
  which employs banker's rounding (round-to-even). Over thousands of redemptions
  this introduces a systematic bias that violates Canadian financial rounding
  conventions (ROUND_HALF_UP). All other monetary arithmetic in the codebase
  uses Decimal with explicit quantize(ROUND_HALF_UP) per the coding standards.
Fix: Replace with:
  Decimal(req.points) / Decimal(REDEMPTION_RATE).quantize(Decimal("0.01"), ROUND_HALF_UP)
  Effort: 15 minutes.

[TASK-3-5] PASS | Consumer Wallet — Correct Decimal Arithmetic
File: backend/routes/wallet.py (~lines 11, 28–32)
Finding: All monetary values use Decimal with _d() helper and
  quantize(ROUND_HALF_UP) before DB writes and API responses. No float
  arithmetic on money paths.
Fix: None required.

[TASK-3-6] PASS | Corporate Wallet Delta — Atomic Postgres RPC
File: backend/routes/corporate_wallet.py (adjust endpoint, ~line 47 in service)
Finding: The corporate_wallet_apply_delta Postgres RPC applies debits/credits
  with row-level locking inside a DB transaction. The corporate path is safe
  from the TOCTOU race that affects the consumer wallet.
Fix: None required. Note: consumer wallet.py should adopt the same pattern
  (see TASK-2-1 through TASK-2-3).

[TASK-3-7] PASS | Stripe Webhook — Idempotency Guard
File: backend/routes/webhooks.py (already audited in prior sessions)

[TASK-4-1] HIGH | Promo discount_value — No Upper Bound
File: backend/routes/promotions.py (CreatePromoCodeRequest, ~lines 43–46)
Finding: The discount_value field on a promo has no maximum validation. Because
  the admin promo endpoints are also unprotected (TASK-1-3), an attacker can
  create a promo code with discount_value=999999 and type="flat", making every
  eligible ride free or negative-cost. Even after auth is added, a maximum bound

Fix: Add Field(..., gt=0, le=500) on discount_value for flat discounts and

[TASK-4-2] MEDIUM | fares.py — lat/lng Query Params Lack Bounds
File: backend/routes/fares.py (GET /fares/fares, ~line 272)
Finding: The lat and lng query parameters are typed as float but have no
  ge/le constraints in the Query() declaration. FastAPI/Pydantic will accept
  float("nan"), float("inf"), or out-of-range values (e.g., lat=999). These
  flow into resolve_service_area_for_point() which may behave unexpectedly on
  invalid coordinates, producing confusing 500 errors rather than a 422.
Fix: Change declarations to:
  lat: float = Query(..., ge=-90.0, le=90.0)
  lng: float = Query(..., ge=-180.0, le=180.0)
  Effort: 15 minutes.

[TASK-4-3] MEDIUM | favorites.py — GPS Coordinate Bounds Not Validated
File: backend/routes/favorites.py (SaveFavoriteRequest, ~lines 26–33)
Finding: pickup_lat, pickup_lng, dropoff_lat, dropoff_lng are float fields in
  the Pydantic model with no geographic bounds. A user can store
  pickup_lat=9999.0 in their favorites; this breaks downstream route-finding
  calls when the favorite is used to pre-fill a ride request.
Fix: Apply the validators from backend/validators.py (validate_coordinates or
  equivalent) to the four coordinate fields via @field_validator. Effort: 30 min.

[TASK-4-4] MEDIUM | favorites.py — name Field Has No max_length
File: backend/routes/favorites.py (SaveFavoriteRequest.name, ~line 26)
Finding: The name field for a saved favorite has no length constraint. A user
  can submit a string of arbitrary length (MB-scale) that is stored and returned
  on every GET /favorites call. With 20 favorites each carrying a 1MB name, a
  single API response would be 20MB, causing performance degradation and
  potentially exhausting the response buffer.
Fix: Add max_length=100 to the field definition:
  name: str = Field(..., min_length=1, max_length=100)
  Effort: 5 minutes.

[TASK-4-5] MEDIUM | wallet.py — recipient_phone Not Validated in Transfer
File: backend/routes/wallet.py (TransferRequest, ~lines 97–98)
Finding: recipient_phone is accepted as a plain str with no pattern, min_length,

[TASK-4-6] MEDIUM | corporate_wallet.py — AdjustRequest.amount Has No Bounds

[TASK-4-7] MEDIUM | corporate_company.py — Allowance float Instead of Decimal

TASK 5 — ERROR HANDLING (DIM-10)
================================================================================

[TASK-5-1] HIGH | Dispute Resolution — Stripe Failure Does Not Roll Back Resolved Status
File: backend/routes/disputes.py (admin_resolve_dispute, ~lines 188–208)
Finding: The flow marks the dispute as "resolved" in the DB, then calls
  stripe.Refund.create(). The Stripe call is wrapped in a bare except Exception
  (# noqa BLE001). If Stripe fails, the exception is logged but execution
  continues — the dispute is left in "resolved" state with no refund ever
  issued. The rider's complaint is closed but the money was never returned.
  Admins have no automatic alert; the discrepancy can go unnoticed for weeks.
Fix: Either (a) call stripe.Refund.create() BEFORE updating the dispute status
  and only commit the status change if Stripe succeeds, or (b) on Stripe
  failure, revert dispute status to "pending" and return 502. Effort: 2–3 hours.

[TASK-5-2] MEDIUM | Loyalty Redemption — Points Deducted, Wallet Credit Fails Silently
File: backend/routes/loyalty.py (redeem_points, ~lines 206–226)
Finding: The redemption endpoint deducts loyalty points first, then credits the
  rider's wallet. If the wallet credit throws, the exception is caught and
  logged but the loyalty deduction is NOT reversed. The rider loses points with
  no financial benefit — a silent one-sided transaction.
Fix: Perform the wallet credit first. If it succeeds, deduct the points. If
  points deduction then fails, issue a compensating wallet debit and return 503.
  Effort: 2–3 hours.

[TASK-5-3] MEDIUM | Corporate Account — Wallet Creation Failure Not Handled on KYB Approval
File: backend/routes/corporate_accounts.py (kyb_review endpoint, ~line 169)
Finding: ensure_corporate_wallet() is called when KYB is approved but
  exceptions are not caught. If wallet creation fails (e.g., DB timeout), the
  company's KYB status becomes "approved" but no wallet exists. The next ride
  billed to the company will fail with a confusing 500.
Fix: Wrap in try/except; on failure return 503 and set KYB status back to an
  intermediate state, then retry via a background task. Effort: 1–2 hours.

[TASK-5-4] MEDIUM | /wallet/transactions — DB Error Silently Returns Empty List
File: backend/routes/wallet.py (get_transactions, ~lines 226–228)
Finding: db.get_rows() is inside a try/except that catches any exception and
  returns an empty list. A rider with 50 transactions will see an empty history
  if the DB is slow, with no indication of an error. HTTP status is 200.
Fix: Remove the swallow or re-raise as HTTPException(503). Effort: 15 minutes.

[TASK-5-5] MEDIUM | promotions.py — Bare except in get_available_promos
File: backend/routes/promotions.py (get_available_promos, ~lines 365–366)
Finding: A bare except Exception silently drops any promo that raises during
  per-promo validation. A promo with corrupted data is invisibly skipped —
  admins never see why a promo stopped appearing in the app.
Fix: Log at ERROR level with promo_id, and optionally surface a partial-failure

[TASK-5-6] PASS | disputes.py — User-Facing Endpoints Return Proper HTTPExceptions
File: backend/routes/disputes.py (create_dispute, get_user_disputes, get_dispute)

TASK 7 — PERFORMANCE (DIM-14)
================================================================================

[TASK-7-1] HIGH | disputes.py Admin List — N+1 Query Pattern (100+ DB Calls)
File: backend/routes/disputes.py (admin_get_disputes enrichment, ~lines 130–140)
Finding: After fetching up to 50 dispute rows, the endpoint loops over each
  dispute and makes two additional DB calls: get_user_by_id() and get_ride().
  With 50 disputes this produces up to 101 sequential DB round-trips per
  request. Under Supabase's REST API latency (~5–15ms/call), this adds 0.5–1.5
  seconds of pure DB latency per admin page load — and will worsen as dispute
  volume grows.
Fix: Collect unique user_ids and ride_ids from the dispute rows first, then
  batch-fetch users and rides with get_rows({"id": {"$in": [...]}}) — reducing
  to 3 total queries regardless of dispute count. Effort: 2 hours.

[TASK-7-2] MEDIUM | promotions.py — N+1 Per-Promo Usage Check in get_available_promos
File: backend/routes/promotions.py (get_available_promos, ~lines 294–296, 324–327)
Finding: The endpoint fetches up to 100 active promos, then for each promo
  makes a count_documents() call to check how many times the current user has
  used it. 100 promos → 100 extra DB calls per request. For a rider checking
  available promos on the booking screen this causes noticeable latency.
Fix: Fetch all promo_applications for the current user in one query, then join
  in memory:
    used = {row["promo_id"]: row["count"] for row in user_usage_rows}
  Effort: 2–3 hours.

[TASK-8-1] MEDIUM | Fare Split — No Refund Logic on Cancellation or Decline
File: backend/routes/fare_split.py (cancel_split ~line 349, participant_respond ~line 235)
Finding: When a split is cancelled by the requester, or when a participant who
  has already paid declines their portion, no refund or wallet credit is issued.
  The paid participant is financially worse off, the split is cancelled, and
  their money is silently retained. This will generate support tickets.
Fix: On split cancellation, iterate participants with status="paid" and issue a
  compensating wallet credit equal to their share. On participant decline after
  payment, issue a credit and recompute remaining shares for still-accepted
  participants. Effort: 3–4 hours.

[TASK-8-2] MEDIUM | corporate_company.py — GeoJSON Geofence Not Schema-Validated
File: backend/routes/corporate_company.py (set_policy endpoint, ~lines 355–358)
Finding: The geofence field of a company policy is accepted as a raw dict and
  stored without GeoJSON schema validation. A malformed geofence (missing
  "features" array, wrong coordinate order) will pass the Pydantic layer but
  break the geofence evaluation function at ride-request time, blocking all
  corporate rides for that company.
Fix: Validate the dict against a minimal GeoJSON schema (type == "FeatureCollection",
  features is a list, each feature has geometry with type and coordinates) using
  a @field_validator before storing. Effort: 1–2 hours.

[TASK-8-3] RECOMMENDATION | Fare Split — Hard Limit of 5 Participants
File: backend/routes/fare_split.py (SplitRequest, ~line 42)

Fix: Add a code comment: # Product limit: max 5 participants by design.
  No change needed at current scale.
