# Challenges & Issues: Decide and, if warranted, implement a rideless/standalone SOS path

## Stage 3-4: Design & Architecture

**Stage 1-2's mount-site assumption was wrong — `app/(tabs)/index.tsx` mounts `RiderSOS`, not `SOSButton` directly.**
The Stage 1-2 report (and the acceptance criteria it produced) described the client wiring as "`SOSButton`'s `if (!rideId)` branch ... calls the new path instead of showing the blocking dialog," implying the home screen mounts `SOSButton` directly. Re-reading `rider-app/app/(tabs)/index.tsx` in this stage shows it actually mounts `RiderSOS` (`rider-app/components/RiderSOS.tsx`), a thin wrapper that forwards only `rideId`/`onTrigger`/`size`/`t` to the real `SOSButton`. Had this gone unnoticed into Stage 5, the two new optional props could have been added to `SOSButton` correctly and still been completely unreachable from the actual app, because `RiderSOS` wouldn't have forwarded them — a "looks done, isn't" failure mode that unit tests on `SOSButton` alone would not have caught (they'd test the component that has the capability, not the wrapper that fails to expose it). Caught by grepping every mount site of both `SOSButton` and `RiderSOS` and cross-checking against the exact JSX tag at the home-screen line number, not by trusting the prior stage's prose description. `RiderSOS.tsx` is now in the Stage 5 file list because of this.

**The `app_settings`/`settings` table turned out to have a real schema constraint that Stage 1-2 explicitly flagged as unverified — and it mattered.**
Stage 1-2's report said plainly: "I did not check whether `app_settings`'s admin API already supports adding an arbitrary new boolean flag key without additional plumbing, or whether it needs a schema/migration change first." This stage checked, and the answer is consequential: `settings` is a fixed-flat-column table with no JSON catch-all (confirmed via migration 313's own header, which exists specifically because a prior PR added flag fields to the Pydantic model without a matching migration and broke `PUT /api/admin/settings` outright — the request 500s on referencing an unknown column). This means "add a new `app_settings` flag" is not free — it always requires a same-PR migration, and skipping that step would reproduce a bug this codebase has already been bitten by once. Good example of Stage 1-2's "I didn't check X" note doing its job: it flagged exactly the right unknown to resolve before Architecture could commit to a design.

**The `isSosUrl` regex in `shared/api/client.ts` is a narrow, easy-to-miss piece of shared security-relevant logic.**
Nothing in the Requirements or Stage 1-2 report mentioned this file at all. It surfaced only from reading `shared/api/client.ts` directly while tracing how the existing ride-scoped SOS call avoids the 401-refresh interceptor. If Stage 5 had implemented the new endpoint and new client call without also touching this regex, the feature would have *appeared* to satisfy acceptance criterion 1 in every manual test with a valid token, and would have silently failed it only for a rider whose access token had actually expired — precisely the scenario the whole "never gate SOS behind auth refresh" rule exists to protect, and precisely the scenario least likely to be covered by a casual smoke test. Recorded as its own decision in `decisions.md` rather than a one-line file-list entry, because getting the regex's exact shape wrong (too broad) is its own separate risk, not just a missed feature.

**Not a challenge, but worth naming as a genuinely good sign:** the migration-315 idempotency unique index turned out to have zero `ride_id` dependency at all (`(reported_by_user_id, sos_idempotency_key) WHERE sos_idempotency_key IS NOT NULL`), which meant a finding I went looking for — "does Postgres's NULL-is-distinct-in-unique-indexes behavior break dedup for ride_id=NULL rows" — doesn't actually apply here, because `ride_id` was never part of the index. Worth stating explicitly rather than silently dropping the check, per GUARDRAILS.md's "things the pipeline will not pretend it verified" — this one *was* verified, and came back clean.
