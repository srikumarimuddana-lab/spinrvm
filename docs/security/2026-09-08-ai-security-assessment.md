**Spinr AI security assessment — 8 September 2026**

Repository: [srikumarimuddana-lab/spinrvm](https://github.com/srikumarimuddana-lab/spinrvm). Reviewed revision: [7e8ae35f2c006b40abb1697cf014bd366026b3b3](https://github.com/srikumarimuddana-lab/spinrvm/commit/7e8ae35f2c006b40abb1697cf014bd366026b3b3), the main-branch revision captured for this review. All code links below are pinned to it. The assessment was read-only. This documentation PR records its findings and remediation acceptance criteria; it does not implement the fixes or change application code, deployment settings, or database records.

**Review baseline:** Findings and test results apply to the pinned revision above. The PR is based on a newer main revision; implementation work must revalidate each finding against its starting revision. The recorded test results are historical audit evidence, not tests of a security fix.

**Assessment: the rider AI has sound server-side ownership controls, but the stronger claim “only a verified phone/email customer can chat, access ends at logout, and all privacy guardrails hold” is not established by this implementation.** Several concrete gaps need correction. No working remote attack that reads another customer's private ride, wallet, or conversation records was demonstrated. That conclusion does not eliminate the device-local disclosure, identity-policy, privacy, and cache defects below.

**Answers to your questions**

| Question | Finding |
|---|---|
| Can someone call the rider AI without an authorization token? | The rider `/api/v1/ai/chat` route requires `get_current_user`; the focused route tests reject missing authentication. |
| Is a valid token necessarily a non-anonymous, phone/email-verified customer? | No. The Firebase exchange does not reject the anonymous sign-in provider or require a verified contact claim. An offline probe reproduced provisioning and token issuance with neither phone nor email. Production reachability depends on Firebase configuration and deployed controls. |
| Does the AI identify a customer by a phone/email typed into the chat? | No. The trusted identity is the server-resolved user ID. | Is there caching or stored memory? | Yes: database chat history, optional shared FAQ answer caching, conversation quote pins, provider prompt caching, and device state. These have different isolation and retention rules. |

**The actual AI surfaces**

There are more security boundaries than the two main chat interfaces. Rider and driver help-centre chat use the shared authenticated engine. The separate `agents/` development framework is not the customer AI runtime.

| Surface | Access and data scope | Relevant controls or exception |
|---|---|---|
| Rider assistant and shared help-centre chat | `/api/v1/ai/chat`, authenticated user; rider/driver tools selected by audience | Ownership checks, daily quota, bounded tool loops, global enable switch. A rider cannot request driver tools without driver status. |
| Public website assistant | `/api/v1/ai/public-chat`, intentionally anonymous | Separate public switch plus global switch; only `search_faqs` and `get_company_info`; no customer account lookup or saved chat history. |
| Older Gemini support chat | `/api/v1/support/chat`, authentication required | Still mounted; bypasses the newer global AI switch and AI-specific usage controls. |
| Admin AI console | Super-admin can select a non-staff target user | Audited impersonation/read capability; bypasses the target user's daily quota, with a separate request limiter. |
| Help-desk AI reply drafting | Staff with support-ticket permission | Reads the selected ticket/thread and produces a draft; no AI tools and no automatic sending. |
| Optional external MCP interface | `/mcp`, bearer token and both enable switches required | Read-only exposed tools, request-local identity and daily tool quota; staff-role rejection and strict redaction have defects. |

**Controls that are implemented well**

The security boundary is principally backend code, not the model's promise to obey instructions. `execute_tool` restricts audiences, rejects unknown/forbidden identity arguments, validates schemas, verifies owned resources, injects the authenticated user, applies timeouts, and caps tool output. There is no general customer-search, arbitrary SQL, shell execution, or arbitrary URL-fetch tool in the reviewed registry. The recent anonymous-tool identity exception applies to the restricted `web` audience; it does not grant that audience personal tools. [Tool authorization and execution](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools.py#L393-L474).

Ride tools verify `rider_id == user.id`; wallet tools find the user's own wallet before transactions; saved places use the user's ID. Existing conversation selection, listing, message retrieval, and deletion check the owner. Passing a foreign conversation or ride ID is treated as missing. [Ride ownership](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools_rides.py#L90-L151), [account tools](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools_account.py#L49-L78), [conversation ownership](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/conversations.py#L32-L60), [history/delete ownership](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/conversations.py#L117-L169).

The AI proposes a ride; it does not directly create, charge, cancel, or refund one. The booking card obtains authoritative estimates, shows the price, requires a rider tap, and calls the normal booking path. Card payments can require the standard payment flow. This preserves a valuable human confirmation boundary. [Booking proposal tool](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools_booking.py#L1480-L1581), [confirmation handling](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/rider-app/components/BookingProposalCard.tsx#L170-L213).

The database migrations enable RLS and deny direct authenticated-client access to AI tables. The backend uses service-role access, so its ownership predicates remain the decisive per-customer control; this is not database-enforced per-user isolation for service-role queries. Supabase explicitly documents service-role bypass behavior. [AI RLS migration](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/migrations/140_ai_assistant_conversations.sql#L49-L79), [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

**Priority findings**

High means address before relying on the stated customer-only/privacy guarantee. Medium means a material conditional defect or missing protection. These are assessment priorities, not CVSS scores or proof of a production incident.

**F01 — High, conditional production exposure: anonymous Firebase identities are not explicitly prohibited.**

`firebase_auth_login` validates the Firebase token and project audience, then accepts a UID with `phone_number` absent, creates a rider row with an empty phone, and issues access/refresh tokens. It never checks `firebase.sign_in_provider == anonymous` or requires verified phone/email. The shared authentication dependency accepts the resulting customer JWT and the AI route does not impose a verified-contact requirement.

An isolated probe supplied an already-verified anonymous Firebase payload, mocked database writes, and observed both token issuance and acceptance by the AI authentication dependency. This verifies the backend policy gap, not that anonymous authentication is currently enabled in production. Firebase supports anonymous authenticated accounts, so “cryptographically valid token” and “verified phone/email customer” are distinct policies. The schema's unique phone constraint can limit creation of multiple empty-phone rows; it is not an identity-verification control. [Firebase exchange](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/routes/auth.py#L1389-L1487), [Firebase anonymous authentication](https://firebase.google.com/docs/auth/web/anonymous-auth).

**Fix:** explicitly reject anonymous identities and unsupported sign-in providers, enforce the intended verified-contact/account eligibility policy before provisioning or issuing tokens, and apply that eligibility policy consistently to protected customer AI. Verify the production Firebase provider configuration. App Check attests a client; it does not replace verification of the customer's identity.

**F02 — High: ordinary logout leaves access-token authority; refresh revocation also depends on token transport.**

The logout handler explicitly leaves the access token valid until expiry. It writes a session tombstone, but the shared `get_current_user` dependency does not consult that ordinary-logout tombstone. An offline check confirmed that a valid customer JWT still authenticates without consulting positive session-revocation evidence. The configured default access lifetime is 15 minutes. This requires possession of a previously valid token; it is not unauthenticated access.

The shared mobile logout calls `api.post('/auth/logout')` with no body. The server revokes a refresh token only if one arrives in a cookie or the body. A separate probe confirmed successful logout with no refresh revocation when neither is supplied. Native cookie handling was not exercised on a device, so this part is conditional on whether that client actually sends a refresh cookie. A retained unrevoked refresh token has a default 30-day lifetime. Logout-all has stronger user-wide token-version/Firebase-watermark controls. [Logout implementation](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/routes/auth.py#L1895-L1956), [mobile logout](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/shared/store/authStore.ts#L641-L700), [token lifetimes](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/core/config.py#L117-L129).

**Fix:** enforce revocation for the signed-out session on protected AI requests and terminate its active AI streams. Explicitly pass/revoke the native refresh credential or revoke the authenticated session's refresh-token family server-side. Preserve legitimate other-device sessions. Test normal logout separately from logout-all.

**F03 — High: rider AI state is not cleared or partitioned when the account changes.**

The AI store uses a single `spinr_ai_conversation_id` AsyncStorage key and an in-memory message/action list. Unlike other per-session stores, it registers no logout callback. Auth logout runs registered callbacks, but the AI messages, conversation ID, pending map pin, and stream controller are not reset there. The screen initially renders the existing store and asynchronously loads history. An eventual foreign-conversation rejection clears the store, but it does not prevent displaying stale data while the request is pending or an earlier stream updating state.

This is a same-device/account-switch privacy defect identified from source; a physical device/UI reproduction was not performed. It does not show that the new account can fetch the old account's history from the backend. [AI store and persistence](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/rider-app/store/aiChatStore.ts#L11-L169), [stream callbacks and reset](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/rider-app/store/aiChatStore.ts#L199-L355), [screen state and history loading](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/rider-app/app/ai-assistant.tsx#L216-L298).

**Fix:** clear AI state on every session end/account switch, namespace any retained conversation pointer by authenticated user ID, abort in-flight work, and reject callbacks from a previous session generation. Do not reuse the current `stopStreaming` behavior blindly for logout: it can flush a queued map pin into another send.

**F04 — High: the older support AI bypasses the new incident and usage controls.**

`/api/v1/support/chat` is still mounted and can invoke Gemini using `GEMINI_API_KEY`/`GOOGLE_API_KEY` without consulting `ai_assistant_enabled`, the provider factory, or the user AI daily quota. Its message field lacks the newer chat length bound, and it calls synchronous `generate_content` inside an async route. A slow provider can block that worker's event loop. Authentication remains required; the unused `driver_id` field is not evidence of another driver's data being read. General HTTP middleware may still apply, so this is a bypass of AI-specific controls rather than a claim that all rate limiting is absent. [Legacy endpoint](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/routes/support.py#L99-L149).

**Fix:** remove the unused route or route it through the central authenticated engine with the same switch, budgets, input limits, provider configuration, and asynchronous timeout handling. The current help-centre UI already uses the newer endpoint. The legacy route, current Gemini adapter, and Gemini embeddings use the deprecated `google.generativeai` SDK; migrate the remaining paths to a supported SDK. Google's repository confirms the legacy library no longer receives fixes. [Gemini adapter](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/providers/gemini_adapter.py#L78-L100), [Google deprecation notice](https://github.com/google-gemini/deprecated-generative-ai-python/blob/main/README.md).

**F05 — Medium: truncation drops the shared-cache exclusion flag.**

FAQ search marks location-dependent results with `_no_cache`. `_cap_result` rebuilds results over 4,000 characters and preserves selected guardrail keys, but omits `_no_cache`. The orchestrator then sees an ordinary FAQ-only turn and may cache it under audience plus normalized question, without service area. The offline integration probe demonstrated that a short scoped result is not stored while the same kind of long result is stored.

Impact: a response based on one service area's policy can be replayed to another user's identical opener. This is a confirmed cache-isolation/correctness defect, not demonstrated leakage of private ride records. The FAQ response cache defaults off; current production state was not queried. [FAQ flag](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools_support.py#L348-L380), [truncation](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools.py#L240-L294), [cache decision](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/orchestrator.py#L435-L446).

**Fix:** preserve security/cache metadata outside the model-facing truncation path. Keep shared caching limited to explicitly public, grounded responses; include relevant scope/content versions and invalidate on FAQ changes. The present cache also permits answers with no tool calls, so it does not prove the answer came from approved FAQ content. Clear existing entries when deploying the fix.

**F06 — High for sensitive-data handling: redaction is incomplete and inconsistent across egress paths.**

Three defects were reproduced with synthetic data. First, normal 4-6-5 spaced Amex formatting and bare nine-digit SIN-shaped values survive `scrub_pii`. Second, help-desk staff instructions are appended verbatim after ticket/thread scrubbing, so pasted customer phone/email bypasses that boundary. Third, MCP's purported STRICT serialization retains numeric `lat`/`lng` values; it scrubs string values recursively, not coordinate fields. Plain street addresses also remain. The saved-place tool supplies exactly those structured fields.

These defects expose data to the selected provider or authorized external MCP client. They do not independently make another customer's account readable. Names, free-form addresses and licence identifiers are also not reliably anonymized by the regex approach. [PII patterns and policy](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/pii.py#L79-L126), [recursive scrubber](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/pii.py#L261-L297), [staff-instruction exception](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/support_assistant.py#L117-L184), [MCP serializer](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/mcp_server.py#L77-L89), [saved-place output](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools_account.py#L183-L195).

**Fix:** define typed, allowlisted payloads for each recipient; redact sensitive fields by meaning as well as string pattern, sanitize staff input too, and reject payment/identity-document content that the assistant does not need. Apply a separately documented location policy to external MCP clients. Add synthetic boundary tests for mixed numeric/string payloads and split/formatted sensitive identifiers.

**F07 — Medium, MCP must be enabled: staff rejection checks only one role.**

MCP rejects `role == admin`, while the verified staff token pipeline also returns `super_admin`, `operations`, `support`, `finance`, and `custom`. Offline middleware probes confirmed the admin role is rejected but those five verified staff roles reach the downstream MCP app. Tools remain scoped to the supplied staff identity; no arbitrary customer impersonation through this defect was demonstrated. [MCP gate](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/mcp_server.py#L146-L167), [staff roles and verified marker](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/dependencies/__init__.py#L246-L264).

**Fix:** reject all verified administrative principals using the trusted authentication marker and an explicit customer-principal policy. Test every staff role. Prefer dedicated, narrow, revocable MCP credentials if external clients are a supported product feature, instead of sharing general app tokens.

**F08 — Medium: filtering occurs after live AI output is delivered.**

The orchestrator yields provider text directly as token frames. Only at the end does it scrub/filter text for persistence and caching. The non-streaming help-centre path concatenates those same unfiltered frames. A scripted provider response containing a synthetic email reached the emitted response unchanged. Therefore a clean database transcript does not prove the user saw a clean answer. Threat scanning is explicitly detection/telemetry; suspicious text still goes to the model. [Live emission and final filtering](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/orchestrator.py#L374-L495).

**Fix:** validate the answer before delivery, or use bounded streaming buffers capable of detecting sensitive values across token boundaries. Apply consistent output rules to streaming and non-streaming responses. Preserve the hard backend tool checks even when improving prompts: no system prompt can guarantee every response stays on topic or is factually correct.

**F09 — Medium: cost and concurrency safeguards are useful but incomplete.**

The main route has a user-based 10/minute limit and a default 50 messages/day. Defaults also bound output tokens to 1,024, iterations to 6, and tool calls to 5 per iteration, with per-tool timeouts. MCP has a separate daily tool quota. Public chat has 6/minute per IP and smaller loops, but no aggregate daily spend ceiling in its runner. Distributed clients can multiply the public limit. The IP resolver trusts forwarding headers and explicitly relies on origin traffic being restricted to the trusted proxy.

On Redis failures the daily cap falls back to a bounded process-local allowance, which can multiply across workers/restarts. Conversation locking fails open on Redis error; its 90-second TTL is neither renewed nor released using a unique ownership token. These are cost/order/availability risks rather than demonstrated cross-customer reads. [Rate limits](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/utils/rate_limiter.py#L541-L557), [trusted-proxy assumption](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/utils/rate_limiter.py#L87-L108), [quota and lock behavior](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/orchestrator.py#L142-L233).

**Fix:** add global provider-spend/token budgets and concurrent-generation limits, a bounded whole-turn deadline, cancellation cleanup, and an explicit distributed-store outage policy. Protect public chat with server-verifiable abuse controls and verify direct-origin restrictions. Use an ownership-safe lock with a suitable renewal/deadline strategy.

**F10 — Medium assurance gap: adversarial model evaluation is manual and the documented URL is wrong.**

The promptfoo harness is intentionally outside CI. Its documented base URL is the root development server, while its configured request appends `/ai/chat`; the application mounts `/api/v1/ai/chat`. As documented, it will not test the intended route. This was established from configuration and router mounting, not by running paid/live model evaluations. Model responses, actual tool decisions, successful HTTP status and the positive baseline need to be checked together. [Evaluation configuration](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/evals/promptfoo/promptfooconfig.yaml#L13-L61), [documented execution](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/evals/promptfoo/README.md#L21-L36).

**Fix:** correct the route/base-URL contract, assert status/schema and successful normal use, and require recorded adversarial evidence for model, prompt, tool, and caching changes. Include direct/indirect injection, account swapping, long scoped FAQ output, all staff roles, and the redaction cases above. Unit tests using scripted providers cannot measure real-model jailbreak resistance.

**Caching, memory and retention**

| Mechanism | What is retained | Isolation / lifetime | Assessment |
|---|---|---|---|
| Database conversation history | User text, assistant text, tool names, usage/model metadata; no full tool argument/result records in these chat tables | Conversation linked to user; default model context is the most recent 12 messages; message purge policy 90 days | Sound owner checks; text scrubbing is incomplete and location exemptions preserve sensitive trip context. |
| Shared FAQ response cache | Final answer for a normalized, scrubbed first question | Redis key is audience + question hash; default TTL 3,600 seconds; defaults off | Personal tools, follow-ups and admin turns excluded, but F05 breaks scoped-FAQ exclusion. No-tool answers are allowed. |
| Pinned fare quote | Trip endpoints/addresses and quote context | Redis `ai:quote:{conversation_id}`; 900 seconds | Read after conversation ownership is established. Deleting a conversation does not explicitly evict this key. |
| Anthropic prompt cache | The system prompt is marked ephemeral | Provider-managed; this code does not specify a TTL | The system prompt can include the conversation's pinned quote. It is not guaranteed to contain only public static text. |
| FAQ embeddings | Model-labelled FAQ vectors; query/FAQ text sent for embedding | Persistent FAQ vectors; optional semantic search defaults off | Not a shared customer conversation memory. It creates an additional provider egress path. |
| Device AI store | In-memory messages/actions; conversation pointer in AsyncStorage | One unscoped pointer and one store per app process | F03: cleanup and session binding are missing. |
| Settings and account helper caches | Runtime settings, selected account/driver records | Settings nominally 60 seconds; driver-by-user 30 seconds | These are application caches, not learned AI memory. Settings changes can have propagation delay. |

The 90-day SQL purge and a daily background invocation are present in code, but successful execution on the production database was not verified. AI tool/security audit tables retain metadata and need their own confirmed retention policy. Deleting a chat does not prove deletion from provider logs, Redis quote pins, support tickets or backups. “New conversation” currently resets local state and is not a server-side erasure operation. [Retention SQL](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/migrations/335_purge_pii_retention_step_a_planned_route_polyline.sql#L273-L295), [scheduled purge](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/core/lifespan.py#L450-L452), [quote cache](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/tools_booking.py#L277-L313), [provider prompt caching](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/providers/anthropic_adapter.py#L68-L75), [FAQ cache implementation](https://github.com/srikumarimuddana-lab/spinrvm/blob/7e8ae35f2c006b40abb1697cf014bd366026b3b3/backend/ai/response_cache.py#L36-L92).

**What leaves Spinr, even when the correct user is selected**

Account isolation is separate from third-party data disclosure. The AI_CHAT policy deliberately preserves trip-location information, including bracketed coordinates and postal codes. Personal tool results can include trip addresses, saved places, balances and ride/fare context. The model therefore can receive sensitive data about the authorized customer. UI-only `_client_action` content is separated from model-facing output, which is a useful minimization measure, but does not remove all location data from the model's context.

| Recipient/path | Possible data | Required production decision |
|---|---|---|
| Selected chat provider: Anthropic, OpenAI, Gemini, or OpenRouter | Chat/history, allowed personal tool results, addresses/pins, FAQ/company content | Approved provider/model, processing location, retention/training settings, subprocessor terms, customer notice/consent. OpenRouter adds its routing/provider chain. |
| Embedding provider | FAQ questions and generated search queries | Apply a separate data-minimization policy; do not assume the main chat scrubber protects this call. |

Provider selection is an allowlist, with no arbitrary user-supplied provider URL and no silent fallback provider. Keys are server-side settings/environment values, masked on normal admin reads; super-admin reveal is audited. However, AI credential/provider/model changes are not included in the settings handler's super-admin-only field list. Treat permission to change the AI destination as a sensitive governance capability. Settings-backed AI keys are persisted as text fields without an application-level encryption step in the reviewed write path; storage encryption and secret-management controls must be verified separately. Two additional boundaries deserve tightening. If `ai_escalation_creates_ticket` is enabled, the model-triggered tool can create a support ticket without a separate explicit confirmation/idempotency step. Super-admin console turns can append messages into the customer's thread, while message rows do not carry per-message admin authorship; use separate test/support threads or clearly labelled provenance. These are authorized features whose effects should be visible to the customer and auditable, not claims of anonymous access. **Alignment with AI-agent security guidance**

The evaluation used OWASP's guidance on least-privilege tools, context isolation, human approval, output validation and adversarial testing, together with its authorization guidance. These are engineering benchmarks, not a certification or a claim about Uber/Lyft's private implementation. [OWASP AI Agent Security](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html), [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

| Control area | Spinr assessment |
|---|---|
| Authenticated principal and verified identity | Partially met: token validation works; anonymous-provider eligibility and ordinary-logout revocation need correction. |
| Resource authorization and least privilege | Strong in reviewed customer tools; keep central ownership checks mandatory for new tools. MCP staff-role exclusion needs correction. |
| Memory/context isolation | Server conversation ownership is strong; shared cache and device-session boundaries need fixes. |
| Human approval for consequential actions | Ride creation has a confirmation card and normal backend path; ticket creation and admin message provenance need tightening. |
| Sensitive-data minimization | Partial: regex filters and whitelists exist, but structured fields, staff input and identifier formats bypass them. Location transfer is intentional on the rider path. |
| Prompt injection and output safety | Backend tools limit impact; detection alone does not block attacks, and emitted text precedes filtering. |
| Resource/cost limits and safe degradation | Useful per-user/per-turn limits; legacy/public paths and distributed-store failure behavior need stronger ceilings. |
| Observability and testing | Tool/security metadata, metrics and a substantial test suite exist; live adversarial evidence and production retention/alert verification remain necessary. |

**Verification performed and limits**

The focused backend command covered `tests/test_ai*.py`, `tests/test_support_assistant.py`, `tests/test_support_tickets_ai_suggest.py`, and `tests/test_routes_support_coverage.py`, with coverage disabled for this scoped run. Result: **592 passed, 1 skipped, 0 failed**, in 40.14 seconds. Two warnings concerned the test HTTP client and the deprecated Google AI SDK. This is a focused suite result, not a whole-repository coverage percentage or a production penetration test.

Separately, **20 synthetic offline checks** ran against the unmodified implementation using mocked databases, Redis/provider seams, and verified identity fixtures. They reproduced cache-flag loss and actual cache-store eligibility, output-before-filtering, the PII/MCP payload gaps, all six staff-role outcomes, ordinary-logout authentication behavior, anonymous-origin token exchange and authentication, and the no-cookie/no-body refresh-revocation gap. These checks confirm code behavior under their stated conditions; they do not prove live Firebase configuration, live provider behavior, or database constraints in production.

The review traced authentication, all six AI surfaces, ownership, booking and escalation effects, public tools, provider adapters, embeddings, client chat state, caches, migrations, retention wiring, rate limits, and relevant tests. No customer records or real provider credentials were used. No paid model calls were made. No physical-device account-switch test, live Supabase RLS test, production traffic/secret/incident review, complete dependency-CVE scan, or real-model red-team run was performed.

Source defaults turn the main AI, public AI, MCP, FAQ response cache, semantic FAQ search and automatic escalation ticket creation off. Defaults are not proof of the deployed values.
