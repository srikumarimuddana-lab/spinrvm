# Run: Archive the stale memory/ and discovery/ directories

Confirm nothing references the `memory/` and `discovery/` directories CLAUDE.md flags as stale, remove them from the working tree, and update CLAUDE.md's (and any duplicate's) directory table so this doesn't resurface as an open TODO.

## Stage 1-2: Ideation & Requirements

**What I found before proposing anything:** `memory/` and `discovery/` do not exist in the current working tree, on `origin/main`, or anywhere reachable in `git log --all` for creation without a matching deletion. `git log --all -- memory discovery` shows they *were* deleted already, in commit `223ec89b0` (PR #451, "chore: coverage push 53% → 60.68%", merged 2026-05-05), whose message explicitly says: "Delete `discovery/` (early Expo SDK 54 sandbox, unreferenced by any surface)" and "Delete `memory/` (originally for agent memory, contained only `.gitkeep`)". So the directory-removal half of this task is already done — it happened three and a half months ago, as an incidental side-item in an unrelated coverage-ratchet PR. What was never done is telling CLAUDE.md (and its duplicate, AGENTS.md) that it happened, which is exactly why this task exists: the "Claude-Adjacent Directories" table still describes both as present-and-`Stale`/"can be archived" as of today (2026-08-20), and at least one later audit (`reports/audits/2026-07-22-implementation-certification-plan-v1.md`, dated *after* the actual deletion) cites that stale table as if the directories still existed, using them as precedent for archiving a different directory (`frontend/`).

I also confirmed nothing in the live codebase or CI actually depends on either path: `git grep`/`Grep` across `backend/`, `rider-app/`, `driver-app/`, `admin-dashboard/`, `shared/`, `.github/workflows/`, and `.claude/` for `memory/` or `discovery/` turned up zero real hits — the only substring matches were false positives (`backend/utils/redis_client.py` and `backend/routes/admin/monitoring.py` both contain the phrase "Redis memory/keys" / "Redis memory/usage", unrelated to the directory). `.planning/STATE.md` references paths like `memory/project_rn_0_85_remaining_bugs.md`, but those are keys into a separate external "CMEM" session-memory timeline (the same file's "Key Facts" section says "Memory: access prior session work via `get_observations([IDs])` in the `$CMEM spinrvm` timeline") — not the repo's `memory/` directory. That's a different concept with a confusingly similar name; I did not touch it.

### Candidate approaches

**Approach A — doc-only fix scoped to the two living directory-status tables (CLAUDE.md + AGENTS.md).** Since the directories are already gone, the only real work left is correcting the two current, actively-read guidance docs that still claim otherwise: root `CLAUDE.md`'s "Claude-Adjacent Directories" table and `AGENTS.md`'s duplicate "Codex-Adjacent Directories" table (same rows, same wording, Codex-facing copy of the same doc). Reword the `memory/`/`discovery/` rows to say they were archived, with the date and the commit/PR that did it, so an agent skimming the table in the future sees closed history instead of an open TODO. Tradeoff: small, fast, low-risk diff — but it deliberately leaves several *dated* audit artifacts (`docs/claude-audit-2026-04-22.md`, `docs/claude-audit.json`, `docs/audit/15_TECH_STACK_AND_FILE_MAPPING.md`, `docs/audit/daily/2026-04-11.md`, and two `reports/audits/2026-07-22-*.md` files) still describing `memory/`/`discovery/` as open findings (`P2-001: OPEN` in the JSON).

**Approach B — same as A, plus retroactively mark the dated audit artifacts' `memory/`/`discovery/` findings as resolved.** Goes further: also edits `docs/claude-audit.json`'s `P2-001` status from `OPEN` to `RESOLVED` (and the prose equivalents in the `.md` audit files) so no artifact anywhere in the repo shows this as outstanding. Tradeoff: more thorough in the sense of zero remaining "OPEN" strings, but it means editing timestamped, point-in-time audit snapshots after the fact — those files are literally named by date (`2026-04-22`, `2026-04-11`, `2026-07-22`) and represent what was true *at that audit*, the same way a git commit or a Change Impact Log entry isn't edited after merge. It's also unclear whether `docs/claude-audit.json` is hand-maintained or regenerated by `audit-framework/` on its next run (I did not read that tooling to check) — editing it by hand risks being silently overwritten or, worse, drifting from whatever the generator expects.

### Recommendation

**Approach A.** The task's own instruction — "update CLAUDE.md's table (and any other doc that lists them as 'can be archived')" — reads naturally as: fix the docs that currently function as a live TODO list, not rewrite historical audit reports. `CLAUDE.md` and `AGENTS.md` are both read as current guidance on every session; a dated audit snapshot is not read that way and rewriting it after the fact would misrepresent what that audit actually found on the day it ran. This also keeps the change minimal and reversible, consistent with this being a `chore`-scope piece of work with no live-tested-surface involvement (GUARDRAILS.md's soft-stop list doesn't apply here — this touches no rides/dispatch/payments/auth/corporate/safety code).
