# Runbook — Backend Dependency Update

**Owner:** `backend` · **Cadence:** As needed + monthly CVE sweep
**Closes:** B-P1-10 (supply-chain hash-pinning of `requirements.txt`)

---

## Why This Matters

The backend container installs from `backend/requirements-locked.txt` with
`pip install --require-hashes`. Each line in that file pins an exact version
*and* SHA-256 hashes of every wheel/sdist permitted for that package. If a
PyPI mirror is compromised, a typosquat package is uploaded, or a maintainer
account is taken over, pip will refuse to install the tampered artifact and
the build fails loudly instead of shipping the malicious wheel.

This protection only works if the lockfile is regenerated **correctly** when
dependencies change. Hand-editing the locked file, or regenerating it without
`--generate-hashes`, defeats the gate. The CI guardrail
`security-posture-gate` verifies the hash count is ≥ 100; the steps below are
how you stay above that line.

---

## When to Regenerate

| Trigger | Action |
|---|---|
| Adding a new dependency | Add floor pin to `requirements.txt`, regenerate lockfile in same PR |
| Upgrading a dependency | Bump floor in `requirements.txt`, regenerate lockfile in same PR |
| `pip-audit` flags a CVE | Bump the affected package's floor, regenerate, verify CVE cleared |
| Monthly CVE sweep | Run `pip-audit -r backend/requirements-locked.txt` regardless of CI cadence |
| `requirements.txt` and lockfile drift (audit only one) | Regenerate immediately; do not deploy until they match |

Never edit `requirements-locked.txt` by hand. It is autogenerated.

---

## Prerequisites

- Python 3.12 (matches backend runtime)
- `pip-tools` (`pip install pip-tools`)
- Clean working tree on a feature branch (do not regenerate on `main`)

---

## Steps

### 1. Edit the source-of-truth

`backend/requirements.txt` carries floor pins (`>=`) for direct dependencies
only. Add or bump pins there:

```
# Example: bumping stripe from 15.0.1 → 15.4.0
- stripe>=15.0.1
+ stripe>=15.4.0
```

Group additions under the existing section comments (`# Payments`,
`# Authentication`, etc.) so the file stays scannable.

### 2. Regenerate the lockfile

```bash
cd backend
pip-compile --generate-hashes \
    --resolver=backtracking \
    --output-file=requirements-locked.txt \
    requirements.txt
```

This will:
- Resolve the full dependency graph
- Pin every package (direct + transitive) to an exact version
- Embed SHA-256 hashes for every wheel/sdist permitted

Expect the command to take 30 s – 2 min depending on cache state. The
resulting file is large (~3 k lines / ~130 packages today).

### 3. Verify the lockfile locally

```bash
# Count hashes — should be > 2,000 once the graph is healthy.
grep -c -- '--hash=sha256:' backend/requirements-locked.txt

# Dry-run the install in a clean venv to confirm pip accepts the file:
python3 -m venv /tmp/lockcheck && \
    /tmp/lockcheck/bin/pip install --require-hashes \
        -r backend/requirements-locked.txt
```

If pip rejects any hash, the lockfile is corrupt — re-run step 2.

### 4. Run the CVE scan against the new lockfile

```bash
pip install pip-audit
pip-audit -r backend/requirements-locked.txt --fail-on-vuln
```

Address any reported vulnerabilities by bumping the floor in `requirements.txt`
and re-running step 2. Do not merge with known fixable CVEs.

### 5. Commit both files together

`requirements.txt` and `requirements-locked.txt` must always move in the
same commit. A PR that updates one without the other will fail the CI
`security-posture-gate` hash-presence check (if the lockfile was deleted) or
deploy a container with stale dependencies (if only the lockfile changed).

```bash
git add backend/requirements.txt backend/requirements-locked.txt
git commit -m "build(deps): bump <package> to <version>"
```

### 6. Verify in CI

After pushing, confirm:
- `ci.yml › Python dependency CVE scan` passes (pip-audit clean)
- `ci-guardrails.yml › security-posture-gate › Verify requirements-locked.txt has SHA-256 hashes` passes
- `ci-guardrails.yml › security-posture-gate › Run pip-audit` passes
- The Docker image build (deploy-backend) succeeds — `pip install --require-hashes` would fail if any hash is wrong

## Recovery: Lockfile and Source Drift

Symptom: `pip install --require-hashes -r requirements-locked.txt` succeeds
locally but the container build fails with
`Hashes are required in --require-hashes mode`.

Cause: someone added a package to `requirements.txt` without regenerating the
lockfile.

Fix:
1. Run step 2 from the same commit.
2. Verify `git diff backend/requirements-locked.txt` shows the new package
   with its hashes.
3. Commit and push.

---

## Recovery: pip-compile Resolution Fails

Symptom: `pip-compile` errors with "Could not find a version that satisfies".

Cause: floor pins in `requirements.txt` are mutually incompatible (typically
two direct deps that both pin a transitive dep to incompatible ranges).

Fix:
1. Read the resolver error — it names the conflicting packages.
2. Either relax the floor on the older direct dep, or pin the transitive
   dep explicitly in the `# Additional dependencies` section at the bottom
   of `requirements.txt`.
3. Re-run step 2.

---

## Notes

- The lockfile is generated against Python 3.12 (the backend runtime). Do
  not regenerate from a 3.11 / 3.13 venv — the wheel set will diverge.
- `pip-compile` honors `requirements.txt` ordering when emitting the lockfile
  but adds transitive deps alphabetically. Don't reorder the lockfile by
  hand to "tidy" it; the regeneration is canonical.
- Mobile apps (`rider-app`, `driver-app`) and `admin-dashboard` use
  `yarn.lock` / `package-lock.json` for the equivalent guarantee. This
  runbook covers the backend only.
