# Decisions: Archive the stale memory/ and discovery/ directories

## Decision: Treat the directory-removal step as already satisfied, not a no-op to skip silently
**Stage:** Stage 1-2 (Ideation & Requirements)
**What was decided:** `memory/` and `discovery/` were already deleted from the working tree on 2026-05-05 in commit `223ec89b0` (PR #451), months before this task was assigned. Rather than treating "nothing to remove" as reason to skip the removal criterion, it's kept as an explicit, verified acceptance criterion (files 8/criterion 1) so a mechanical check still confirms the state is correct, instead of assuming CLAUDE.md's claim was accurate without checking.
**Why:** CLAUDE.md's own table was the thing that turned out to be wrong (claiming the dirs still exist and need archiving) — trusting it at face value instead of checking git history would have meant "removing" directories that were already gone, or worse, not noticing the real gap (the doc, not the filesystem) was the actual problem.
**Alternatives considered:** Skip verification and just edit the doc, assuming the table was accurate about the dirs still being present. Rejected — GUARDRAILS.md requires stating what was and wasn't checked, and this is exactly the kind of claim ("still present, still stale") that's cheap to verify and expensive to get wrong silently.
**Reversible?** Yes — this is a documentation/history-checking decision, not a code change; no rollback mechanism needed.

## Decision: Leave dated audit-report snapshots (docs/claude-audit-2026-04-22.md, docs/claude-audit.json, docs/audit/15_TECH_STACK_AND_FILE_MAPPING.md, docs/audit/daily/2026-04-11.md, reports/audits/2026-07-22-*.md) unedited even though they list memory/discovery as open findings
**Stage:** Stage 1-2 (Ideation & Requirements)
**What was decided:** Only the two currently-live guidance docs (root `CLAUDE.md` and `AGENTS.md`) get their `memory/`/`discovery/` rows corrected. The historical, date-named audit artifacts that also mention these directories as open/archive-candidate findings (including `docs/claude-audit.json`'s `P2-001: OPEN`) are left as-is.
**Why:** Those files are point-in-time snapshots — named by the date of the audit that produced them — not living trackers. Rewriting a dated report's findings after the fact misrepresents what that audit actually found on the day it ran, the same way CLAUDE.md itself treats a merged Change Impact Log entry or a git commit as immutable history rather than something to edit later. It's also unverified whether `docs/claude-audit.json` is hand-maintained or regenerated by `audit-framework/` tooling on its next run; editing it by hand risks silent overwrite or drift from whatever the generator expects, and I did not read that tooling to find out.
**Alternatives considered:** Edit all of them to `RESOLVED`/closed for a fully "clean" search result across the repo. Rejected as the more thorough-looking but actually riskier option — it touches files well outside what the task named (CLAUDE.md's table), for uncertain benefit, and blurs the line between "current guidance" and "historical record" that this repo otherwise keeps distinct (dated filenames, `docs/change-log/YYYY-MM-DD-*.md` convention, etc).
**Reversible?** Yes — if a human decides the audit snapshots should be marked resolved after all, that's a follow-up doc edit, not a code or data change.

## Decision: Treat `.planning/STATE.md`'s `memory/project_*.md` references as a different, unrelated concept and leave them untouched
**Stage:** Stage 1-2 (Ideation & Requirements)
**What was decided:** `.planning/STATE.md` references paths like `memory/project_rn_0_85_remaining_bugs.md` and `memory/reference_ci_failures_pattern.md`. These are not treated as references to the repo's `memory/` directory (which never held files like this — it only ever had `.gitkeep`), and are left out of this run's scope.
**Why:** The same file's "Key Facts for Next Session" section explains these as keys into an external session-memory tool ("Memory: access prior session work via `get_observations([IDs])` in the `$CMEM spinrvm` timeline") — a naming convention that happens to reuse the word "memory," not a claim that files exist under the repo's top-level `memory/` directory. Treating it as in-scope would risk "fixing" a reference that was never broken.
**Alternatives considered:** Flag `.planning/STATE.md` as needing the same correction as CLAUDE.md. Rejected once the file's own text clarified the naming was unrelated — confirmed by reading the surrounding context rather than pattern-matching on the string `memory/` alone.
**Reversible?** Yes — no change was made, so there's nothing to revert; a future run can still choose to touch this file if the CMEM-naming read turns out to be wrong.
