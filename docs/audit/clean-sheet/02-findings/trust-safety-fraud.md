### TSF-001 — Only documented SOS on-call runbook describes a system that does not exist in code
- Hierarchy: L2 Safety, Trust & Fraud › L3 SOS / emergency › L4 on-call response › L5 who responds at 3 a.m.
- Severity: HIGH   Priority score: S×B×L = high (life-safety domain; likelihood is not rare — it's every real SOS today)
- Status: VERIFIED   Existing item: new (not found under any of the checked duplicate-id ranges; closest relative is ACTION_ITEMS B15(b), which built the webhook this runbook doesn't know about)
- Adversary: regulator / plaintiff's lawyer (a post-incident review that pulls this runbook as "the documented process" finds it doesn't match what happened)
- Evidence: `docs/runbooks/sos-incident.md:18-35,41` vs `backend/routes/rides/safety.py:202-317`, `backend/utils/safety_paging.py`, `.claude/context/domain-safety.md:31-45`
- What happens (plain language): the only runbook a real on-call responder would open during an SOS says the system writes to a `sos_events` table, and that the responder gets **SMS'd on a phone number** (primary + backup) within a documented 2-minute-ack SLA. Neither exists: the actual table is `safety_incidents`, and the actual paging mechanism (`page_sos_on_call` → a PagerDuty-Events-API-shaped webhook) is **unconfigured in every environment** (`sos_paging_webhook_url` unset), so it silently no-ops (logs at `debug`, returns `False`, never raises). A responder following this runbook literally during a real incident would query a table that doesn't exist and wait for a page that will never arrive.
- Root cause: the runbook was written to describe an intended architecture (or an even-earlier one) and was never updated when the actual implementation (`safety_incidents` + dark-by-default webhook, per ACTION_ITEMS B15(b)) shipped. This is the same doc-vs-code drift class W0-SUMMARY flags generally (bullet 4), but landing on the one document where staleness has the highest consequence.
- Recommendation: rewrite `docs/runbooks/sos-incident.md`'s "SOS Event Flow" and "On-Call Responder Flow" sections to match the real table (`safety_incidents`), the real channels (admin WS broadcast, safety-team email, `logger.critical`, Zoho urgent ticket, and the dark `page_sos_on_call` webhook), and to state plainly that **no automated page currently fires anywhere** until `sos_paging_webhook_url` is configured. Separately — and this is the actual open safety gap, not just a doc fix — get a real on-call phone/PagerDuty/OpsGenie target configured, since today's answer to "who responds at 3 a.m." is "nobody is automatically paged; response depends on someone watching the admin dashboard, the safety-team inbox, or Sentry/log alerts happening to be staffed." Alternative considered: leave the runbook as an aspirational target and treat the webhook as the thing to build toward it — rejected, because a stale runbook that's wrong about *which table exists* is actively dangerous during a real incident, independent of whether paging gets built; the doc needs fixing regardless of the staffing decision.
- Blast radius: documentation only for the fix; the underlying paging gap is `backend/utils/safety_paging.py` + `app_settings.sos_paging_webhook_url`, already isolated (re-confirms A8's framing, but A8 treated this as a "known, documented, not a live gap" WARNING — this pass disagrees with "not a live gap" specifically because the *documentation* itself is actively wrong, not just the paging feature being unconfigured).
- Rollout: doc fix is immediate, no flag. Paging-target configuration is an ops/business decision (who is on-call, what tool), not a code change — same "human-only question" A8 already carried forward, restated here because it's now tied to a bigger finding.
- Verification to close: on-call runbook accurately names `safety_incidents`, lists the 5 real notification channels in `trigger_emergency`, and explicitly states paging is dark until configured; separately, confirm with a human whether a real on-call phone/PagerDuty account now exists (per W0-SUMMARY's carried-forward human-only question on `ALERT_WEBHOOK_URL`, which is the general-loop equivalent of this same open question).

### TSF-002 — Driver–rider collusion on fake rides: no detection signal exists
- Hierarchy: L2 Safety, Trust & Fraud › L3 Fraud detection (S-safety-05) › L4 collusion › L5 repeated same-pair rides for incentive farming
- Severity: MEDIUM-HIGH   Priority score: S×B×L = medium-high (money-shaped: quest/incentive payouts and cancellation-fee farming both ride on this same undetected surface)
- Status: VERIFIED   Existing item: closes A8 SAFETY-05's UNKNOWN (traceability.csv row 1777, `S-safety-05` is itself marked `gap` — "As trust&safety, referral/promo abuse and GPS spoofing are detected" has **zero** mapped code, confirmed by the traceability row's own `NONE`/`gap` entries)
- Adversary: fraudulent driver + fraudulent rider acting together (fake trips to farm quest/incentive bonuses, or a driver's own second account riding with them)
- Evidence: `grep -rn "collusion\|same_device\|shared_payment_method\|ride_count_anomaly" backend/services backend/utils` → zero hits; `.claude/agents/spinr-fraud-auditor.md` documents 4 fraud surfaces (referral velocity, promo stacking, device/phone reuse, GPS plausibility) and collusion detection is not one of them — this is a genuine blind spot in both the code and the agent's own charter, not just an unimplemented check the agent already tracks
- What happens: a driver and rider (real accounts, or a driver's alt account) can repeatedly "complete" short/fake trips to trigger quest bonuses (`routes/quests.py`), driver incentives (`routes/admin/incentives.py`), or referral-completion thresholds, with nothing in the codebase comparing device IDs, payment methods, locations, or the raw frequency of one driver/rider pair repeating.
- Root cause: never built — `spinr-fraud-auditor.md`'s own 4-surface scope doesn't include this pattern, so it's not merely an implementation gap under an existing charter, it's a charter gap.
- Recommendation: add a same-pair ride-frequency signal (e.g. N rides between the same driver_id/rider_id within a rolling window with GPS teleport-consistency and quest/incentive-claim correlation) as a **detection**, not prevention, layer — false positives are common in low-density service areas (Regina/Saskatoon are not NYC; a regular commuter route pairing the same driver/rider repeatedly is plausible and legitimate) so this should feed an admin review queue, not an auto-block. Alternative considered: block same-pair rides outright above a threshold — rejected, high false-positive risk in a low-driver-density market is exactly the kind of "sounds good, should NOT build as an auto-block" case greenfield-extensions §11 asks for.
- Blast radius: new code only; no existing table/column changes needed to start (correlate existing `rides`, `ride_offers`, quest/incentive claim tables).
- Rollout: new admin-only detection job/report, no rider/driver-facing change, no flag needed for a read-only admin signal.
- Verification to close: a test that seeds N repeated same-pair completed rides with a quest claim and confirms the new signal fires; product sign-off on the review-queue threshold.

### TSF-003 — Cancellation-fee farming: no detection signal exists
- Hierarchy: L2 Safety, Trust & Fraud › L3 Fraud detection › L4 cancellation-fee abuse › L5 driver waits past the free-cancel window then collects the fee repeatedly
- Severity: MEDIUM   Priority score: S×B×L = medium (bounded dollar impact per incident, `cancellation_fee_driver` default $4.00, but compounds)
- Status: VERIFIED   Existing item: same `S-safety-05` gap row as TSF-002
- Adversary: fraudulent driver (accepts, waits out `free_cancel_window_seconds`, then the rider — possibly a real one frustrated by the wait, possibly a colluding one — cancels and the driver collects `cancellation_fee_driver`)
- Evidence: `backend/services/cancellation_service.py` (full file read) — `calculate_cancellation_fee`/`calculate_noshow_fee`/`pay_driver_cancellation_fee` compute and pay the fee per-ride with no query against the driver's recent cancellation-fee count, no per-driver velocity cap, no flag for "accepted then let the free window lapse" as a repeated pattern
- What happens: nothing currently distinguishes a driver who occasionally benefits from a genuine rider cancellation from one whose earnings are structurally built on accept-then-stall.
- Root cause: `cancellation_service.py` was built (correctly) as a pure fee-calculation module with no fraud-signal responsibility — this is a reasonable single-responsibility boundary, but nothing else in the codebase picked up the detection half.
- Recommendation: an admin-facing metric/report — cancellation-fee earnings as a % of a driver's total earnings, or fee-triggering cancellations per 100 accepted rides — flagged for review above a threshold. Alternative considered: automatically capping or clawing back a driver's cancellation-fee earnings above a threshold — rejected as a first step; a false positive here (e.g. a driver working an underserved area with genuinely long waits) directly reduces a contractor's earnings, which needs human review before any automated penalty, consistent with CLAUDE.md's driver-classification "no control-of-work" guardrail.
