# ADR-008: Two report modes — Spinr-branded vs. fixed regulator format

**Date:** 2026-07-28
**Status:** Accepted

---

## Context

Spinr's admin panel generates two categories of exported documents that look
similar at a glance (both are PDF/tabular exports triggered from an admin
button) but have fundamentally different constraints:

1. **Regulator-owned forms** — SGI's D00032 (Passenger for Hire – Driver
   Details) and D00033 (Transportation Network Company – Vehicle Details),
   generated by `services/data_transfer/sgi_form_filler.py`. These are
   AcroForm PDFs supplied by the regulator; the filled document itself is
   what gets submitted to SGI. The layout is not Spinr's to change.
2. **Spinr's own reports** — GST/PST tax remittance and the driver
   insurance-period regulatory audit export (`routes/admin/compliance.py`,
   shipped in PR #2650), plus the existing DSAR lookup. Nothing external
   prescribes their layout; CRA's remittance filing process, for example,
   has no required document format — only the numbers need to be correct.

The compliance reporting module's initial build (PR #2650) needed a shared
PDF/Excel/Word/CSV rendering layer (`backend/utils/report_branding.py`) for
its two new report types. Before adding a third report family (fixed vs.
branded) to a growing admin panel, this decision needed to be made explicit
and enforced in code — not left as tribal knowledge — because getting it
wrong has real consequences: applying Spinr's logo/red header band to a
filled SGI D00032 would alter a document being submitted to a provincial
regulator.

## Options Considered

| Option | Rejected / chosen because |
|---|---|
| **Brand everything, including SGI forms** | Rejected outright — SGI's AcroForm PDFs have a fixed, regulator-defined field layout. Overlaying Spinr branding (even just a header band) risks altering a document Spinr does not own the format of, and could jeopardize the form's validity with the regulator. Never implement this. |
| **One shared renderer with a `branded: bool` flag threaded through every call site** | Rejected — a boolean flag at each call site is exactly the kind of thing that gets silently flipped wrong on a copy-pasted new report (CLAUDE.md's own guidance: prefer additive, hard-to-misuse patterns over parameters that are easy to get wrong). A future engineer adding a ninth report type could pass `branded=True` for a fixed-format form by mistake, with no compiler or reviewer catching it. |
| **Two entirely separate, unrelated code paths with no shared registry** (chosen direction, refined below) | Correct instinct — fixed-format and branded reports *should* never share a rendering call site — but needed one more piece: a single lookup table so "which mode does report X use" is answered in one place, not re-derived by every caller from the report's name. |
| **`REPORT_FORMAT_REGISTRY` — a typed, name-keyed lookup in `report_branding.py`, with `report_mode()` raising `KeyError` on an unregistered name** (chosen) | Makes the two code paths genuinely separate (branded helpers in `report_branding.py`; fixed-format filling stays in `sgi_form_filler.py` and never imports `report_branding.py`'s branded helpers) while still giving a single, greppable source of truth for "which report is which." Critically, an **unregistered report type raises loudly** instead of silently defaulting to either mode — the failure mode for a forgotten registration is an immediate `KeyError` at development time, not a mis-rendered regulatory document discovered after the fact. |

## Decision

`backend/utils/report_branding.py` defines `REPORT_FORMAT_REGISTRY: dict[str,
ReportRegistration]`, mapping every compliance/admin report type to exactly
one of two modes:

```python
ReportMode = Literal["branded", "fixed_format"]

REPORT_FORMAT_REGISTRY: dict[str, ReportRegistration] = {
    "sgi_driver_details": {"mode": "fixed_format", ...},
    "sgi_vehicle_details": {"mode": "fixed_format", ...},
    "gst_pst_remittance": {"mode": "branded", ...},
    "insurance_period_audit": {"mode": "branded", ...},
    "dsar_lookup": {"mode": "branded", ...},
}
```

Rules that follow from this:

- **`fixed_format` reports never call `report_branding.py`'s branded
  helpers** (`new_branded_pdf`, `new_branded_workbook`,
  `new_branded_document`). They are generated exclusively by
  `services/data_transfer/sgi_form_filler.py`, which fills the regulator's
  own AcroForm PDF fields and changes nothing about the visual layout.
- **`branded` reports never touch `sgi_form_filler.py`** and always render
  through the shared helpers in `report_branding.py` — logo, brand color
  (`BRAND_RGB`/`BRAND_HEX`), consistent header/footer, across all four
  output formats (PDF/CSV/XLSX/DOCX).
- **A report type not in the registry is a bug, not a default.**
  `report_mode()` raises `KeyError` for an unregistered name rather than
  guessing — enforced by `TestReportFormatRegistry.test_unregistered_report_type_raises`
  in `backend/tests/test_report_branding.py`. Adding a ninth report type
  that forgets to register itself fails fast during development instead of
  reaching production in the wrong mode.
- **The registry is the only place "which mode" is decided.** No call site
  in `routes/admin/compliance.py`, `routes/admin/sgi_forms.py`, or any
  future admin route branches on a report-name string to decide branding —
  they either import from the branded helpers or from `sgi_form_filler.py`,
  and the registry documents (for humans and for tests) which one is
  correct for a given name.

## Consequences

**Positive:**
- Structurally impossible for a future report to accidentally end up
  Spinr-branded when it's a regulator's fixed form, or vice versa — the two
  rendering code paths don't share call sites, and the registry is the
  single documented cross-reference, checked by a test that would fail if
  a new report type shipped unregistered.
- Extends cleanly to a future province's equivalent of SGI's forms: add one
  `fixed_format` registry entry, no changes to the branded helpers.
- The registry doubles as living documentation — `report_mode(x)` answers
  "is this Spinr's to restyle?" without reading either renderer's source.

**Negative / trade-offs:**
- One more place to remember to update when a new report type is added
  (the registry itself). Mitigated by the raise-on-unregistered test, which
  makes forgetting a build/test-time failure rather than a silent bug.
- The registry doesn't (and shouldn't) enforce *which* renderer a route
  actually calls — a route could still import the wrong helper set despite
  a correct registry entry. This is a naming/lookup convention, not a type
  system guarantee; `report_mode()` is documentation-as-code, not a compiler
  check. Acceptable given Python's dynamic typing throughout this codebase,
  and the existing test coverage on both report families' output shape.
