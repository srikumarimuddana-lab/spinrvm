SECTION 14B: FLATLIST & LIST VIRTUALISATION
================================================================================

[14-7] CRITICAL | Math.random() Used as FlatList Key
File: driver-app/app/driver/rides.tsx:284
Finding: keyExtractor={(item) => item.id || Math.random().toString()}
This is a CRITICAL performance issue. Every time the parent component re-renders,
Math.random() generates a new key for items without an id, forcing React to unmount
and remount the entire list, re-running render logic, resetting internal state of
child components, and causing severe frame drops. This is especially bad during:
- Pull-to-refresh (list re-renders while data refreshes)
- Filter changes (state change triggers re-render)
- Any parent state change (unrelated to the list)
Users will see jank, animations will stutter, and old state will be lost.
Fix: Ensure every ride object has a stable, unique id field from the backend.
If some items lack an id, use the array index as a fallback ONLY if the list
is never reordered, or generate a stable hash. Replace with:
  keyExtractor={(item, index) => item.id ? String(item.id) : `ride_${index}`}
This guarantees the same key for the same position across re-renders.

[14-8] MEDIUM | FlatList Missing Virtualization Optimization Props
File: driver-app/app/driver/rides.tsx:281-301
Finding: FlatList has no initialNumToRender, maxToRenderPerBatch, windowSize, or
getItemLayout props. This means:
- Every item is rendered eagerly when the list mounts (slow on load)
- Rendering batch size defaults to ~10 items, which can cause
  visible gaps on fast scrolls
- No fixed-height layout, so the scrollbar can't scroll efficiently
- Large lists (50+ items) will have noticeable stutter on lower-end devices
Fix: Add props:
  initialNumToRender={10}
  maxToRenderPerBatch={20}
  windowSize={10}
  removeClippedSubviews={true}
  getItemLayout={(data, index) => ({
    length: 180, // Approximate height of a ride card in pixels
    offset: 180 * index,
    index,
  })}
Measure the actual height of a rendered ride card and adjust the '180' value.

[14-9] LOW | removeClippedSubviews Not Enabled
File: driver-app/app/driver/rides.tsx:281-301
Finding: removeClippedSubviews is not set (defaults to platform default, often false).
When enabled, off-screen items are unloaded from the native view hierarchy, saving
memory and improving scroll smoothness on large lists.
Fix: Add removeClippedSubviews={true} to the FlatList. This is safe for most
layouts and provides a noticeable smoothness boost on older Android devices.

SECTION 14D: BACKEND QUERY PERFORMANCE
================================================================================

[14-14] CRITICAL | Driver Rating Calculation Loads 1000 Ride Records
File: backend/routes/rides.py:1249
Finding: driver_rides = await db_supabase.get_rows("rides", {"driver_id": driver_id}, limit=1000)
This fetches up to 1000 rides into memory every time a driver is rated. A busy driver
with 2+ years of history will hit this limit. The code then loops through all 1000
records in Python to calculate average rating (line 1250-1253), which is inefficient.
- Memory: 1000 ride records × ~2KB each = 2MB per rating calculation (not huge, but wasteful)
- CPU: Python loop over 1000 records on the request thread (blocks other requests)
- Latency: If there are 1000 rated rides, this could take 100-500ms
On a busy system with concurrent rating updates, this serializes the rating calculation
and slows down the entire endpoint.
Fix: Use a database-side aggregation instead:
  SELECT AVG(driver_rating) FROM rides WHERE driver_id = $1 AND driver_rating IS NOT NULL;
  UPDATE drivers SET rating = (SELECT AVG(driver_rating) ...) WHERE id = $1;
This eliminates the limit=1000 fetches and computes the aggregate in SQL. For even
better performance, maintain a rides_by_driver_stats table updated via trigger on
ride inserts/updates.

[14-15] MEDIUM | No Composite Index on rides(driver_id, created_at)
File: backend/migrations/ (all migration files scanned)
Finding: There is no CREATE INDEX on rides(driver_id, created_at). The rides table
is queried by driver_id in at least two places:
  - Line 169: get_rows("rides", {"driver_id": {"$ne": None}}, sort=[("created_at", -1)], limit=1)
  - Line 1249: get_rows("rides", {"driver_id": driver_id}, limit=1000)
Without an index, these queries do a full table scan. As the rides table grows (1M+
records), these scans will slow down. The sort by created_at DESC further requires
a sequential sort unless the index includes created_at.
Fix: Add to a migration file:
  CREATE INDEX IF NOT EXISTS idx_rides_driver_created ON rides(driver_id, created_at DESC);
This allows both queries to use the index for fast lookup + sort.

[14-16] MEDIUM | Rides Estimate Endpoint Loads 500 Drivers
File: backend/routes/rides.py:131-139
Finding: get_rows("drivers", {...}, limit=500) is used to find candidate drivers
for ride matching. In a city with 500+ drivers online, this will only consider the
first 500 returned by the database, potentially missing nearby drivers if they're
not in the first 500 rows.
Fix: Either:
  1. Increase limit to 1000+ if your city has many drivers, OR
  2. Push the distance filter (10km radius) to the database query using PostGIS,
     so you fetch only nearby drivers instead of all 500 and filtering in Python
The current approach is safe for small fleets but may underserve high-traffic cities.

[14-17] MEDIUM | Rider History Query Loads 200 Rides Without Pagination
File: backend/routes/rides.py:786-792
Finding: get_rows("rides", {"rider_id": current_user["id"]}, limit=200)
This endpoint has no pagination parameters (no offset, no cursor). A rider can only
see their last 200 rides. If they have 300 rides, the older 100 are invisible. Also,
loading 200 rides into memory every request is wasteful if only 10 are displayed.
Fix: Add pagination support:
  @router.get("/rides/history")
  async def get_rider_ride_history(skip: int = 0, limit: int = 50):
      all_rides = await db_supabase.get_rows(
          "rides", {"rider_id": ...}, limit=limit, offset=skip, sort=[(...)])
      return {..., "total": count_rides, "has_more": (skip + limit) < count_rides}
This allows the client to fetch rides in batches of 50.
