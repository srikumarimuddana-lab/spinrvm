## Decision: Frame the finding as a verifiability/drift gap, not a broken-access-control gap
**Stage:** Ideation & Requirements
**What was decided:** After tracing the full KYB upload/submit/view flow (portal routes, staff routes, `corporate_repo.py` storage helpers, the backend's service-role Supabase client, and the admin-dashboard's browser-side upload code), the application-layer authorization was found to already be correctly scoped — `require_company_admin` restricts the company portal per company, the portal never receives the storage key, staff reads are proxied server-side with the service-role client, and the tenancy/path-traversal guard already exists and is tested on both submission endpoints. The actual gap that survives scrutiny is that the `kyb-documents` bucket's own configuration (private flag, size/type limits, no-RLS-for-authenticated/anon posture) is never expressed in source control — it's a manually-created bucket per `backend/docs/STORAGE_BUCKETS.md`, unlike every other recently-added bucket in this repo (202, 236, 339, 340), which are all migration-provisioned. The recommendation is therefore to close that specific gap (migration + one missing regression test), not to rewrite any authorization logic.
**Why:** CLAUDE.md is explicit that a "not confirmed" finding is a legitimate outcome and that a fix must not be manufactured for a problem that doesn't exist. Treating this as "access control is broken, patch the routes" would have been guessing in the wrong direction and would risk introducing a real behavior change (a live-tested, corporate-surface change) to fix a bug that isn't there. Treating it as "nothing to do at all" would have ignored the concrete, checkable gap that does exist (no source-controlled bucket posture, one untested denial path) and would leave the next audit exactly where B12 left this one.
**Alternative(s) considered:** (1) Assume the storage bucket is misconfigured and write a defensive RLS-policy migration regardless — rejected, this would be guessing at a problem with no evidence, and RLS policies on `storage.objects` are moot anyway since the backend exclusively uses the service-role key which bypasses RLS; the real protection is the FastAPI route guards. (2) Do nothing and just restate B12's "not confirmed" wording verbatim — rejected as under-delivering: the investigation did surface a concrete, fixable, low-risk gap (the missing migration + missing cross-tenant test) that closes real uncertainty without inventing a fake bug.
**Reversible?** Yes — this is a framing/recommendation decision, not a code change. If a later stage (e.g. Security) finds something this pass missed, the recommended migration and tests can be extended or the framing revisited without having shipped anything destructive.

## Decision: Do not attempt to inspect the live Supabase project's actual bucket configuration
**Stage:** Ideation & Requirements
**What was decided:** This pass reasoned entirely from source code and repo documentation (`backend/docs/STORAGE_BUCKETS.md`) about the `kyb-documents` bucket's intended posture, and explicitly did not use the `mcp__Supabase__*` tools (list_projects / execute_sql / get_advisors, etc.) to connect to the live Supabase project and read its actual current `storage.buckets`/`storage.objects` RLS state.
**Why:** `agents/GUARDRAILS.md`'s hard stops say this pipeline "cannot see or move real user PII" and "cannot apply a migration to production" — while read-only inspection of bucket metadata isn't itself a PII or migration action, connecting to a live production-adjacent Supabase project from an Ideation/Requirements stage, with credentials/scope this run was never explicitly given for that purpose, is exactly the kind of judgment call GUARDRAILS.md says to escalate rather than guess. It's also simply out of scope for what Stage 1-2 (Ideation & Requirements) is meant to produce — verifying a fix's actual effect against the live system belongs to a later stage (Development/QA/Security) with an explicitly scoped, authorized connection, not to the stage that's proposing candidate approaches.
**Alternative(s) considered:** Connect via `mcp__Supabase__list_projects`/`get_advisors`/`execute_sql` now to settle the question definitively before writing acceptance criteria. Rejected for this stage: even a read-only check would require picking (and trusting) a specific project as "the" Spinr production project without an explicit human instruction to do so, and the payoff (settling one input to the requirements) doesn't justify reaching into a live environment from an ideation pass. This is flagged instead as an explicit unverified item and as part of the acceptance criteria for a later stage to check with proper authorization.
**Reversible?** Yes — a later stage can make this call differently (e.g., Architecture or Security stage, with explicit human sign-off per the Change Review gate this run already requires) and connect to Supabase directly to confirm live bucket state; nothing here forecloses that.

## Decision: Extend `test_corporate_company_kyb.py` rather than create a dedicated cross-tenant test file
**Stage:** Plan & Design / Architecture
**What was decided:** The four new regression tests (cross-tenant 403 on `/kyb/upload-url` and `/kyb/submit`; member-role 403 on the same two endpoints) will be added to the existing `backend/tests/test_corporate_company_kyb.py` rather than a new file, even though the acceptance criteria explicitly allowed either.
**Why:** That file already defines the exact fixtures the new tests need (`rider_override`, `_admin_guard()`, `_company()`) and already contains the closest-related coverage (member-role 403 on `GET /kyb`, tenancy/traversal 403 on `/kyb/submit`) that the new tests extend the pattern of. A new file would either duplicate those helpers or import them across files, and CLAUDE.md's simplicity-first principle ("no speculative... configurability that wasn't asked for") argues against adding a second test file for four tests that share 100% of their setup with tests already in the first one.
**Alternative(s) considered:** A new dedicated file (e.g. `test_corporate_company_kyb_tenancy.py`) — rejected as unnecessary indirection for this size of addition; would make sense only if the cross-tenant/role-boundary tests were expected to grow substantially beyond KYB (they're not — this run is scoped to KYB only).
**Reversible?** Yes — moving four test functions to a new file later is a pure refactor with no behavioral effect either way.

## Decision: Flag the migration's rollback comment as needing bucket-specific wording, not a copy of migration 340's
**Stage:** Plan & Design / Architecture
**What was decided:** Migration 340 (`safety-evidence`) safely wrote a rollback comment saying `DROP TABLE` / `DELETE FROM storage.objects/buckets` because that bucket was net-new — nothing existed to lose. `kyb-documents` already exists and has been written to by the running application since before this repo tracked it (per `backend/docs/STORAGE_BUCKETS.md`'s "create it once via the dashboard... the app writes to it at runtime" framing) — companies may have real KYB documents in it right now. This stage decided **not** to write the migration text itself (that's Stage 5), but to explicitly flag, in `progress-report.md` and `challenges-and-issues.md`, that Stage 5 must not mechanically copy 340's rollback block — a `DROP`/`DELETE FROM storage.objects` rollback here would destroy live corporate verification documents, which is a materially different risk than 340 ever carried.
**Why:** GUARDRAILS.md's "things the pipeline will not pretend it verified" rule and CLAUDE.md's rollback-plan requirement ("how to revert without a second deploy... a `git revert` is not a rollback plan for anything already applied to live data") both point the same direction: silently pattern-matching migration 340's rollback text onto a bucket with different data-safety characteristics would produce a rollback plan that reads as safe but isn't. Catching this at Design/Architecture time (before the migration text is written) is cheaper than catching it at Change Review.
**Alternative(s) considered:** Let Stage 5 discover this on its own without a flag here — rejected; the whole point of a Design stage reading the reference pattern before Development is to catch exactly this kind of "looks like the same shape, isn't" mismatch before it's written, not after.
**Reversible?** Yes — this is a note to a later stage, not a code change; Stage 5 can act on it however it judges best, including asking a human if the correct rollback wording is unclear.

## Decision: Write a config-only rollback (UPDATE, not DROP/DELETE) for migration 354
**Stage:** Development
**What was decided:** Resolving the flag Stage 3-4 raised (see the decision above), the rollback comment in `backend/migrations/354_kyb_documents_bucket_private.sql` does not offer `DROP TABLE`, `DELETE FROM storage.objects WHERE bucket_id = 'kyb-documents'`, or `DELETE FROM storage.buckets WHERE id = 'kyb-documents'` as options at all — the only rollback given is `UPDATE storage.buckets SET public = false WHERE id = 'kyb-documents'` plus `NOTIFY pgrst, 'reload schema'`, with an explicit inline warning against the destructive alternatives.
**Why:** This migration only ever asserts bucket *metadata* (`public`, `file_size_limit`, `allowed_mime_types`); it never uploads, moves, or reads an object. The bucket predates this repo's tracking of it and may already hold live corporate KYB documents (incorporation records, business licenses) uploaded by real companies. Offering a `DROP`/`DELETE` rollback option — even framed as "only if nothing depends on it" the way 340 could safely do for its net-new bucket — creates a plausible-looking path to destroying live customer data that this migration has no authority over and no way to distinguish from "safe to run." CLAUDE.md's rollback-plan requirement is explicit that a destructive option on live data is not a real rollback plan; giving only the non-destructive option removes the temptation entirely rather than relying on a reader to notice the warning.
**Alternative(s) considered:** (1) Copy 340's rollback verbatim, as a literal reading of "mirror migration 340" might suggest — rejected, this is exactly the mismatch Stage 3-4 flagged before any code existed. (2) Offer both the UPDATE and a heavily-caveated DROP/DELETE option "for completeness" — rejected as unnecessary: nothing about this migration or its forward direction ever needs the bucket or its objects removed, so there is no legitimate rollback scenario that requires them; including the option anyway only adds a footgun with no corresponding benefit. (3) Leave the rollback comment more generic/vague to avoid asserting a specific value for `public`'s prior state — rejected; `false` is the only value this repo has ever asserted for this bucket (there is no earlier migration to diff against), so stating it directly is accurate, not presumptuous.
**Reversible?** Yes — this is comment text, not executable schema; if a future stage determines the bucket genuinely needs to be dropped (e.g. the feature is fully decommissioned and all documents are confirmed migrated/deleted through the proper PIPEDA retention process), that would be its own new migration with its own justification, not a retroactive edit to this one's rollback comment.
