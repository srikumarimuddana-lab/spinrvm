## §2 Hypothesis tests

Each hypothesis is tested against what the code does today, then given a verdict from {adopt, adopt-incrementally, reject, insufficient evidence}, with cost (S/M/L), risk on the live product, and the smallest incremental first step.

### H1 — One ride state-machine module with an append-only event log

- **What exists (VERIFIED).** Two canonical guards (`_require_ride_in_state` for driver-owned transitions, `_require_ride_in_state_rider` for rider-owned) plus an atomic CAS `{status: expected}` filter or a single-transaction RPC at every multi-actor write site; `dispatch.md` §4 tabulates ~13 production-reachable `rides.status` write sites and found none unguarded. `RideStatus` is a single enum with eight values and no subclass. **There is no ride event-log table**; "what happened to this ride" is reconstructed from `audit_logs`, WS log lines and the insurance-period rows. Side effects (WS emit to both keys, metric, insurance-period call) are re-implemented per site: DISPATCH-001 is a forgotten rider WS emit at one site; `dispatch.md` §4 marks the `/start` dev path "metric missing" and the completion path's driver-key emit "not verified"; HIST-010 is the same omission for insurance periods, fixed by moving the write *into* the claim RPC (#5748).
- **Verdict: ADOPT-INCREMENTALLY** — one transition helper and an append-only `ride_status_events` table, **not** an event-sourced rebuild and **not** the external prompt's 11-state machine (`greenfield-extensions.md` §13 already declined it; `dispatch.md` §6 concurs: MODIFY, not REPLACE). `rides.status` remains the source of truth; the event table is an append-only *record* of every transition (actor, from, to, reason, request id, ts), the same pattern the codebase already trusts for `driver_insurance_periods` (migration 64's append-only trigger, `trust-safety-fraud.md` §f).
- **Cost:** M (one migration + one helper + ~13 site migrations of ≤ 3 files each). **Risk on live product:** low if shadow-mode first (the `matching.py` `_shadow_ids`/`spinr_dispatch_admission_shadow_total` precedent, `dispatch.md` §6); medium if any site skips shadow. **Reversibility:** high — the table is additive, the helper is dark-flagged per the `driver_availability_v2_enabled` precedent.
- **What it buys.** Structurally closes the DISPATCH-001 class (a site cannot transition without the emit and the event row), gives the auditor/regulator persona a queryable trail, and makes `dispatch.md` §4's hand-built table a query. It also gives H3 its cheapest producer: the event row *is* the outbox message for non-latency-critical consumers (analytics, admin monitoring, Zoho).
- **Smallest first step.** Additive migration `ride_status_events` (no code) → `transition_ride_status()` in a new `routes/rides/transitions.py`, called in shadow from `scheduled → searching` only (`utils/scheduled_rides.py:448-463`, the newest and best-documented site) → compare N days → migrate sites one PR each, DISPATCH-001's site first. Insurance-period writes stay a separate explicit call (Period 2 opens at *offer*, not at the status write — CLAUDE.md nuance), moving into RPCs as v2 completes.

### H2 — Double-entry ledger as the only money writer

- **What exists (VERIFIED via `money-cra.md` §3.6/§3.11, schema re-read).** `financial_events` is a single-entry, append-only ledger (migration 58; UPDATE blocked; DELETE only inside the retention purge, 289) written *after* money moves by `record_event`, which by design never raises. Double-entry legs (`financial_event_entries`, 286) are a derived projection gated by `ledger_double_entry_enabled` (schema default `False`; "assuming off" on any read error, `ledger_service.py:433`); `ledger_atomic_settle_enabled` (default `False`) gates the atomic settle RPC for card payments only. Production values of both flags: UNKNOWN. Money truth lives on `rides.*`, where `distance_fare`, `time_fare` and `surge_multiplier` are FLOAT8 (VERIFIED, `08_complete_schema.sql:130-136`) and `total_fare`, `tip_amount`, `driver_earnings` are INFERRED FLOAT8 from the `::text::numeric` casts in every SQL rollup (161/166/227/341/349/350) and the code comment at `fare_service.py:480-483` — `rides` has no tracked CREATE, so the live types are UNKNOWN until read from `information_schema`. Driver balance is recomputed from rides + payouts on every read. `corporate_wallet_apply_delta` is the one place where the ledger *is* the only writer, and it works (§3.13; one caller lacks a key — CORP-001).
- **Verdict: ADOPT as the end state; REJECT "only writer" as a near-term step; ADOPT-INCREMENTALLY the "ledger as constraint" path.** `money-cra.md` §7 reached the same verdict independently and I agree with its reasons: the legs projection has never run at volume; `record_event`'s never-raise contract would have to invert on a live settlement path; FLOAT8 columns must migrate first or the projection drifts; ~20 readers and 44 loops compute from `rides.*`. A ledger-first request path on a product with live charges is exactly the change gate 4 exists to stop.
- **Cost:** Now S (flag on in staging, registry + write guard, absorption meter); Next M (atomic header RPCs for wallet/corporate/refund/dispute/top-up); Later M (driver-payable view with dual-read); Rewrite-only L (`rides` money columns as a read model). **Risk:** low → medium → medium. **Reversibility:** flags at every step; legs are derived and re-projectable.
- **What it buys, in order.** (1) HIST-001 stops recurring at the boundary, not at the grep — a money-column registry generated from `information_schema` plus a repository write guard that rejects `float` for registered columns (`00-history.md` HIST-001 recommendation; MONEY-006 confirms the class is still open). (2) "payout ≤ collected + funded absorption" becomes measurable (MONEY-010) and then a constraint. (3) Reconciliation collapses from eleven population-mismatched checks (MONEY-013) toward one `Σ cash == Stripe balance`.
- **Smallest first step.** Step 0 is a **write-site coverage inventory**, because the guard cannot see every writer: about 71 direct `.table()` writes bypass `repositories/_base.py`, including `rides` (`repositories/ride_repo.py:260,276`) and `payouts` (`services/stripe_payout_sync_service.py:457,464`), plus about 90 `supabase.rpc(` calls whose arguments the guard never sees (`08-hostile-review.md` U-1, single-line grep lower bounds — VERIFIED by the orchestrator for the two named files). Then the registry + write guard behind `money_write_guard` (500 in dev/test, metric in prod) at `_base.py` **and** routed explicitly through `ride_repo` and the payout sync first, then the remaining direct writers per the inventory. Exit criterion: 100 % of registered-column writers covered *and* zero rejections — not "zero rejections" alone, which would be false assurance while writers bypass the guard. The semgrep allowlist stays until coverage is complete. Alternative considered: keep widening the semgrep allowlist only (7 exclusions already; 12 files covered, 13 money-adjacent files outside it per §3.12) — rejected as the sole mechanism, it cannot see column types.

### H3 — Transactional outbox for every side effect

- **What exists (VERIFIED).** A real Postgres transactional outbox (`migrations/399`, `services/outbox.py`, `utils/outbox_worker.py`, `scripts/outbox_admin.py`): producer is an `AFTER UPDATE` trigger on `rides` so the row commits with `payment_status='paid'`; lease/ack RPCs; dead-letter redrive; payloads are ids only. Scope: **one topic** (`ride_receipt.v1`), **default off**, and it needs a worker process — which `reliability.md` REL-003 shows is unset in the real Fly/Railway configs, so every machine runs all 45 loops. Adjacent machinery: `utils/push_retry.py` (a retry queue for FCM), the Redis per-client seq/outbox replay ring for WS (`socket_manager.py:346-348`; rider client never sends `last_seq`, RIDERJ-006), and the payment-retry loop with per-attempt keys (§3.10). Side effects that today run inline and can be lost: Zoho ticket creation incl. the SOS ticket (INT-002, warning-and-drop), receipt email when the outbox is off, insurance-period writes at v1 call sites (HIST-010).
- **Verdict: ADOPT-INCREMENTALLY, scoped to durable, non-latency-critical side effects; REJECT "every".** WS fan-out (< 100 ms SLA) and the offer push (P95 < 2 s) must stay in-request with their existing replay/retry paths; routing them through a polled outbox would breach the SLAs `CLAUDE.md` sets and add a worker to the dispatch critical path. Durable effects — receipts, support/Zoho tickets, emails, statement generation, analytics/admin projections — belong in the outbox, where "swallowed" becomes impossible by construction (the corner of HIST-004 that is architectural).
- **Cost:** S per topic once the worker runs; the worker itself is an ops step (REL-003). **Risk:** low — every topic is flag-gated and the API fallback path already exists (399's rollback block). **Reversibility:** flag off; rows drain; table stays.
- **Smallest first step.** Set `SPINR_PROCESS_ROLE` on one machine group (REL-003's own step 3) and flip `outbox_receipts_enabled` in staging → add `support_ticket.v1` with the SOS Zoho ticket as the first consumer (INT-002/TSF-001's blast radius) → make `ride_status_events` (H1) the producer for admin/analytics consumers. Dependency: the worker; do not add topics before it exists.

### H4 — Idempotency keys on every mutating endpoint

- **What exists (VERIFIED).** 373 mutating route decorators. Keys already exist where money or state moves: booking (idempotency key bucketed by pickup/dropoff/2-min window + DB unique index, `rider-journey.md` §b #1), payments (17 references), safety/SOS (19; idempotent per press), admin/corporate wallet (`client_idempotency_key`, #4602), payouts, Stripe (three layers, `money-cra.md` §1.3), the v2/v3 offer RPC (`request_id`, replay-detected). Concrete gaps: the corporate wind-down debit has no key (CORP-001); `apply_adjustment`'s key is *optional* so a caller can forget it; admin editors have last-write-wins with no version (ADMIN-OPS-004, ~10 editors incl. surge/fare config); `set_driver_available` is read-then-write (DISPATCH-003).
- **Verdict: REJECT "every endpoint"; ADOPT for the money/state subset by making the key *mandatory at the wrapper*, and ADOPT optimistic concurrency (a `version`/`updated_at` precondition) for admin editors, which is the correct primitive there — idempotency does not stop two admins overwriting each other.** A generic header middleware over 373 endpoints would be speculative complexity (most admin CRUD is naturally idempotent PUTs) and would not have caught CORP-001, which is a *missing argument*, not a missing header.
- **Cost:** S (wind-down key; make `client_idempotency_key` required in `corporate_wallet_service` wrappers; static test listing the money endpoints that must carry a key); M (version column + precondition on the ~10 admin editors). **Risk:** low. **Reversibility:** git revert (no data change for the key; the version column is additive).
- **Smallest first step.** CORP-001's one-line key, then a static test in the style of `test_loguru_call_conventions.py` that fails when a `*_apply_delta`/`wallet_apply_delta` wrapper is called without a key argument.

A generated client would have to reproduce the token-refresh interceptor and the offline/cached client, and would touch every screen — L effort on a live product with no mobile E2E (QUAL-004, B25).
- **Cost:** S (CI job: snapshot `openapi.json` on `main`, diff on PR, fail on removed field/changed type — additive-only evolution); S–M (generate TS types only, into `shared/types/api/generated.ts`, adopt per endpoint); M (WS event schema: one backend enum → JSON schema → a `shared` test that every `wsEvents.ts` type matches and every backend literal is declared). **Risk:** low — none of it changes runtime behaviour. **Reversibility:** delete the job.
- **Smallest first step.** The OpenAPI snapshot-diff CI job (catches the referral-field class before it ships), then the WS event enum + test (catches DISPATCH-001's class). Generated *types*, not clients, and only where a screen is being touched anyway.

### H7 — Feature flags as a first-class service

- **What exists (VERIFIED).** One `settings` row (`id='app_settings'`) holding 37 `*_enabled` booleans plus vendor keys, read through `get_app_settings()` at 281 call sites with a 60 s in-process TTL and keep-last-known-on-rowless (a real kill-switch safety property, `settings_loader.py:46-68`). Per-flag read-failure semantics are a **recorded decision** (ADR-011, amended 2026-09-21): no universal rule; each money-path flag states fail-open/closed at its read site. Rollout is global (no per-area, per-cohort or percentage targeting), there is no flag registry (owner, default, failure mode, created, sunset), no client-side flag SDK (admin reads its `admin_theme_v2_enabled` through the settings endpoint; mobile behaviour is mostly server-decided), and a growing set of "built, dark, unverified" flags: `driver_availability_v2_enabled` (22 references), batch-claim/v3 dispatch (DISPATCH-002), `ledger_double_entry_enabled`, `ledger_atomic_settle_enabled`, `outbox_receipts_enabled`, `minimal_fcm_offer_payload_enabled` (SKB-002: a live PII gap sits behind it), eligibility recheck (COMP-002: every SK rule beyond document expiry is dark), `dual_approval_exports_enabled` (B10), `refresh_successor_commitment_enabled`.
- **Verdict: ADOPT-INCREMENTALLY as a *registry and lifecycle*, MODIFY not REPLACE the store; REJECT buying a flag vendor** (one more sub-processor with a data-residency question, cost, and the `app_settings` pattern already gives rotation-without-redeploy — CLAUDE.md Critical Conventions). Do not re-litigate ADR-011. The architectural gap is not the store; it is that flags have no lifecycle, so dark flags accumulate and the audit keeps finding "the fix exists but is off" (DISPATCH-003, SKB-002, COMP-002, B10, MONEY §3.11).
- **Cost:** S (generate `docs/flags.md` from `AppSettings` with owner/default/failure-mode/sunset; a test that every `*_enabled` field has those four annotations and that no flag is older than N days without a decision); M (per-service-area targeting for consumer-visible flags via `service_areas` config — the "rules as configuration" direction of `greenfield-extensions.md` §10). **Risk:** none for the registry; low for targeting. **Reversibility:** trivial.
- **Smallest first step.** The generated registry + annotation test. It also closes HIST-005 for this particular fact (the flag inventory in `admin-ops.md` §6 is hand-maintained today).

**Summary of verdicts.** H1 adopt-incrementally · H2 adopt (destination) / reject (near-term "only writer") / adopt-incrementally (constraint path) · H3 adopt-incrementally, scoped · H4 reject "every", adopt for money/state + optimistic concurrency for admin · H5 adopt-incrementally on the existing package · H6 adopt-incrementally (types + drift), reject generated client · H7 adopt-incrementally (registry + lifecycle), reject vendor.
