[2-1] CRITICAL | Duplicate /auth/refresh endpoint — old one will crash at runtime
File: backend/routes/auth.py:347-401 and 475-534
Finding: Two functions both register on POST /auth/refresh. The first (lines 347-401) is silently
overwritten by the second (FastAPI only keeps the last registration). The dead first function
calls _store_refresh_token() on line 399 — a function that doesn't exist anywhere in the codebase
— so if it ever ran it would NameError crash immediately. The second (lines 475-534) is correct.
Fix: Delete the old refresh_token() function at lines 347-401 entirely. Keep only
refresh_access_token() at lines 475-534 which correctly uses issue_refresh_token().

[2-2] CRITICAL | MongoDB-style DB calls will crash with AttributeError
File: backend/routes/auth.py:355, 378, 387, 393
Finding: The dead first endpoint uses db.refresh_tokens.find_one() and db.users.find_one()
MongoDB attribute-access syntax. The actual db_supabase API exports plain functions:
db.find_one(table, filters). Calling db.refresh_tokens.anything raises AttributeError.
Fix: Remove the dead function (per [2-1]). If any similar calls exist elsewhere, replace with
db.find_one('refresh_tokens', {'token_hash': hash}) pattern.

[2-3] CRITICAL | Wrong DB field name in revocation check ('revoked' vs 'revoked_at')
File: backend/routes/auth.py:355
Finding: The dead endpoint queries {'revoked': False} but the DB schema (migration 25) defines
revoked_at TIMESTAMPTZ — a timestamp, not a boolean. utils/refresh_tokens.py correctly checks
row.get('revoked_at') is None. The mismatch would silently return wrong results.
Fix: Removed by deleting the dead function per [2-1]. utils/refresh_tokens.py:131 is already correct.

[2-4] HIGH | Undefined function _store_refresh_token called on line 399
File: backend/routes/auth.py:399
Finding: await _store_refresh_token(user_id, new_refresh) — this function is not imported or
defined anywhere. Would crash with NameError if the dead endpoint were ever reached.
Fix: Removed by deleting the dead function per [2-1].

[2-5] HIGH | Firebase auth path never issues a refresh token
File: backend/dependencies/__init__.py:128-172
Finding: Users authenticated via Firebase ID token exchange get an access token issued but
issue_refresh_token() is never called. They cannot refresh their session without re-authenticating
via Firebase. Also, no audience or custom claim check validates driver vs. rider scope on the
Firebase token.
Fix: After line 165, call issue_refresh_token(user_id) and include the refresh token in the
response. Validate a custom Firebase claim (e.g., role == 'driver') if drivers and riders use the
same Firebase project.

[2-6] MEDIUM | OTP send rate limit too lenient — 5/min instead of spec 3/min
File: backend/routes/auth.py:135
Finding: @limiter.limit("5/minute") — spec requires 3/min to limit phone enumeration.
Fix: Change to @limiter.limit("3/minute").

[2-7] MEDIUM | OTP verify rate limit too lenient — 10/min instead of spec 5/min
File: backend/routes/auth.py:200
Finding: @limiter.limit("10/minute") — attacker gets 10 guesses per minute before 5-failure
lockout kicks in, doubling the intended attack budget.
Fix: Change to @limiter.limit("5/minute").

[2-8] MEDIUM | OTP lockout silently disabled when Redis is unavailable
File: backend/routes/auth.py:72-112 and backend/core/config.py:56
Finding: REDIS_URL can be empty string (optional). When Redis is absent, redis_get/redis_incr
raise exceptions that are caught and return None, causing _check_otp_lockout() to skip the check.
Brute-force protection silently evaporates without Redis.
Fix: Add an in-process fallback (threading.Lock + dict with TTL) for OTP attempt tracking that
activates when Redis is unavailable. Log a warning at startup when running without Redis.

[2-9] MEDIUM | Firebase auth path does not validate audience (driver vs. rider)
File: backend/dependencies/__init__.py:136-165
Finding: Firebase token is verified but no custom claim (e.g., role) is checked. A rider Firebase
token could be exchanged for a driver-scoped access token if the user_id happens to match.
Fix: Add check: if decoded_firebase.get('role') not in ('driver', 'rider'): raise HTTPException(401).
Or use separate Firebase projects for driver and rider apps.

[3-2] HIGH | JWT_SECRET Minimum Length Not Enforced at Config Load Time
File: backend/core/config.py:81-97 and backend/core/middleware.py:133
Finding: The Settings class accepts any string for JWT_SECRET without a length check.
Minimum-length validation (≥ 32 chars) only runs in middleware._validate_production_config,
which is called AFTER Settings is instantiated. A 3-character JWT_SECRET would be accepted
by pydantic and only caught later. Cryptographically, a short secret is trivially brute-forced.
Fix: Add to the @model_validator in config.py:
    if self.ENV.lower() == "production" and len(self.JWT_SECRET) < 32:
        raise ValueError("JWT_SECRET must be at least 32 characters in production")
