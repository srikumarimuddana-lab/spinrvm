[01-1] HIGH | UnboundLocalError on first-ever rating: average_rating only
defined inside `if rated_rides:` block but used unconditionally
File: backend/routes/rides.py:1788,1796,1801-1803
Finding: `average_rating = round(...)` is assigned only inside the
`if rated_rides:` branch (line 1796), but lines 1801-1803 reference it
unconditionally to build the update payload. When a driver receives their
first rating and no prior `rated_rides` exist, this raises
UnboundLocalError → 500 response → first-ever rating endpoint crashes.
Compounds 19-1 (rating field-name mismatch) — even after 19-1 fixes the
field, the FIRST rating against any driver still trips this path.
Fix: `average_rating = driver.get('rating', 5.0)` before the conditional;
update the local only when `rated_rides` is non-empty.
Effort: 1 h
Risk score: 24 (HIGH × org × likely)
Regulations: SK-CPPA
Owner: backend · Sprint: P0

[02-1] HIGH | Firebase ID token verified without `audience=` parameter
(DV-10 dup at HEAD)
File: backend/routes/auth.py:392,403,407,408
Finding: `_firebase_auth.verify_id_token(body.firebase_token)` is called
without an audience parameter. A subsequent manual aud-claim check is
gated on `if driver_app_id` — if `FIREBASE_DRIVER_APP_ID` is unset, the
audience check is skipped. Confirms DV-10 still open at HEAD. The same
issue exists for the rider audience (rider Phase E flagged this as 19-6,
21-1, 22-5).
Fix: Pass `audience=settings.FIREBASE_DRIVER_APP_ID` to verify_id_token;
fail startup if the env var is missing in production.
Effort: 2 h
Risk score: 24 (HIGH × org × possible) — duplicate_of: DV-10
Regulations: PIPEDA
Owner: backend · Sprint: P1

[03-1] HIGH | JWT_SECRET length not enforced — only known-weak placeholder
values are blocked
File: backend/core/config.py:84-99
Finding: `_guard_production_secrets` checks `JWT_SECRET` against a list
of placeholder strings (`your-strong-secret-key`, etc.) but does not
enforce a minimum length. A 4-character secret passes validation. HS256
uses the secret as the symmetric signing key — short secret = weak
signature. CLAUDE.md says "JWT_SECRET — must be ≥32 chars; startup fails
in production with weak value" but this isn't actually enforced.
Fix: After the placeholder check, add `if len(value) < 32: raise
ValueError("JWT_SECRET must be ≥32 chars in production")`.
Effort: 1 h
Risk score: 28 (HIGH × org × likely)
Regulations: PIPEDA, SOC2
Owner: backend · Sprint: P1

[04-1] MEDIUM | `float()` used for monetary amounts in corporate allowance
grant — CLAUDE.md "Decimal only" violation on a non-fare path
File: backend/routes/corporate_company.py:269,272
Finding: `amount=float(request["amount"])`, `floor=float(wallet.get(
"soft_negative_floor", -50))`. The pre-commit float-arithmetic hook
covers fare code; corporate wallet code is outside the hook's path.
Same family as 20-1 (rider Phase E flagged the rider wallet path) — this
is the corporate-wallet sibling.
Fix: Replace with `Decimal(str(...))`; sweep `corporate_*.py` for the same
pattern; add the corporate paths to the pre-commit hook scope.
Effort: 2 h
Risk score: 16 (MEDIUM × self × likely)
Regulations: CRA, PCI-DSS
Owner: backend · Sprint: P2

[07-1] CRITICAL | Ride state-string mismatch between complete_ride and
process_payment — rider literally cannot pay after a completed ride
File: backend/routes/rides.py:1309,1312 (process_payment) +
backend/routes/drivers.py:2088 (complete_ride)
Finding: `complete_ride` writes `status='completed'`. The
`process_payment` endpoint guards with `if _ride_status != 'trip_completed'`
and raises 409 otherwise. Once the driver completes the ride, the rider
hits the payment endpoint and gets 409 — fare collection blocked, support
escalation required for every ride.
Same family as DV-3 (`COMPLETE_FROM_STATES = ('in_progress',)` vs
`'trip_in_progress'`). Different specific instance.
Fix: Standardize state strings via a `RideStatus` enum (per DV-3); short
term, change `process_payment` to also accept `'completed'` (or canonicalize
on `'trip_completed'`). Sweep the repo for every state-string literal.
Effort: 2 h (short fix) + 4 h (enum refactor — recommended)
Risk score: 48 (CRITICAL × org × likely)
Regulations: PCI-DSS, SK-CPPA
Owner: backend · Sprint: P0

[08-1] MEDIUM | Stripe webhook handler has no event-type allowlist; unknown
events silently marked processed
File: backend/routes/webhooks.py:94,138,190,218-219
Finding: Webhook routing uses an if/elif chain on `event_type`; the else
branch logs `"Unhandled event"` but still calls
`mark_stripe_event_processed(event_id)`. Any future event type Stripe adds
(refund, dispute, chargeback, payout.paid, account.updated, etc.) is
silently accepted with no business logic + audit trail incomplete.
Fix: ALLOWED_EVENTS allowlist; reject unknown types with 400 + alert
(don't 200 + processed_at).
Effort: 2 h
Risk score: 16 (MEDIUM × org × possible)
Regulations: PCI-DSS, SOC2
Owner: backend · Sprint: P2

[10-1] HIGH | `logger.warning` on Firebase auth / DB persistence failures —
CLAUDE.md rule violation
File: backend/routes/auth.py:96,100,437,443
Finding: `logger.warning(f"firebase_auth: could not persist user {uid}: {e}")`.
CLAUDE.md ground rule: DB / auth / payment errors must use `logger.error`
with full exception, not warning. Production log aggregation typically
filters warnings — silent partial-state bugs (user created in Firebase
but not in DB) hide.
Fix: Replace warning → error; pass `exc_info=True`; alert on error rate.
Effort: 2 h
Risk score: 24 (HIGH × org × possible) — P1
Regulations: PIPEDA
Owner: backend

Fix: `with logger.contextualize(request_id=request.state.request_id):`
around App Check exception logging. Effort: 1 h

[14-1] HIGH | `get_ride_history` fetches 2000 rows then filters/paginates in Python
File: backend/routes/rides.py:1092,1097
Finding: `all_rides = await db_supabase.get_rows('rides', {'rider_id':
current_user['id']}, limit=2000)`. Filter by status, sort, and pagination
are all done in Python after the fetch. Every history request scans 2000
rows from DB even when the caller only wants page 1 (10 rows).
Fix: Push status filter + ordering to DB; cursor-based offset; cap LIMIT
at the page size (≤100). Effort: 3 h
Risk score: 32 (HIGH × org × likely) — P1
Regulations: SK-CPPA
Owner: backend

[14-2] HIGH | Round-robin dispatch query scans the entire `rides` table to
find one row
File: backend/services/dispatch_service.py:239
Finding: `await self.db.get_rows('rides', {'driver_id': {'$ne': None}},
order='created_at', desc=True, limit=1)` to find the last-assigned driver.
No supporting index. As `rides` grows past 100k, every dispatch decision
incurs a sequential scan.
Fix: `CREATE INDEX idx_rides_driver_assigned_at ON rides(driver_id,
assigned_at DESC NULLS LAST)`; query by `assigned_at` instead of
`created_at`. Effort: 2 h
Risk score: 28 (HIGH × org × likely) — P1
Regulations: SK-CPPA (dispatch SLA)
Owner: backend

[14-3] MEDIUM | Driver candidate query has no composite index for

dispatch (`is_online=true, is_available=true, vehicle_type_id=...`) has

Fix: `CREATE INDEX CONCURRENTLY idx_drivers_online_available_type ON

Risk score: 20 (MEDIUM × org × likely) — P2
Regulations: —

[14-4] MEDIUM | DSAR export makes 6 sequential `get_rows` calls instead of
parallel
File: backend/routes/drivers.py:1529-1541
Finding: `_build_and_email_data_export` issues 6 awaits in series (drivers,
users, rides, payouts, documents, notification_prefs). Total latency =
sum of 6 round-trips. Compounds the DSAR SLA risk flagged in 12-2.
Fix: `asyncio.gather(*[get_rows(...), ...])` for parallel fetch.
Effort: 2 h
Risk score: 16 (MEDIUM × org × possible) — P2
Regulations: PIPEDA
Owner: backend

[14-5] MEDIUM | `run_sync` thread pool size unconfigured — default scales
with CPU count, saturates under load
File: backend/db_supabase.py:83-95
Finding: `loop.run_in_executor(None, func)` uses the default executor.
Default `ThreadPoolExecutor` has `max_workers = min(32, cpu_count + 4)`.
On a 4-core container that's 8 threads — concurrent DB calls block each
other under load.
Fix: Explicit `ThreadPoolExecutor(max_workers=16)` (configurable via
`DB_THREAD_POOL_SIZE` env var); export queue-depth + active-thread
metrics. Effort: 3 h
Risk score: 16 (MEDIUM × org × possible) — P2
Regulations: —
Owner: backend

[14-6] MEDIUM | `broadcast()` sends to every connection synchronously —
blocks event loop at high connection count
File: backend/socket_manager.py:97-99
Finding: `for connection in self.active_connections.values():
await connection.send_json(msg)`. At 500+ connections per replica, a
broadcast blocks the loop for the duration of all `send_json` calls.
Fix: `asyncio.gather(*[c.send_json(msg) for c in connections],
return_exceptions=True)`; per-message timeout; log slow broadcasts.
Effort: 2 h
Risk score: 12 (MEDIUM × org × possible) — P3
Regulations: —
Owner: backend

[14-7] LOW | Background loops have no jitter — multiple loops wake at the
same second
File: backend/core/lifespan.py:96-115

all 5-min loops wake at the same second causing periodic load spikes
on the DB pool.
Fix: Add ±10% jitter to each sleep; per-loop duration / error metrics.
(Also closes the heartbeat-emission gap from Phase E 17-5/17-10.)
Effort: 2 h
Risk score: 8 (LOW × org × possible) — P3
Regulations: —
