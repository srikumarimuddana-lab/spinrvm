# Change Impact Log — 2026-09-09 retention purge `recorded_at` column fix

| Field | Detail |
|---|---|
| **Issue/gap identified** | `purge_pii_retention()` PL/pgSQL function crashes every tick with `column "recorded_at" does not exist` on `driver_location_history`, meaning the daily PIPEDA retention purge has never run successfully on this database. |
| **Root cause** | The live function body still references `driver_location_history.recorded_at`, a column from migration 08's `CREATE TABLE` that was a no-op on the pre-existing production table. The actual column is `received_at` (migration 118). Migration 187 fixed this in the repo, and every subsequent re-fork (through 335) carried the fix, but none of those migrations have been applied to the production database. |
| **Fix/remediation** | Migration 409 re-forks `purge_pii_retention()` verbatim from migration 335 (the latest definition), with Step C using `received_at`. If 335 applies first in a batch run this is a harmless no-op; if applied standalone it installs the corrected function directly. |
| **Risk & impact on existing functionality** | `purge_pii_retention()` is called only by `utils/retention_purge.py`'s `run_retention_purge_tick()` via `supabase.rpc()`. No other caller. The function body is identical to migration 335's — no behavioral change beyond fixing the column reference. Steps that reference tables added by later migrations (e.g. `compliance_export_events` from 285, `price_searches` from 228) will fail if those tables don't exist yet; this is the same risk the pending migration 335 already carries, not new. |
| **User experience effect** | None directly visible. The retention loop will start succeeding, meaning `driver_location_history` rows older than 90 days will begin being purged (PIPEDA compliance), and the `retention_purge_loop: tick failed` error log will stop. |
| **Files modified** | `backend/migrations/409_purge_pii_retention_received_at_fix.sql` — new file, `CREATE OR REPLACE FUNCTION purge_pii_retention()` with `received_at` in Step C. |
| **Before/after snippet** | Step C in the live function (pre-fix): `WHERE recorded_at < v_started_at - c_loc_history_age` → Step C after migration 409: `WHERE received_at < v_started_at - c_loc_history_age` |
| **Rollback plan** | Re-apply migration 335's identical function body (no functional difference). Or, if the function must be reverted to the pre-fix version for some reason, re-apply the function from the migration that was previously the live version (likely migration 143 or earlier). The column reference change is the only delta. |
| **Verification performed** | Grepped all 20 migrations that define `purge_pii_retention()` to confirm the `recorded_at` → `received_at` fix is correct and matches migration 187's original fix and all subsequent re-forks (216, 228, 285, 289, 296, 321, 323, 324, 335). Verified the new migration contains zero non-comment references to `recorded_at`. |
| **What was NOT verified** | Cannot verify against the live database from this environment. If other tables referenced by the function (e.g. `compliance_export_events`, `price_searches`, columns added by migrations 228/285/296) do not yet exist in production, the function will fail on the first step that touches them — this is the same risk the pending migration 335 already carries. A `--dry-run` against production after applying is recommended. |
