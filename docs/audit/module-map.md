# Spinr Module Map (Recon Audit)

Generated by read-only static recon on 2026-07-25. Scope: `backend/` (primary,
production runtime), plus a survey of `rider-app/`, `driver-app/`,
`admin-dashboard/`, `shared/`, `agents/`, `scripts/`, `backend/migrations/`.
Core files were opened and read; the ~317 migrations and ~150 test files were
sampled rather than read exhaustively.

## Top-level layout

```
backend/            FastAPI monolith (single horizontally-scalable process)
rider-app/           Expo/React Native rider client
driver-app/          Expo/React Native driver client
admin-dashboard/     Next.js/Vercel admin web app
shared/              Cross-surface shared code/types
agents/              Separate multi-agent dev-automation SDK — NOT production runtime (agents/CLAUDE.md)
scripts/             Ops/dev scripts
docs/                Design docs, runbooks, ADRs
tests/ (root) + test_admin_endpoints.py   Root-level test scaffolding in addition to backend/tests/
```

## Auth

- `backend/routes/auth.py` — phone/OTP signup+login, JWT issuance, refresh-token rotation.
- `backend/utils/password_policy.py`, `backend/utils/refresh_tokens.py`, `backend/utils/crypto.py` — password/refresh-token hashing (SHA-256 for refresh tokens per CLAUDE.md), OTP hashing.
- `backend/routes/admin/auth.py` — separate admin login/JWT path; admin JWTs are fully trusted (role+email+modules baked into claims) per CLAUDE.md — confirmed this is a distinct trust model from rider/driver auth, which is re-derived from `users` table on every request (not fully verified line-by-line in this pass, but no counter-evidence found; recommend a follow-up pass over `dependencies/` for `get_current_user`).
- External: Twilio (OTP SMS, credentials sourced from `app_settings` table per CLAUDE.md, not `.env`), JWT_SECRET (`core/config.py`).

## Driver Onboarding

- `backend/routes/admin/drivers.py`, `backend/routes/admin/documents.py`, `backend/routes/admin/driver_import.py` — admin-side verification, document checks, bulk import.
- `backend/services/driver_import_service.py` — bulk driver import logic.
- `backend/utils/driver_online.py` (116 lines) — gates `go_online`: license/insurance/CRC document expiry checks block Period 1+ (regulatory requirement).
- `backend/utils/driver_presence.py` (249 lines) — Redis-backed short-TTL heartbeat (`present_driver_ids`) used by dispatch to exclude drivers whose app died but `is_online` is stale.
- DB: `drivers` table fields `is_online` (driver-toggled), `is_available` (system-computed — `dispatch_service.claim_driver` / `assign_driver_to_ride` flip this), `is_verified`, `status`.

## Trip Lifecycle

`backend/routes/rides/` is a package (god-file split from a former `rides.py`; see `docs/refactors/god-file-split.md` referenced in code comments). Files read:

- `__init__.py` (457) — package assembly / re-exports (`_require_ride_in_state_rider` re-exported here).
- `_deps.py` (206), `_shared.py` (659) — shared dependency wiring; `_shared.py` hosts `_require_ride_in_state_rider` (rider-side state guard, line 290), `_d`/`_round` Decimal helpers (lines 324-330), `_reestimate_fare_for_stops` (multi-stop re-pricing).
- `booking.py` (1330) — ride creation/booking flow.
- `lifecycle.py` (358) — rider-initiated `simulate-arrival` (dev-only, line 34-59), `rider_start_ride` (line 62), `rider_complete_ride` (line 126). **Does NOT call `_require_ride_in_state_rider`** — instead does an inline `ride.get("status") != X` check followed by an atomic `update_one` filtered on the expected prior status as a race guard (lines 82-100, 145-161). This is a third, hand-rolled implementation of the same "check state, atomically transition" pattern (see findings.md).
- `cancellation.py` (550) — rider/admin cancellation, no-show, scheduled-ride cancel-and-requeue (writes both `CANCELLED` and back to `SCHEDULED`, lines 483/491).
- `matching.py` (1364) — dispatch orchestration glue (offer send/accept/expire, `process_expired_offer`, re-dispatch), imported directly by `utils/offer_expiry_reaper.py` (an inverted dependency: utils → routes, called out in that file's own docstring as deliberate).
- `estimates.py` (624), `stops.py` (221), `chat.py` (243), `rating.py` (140), `receipts.py` (174), `queries.py` (579, ride history/detail), `payments.py` (431), `sharing.py` (312), `safety.py` (210), `tracking.py` (109), `lost_found.py` (96).

- `backend/routes/drivers/` package (parallel split): `_shared.py` hosts a **second, independent** `_require_ride_in_state` (driver-side, line 558) with near-identical structure/docstring to the rider-side one in `routes/rides/_shared.py:290` but a different exception type (`HTTPException` directly vs `SpinrException`/`RideNotFoundException`). `ride_flow.py` (accept/arrive/start), `ride_complete.py` (driver-side complete, line 621 uses yet another inline filter-based atomic guard rather than calling `_require_ride_in_state`), `ride_cancel.py`, `earnings.py`.
- `backend/models/ride_status.py` — canonical `RideStatus(str, Enum)` with `active_statuses()`/`terminal_statuses()` classmethods; docstring states the same transition diagram as CLAUDE.md.
- `backend/utils/scheduled_rides.py` (317) — background loop promoting `scheduled` → `searching` at dispatch time.
- `backend/utils/offer_expiry_reaper.py` (141) — durable backstop for lost in-process offer timers; re-uses `matching.process_expired_offer`; guards re-dispatch by re-checking `status == "searching"` (line 120) as a race guard against a ride that moved on.
- `backend/utils/stuck_ride_sweeper.py` (140) — cancels rides stuck in `searching` >5 min via a raw Supabase `.eq("status","searching").lt("ride_requested_at", cutoff)` claim (a **fourth** independent state-guard implementation, this one hand-written against the Supabase client rather than through `db_supabase`/`db` helpers — see findings.md).
- `backend/routes/admin/rides.py` (3430 lines — largest single route file) — admin ride visibility/overrides; large surface, only sampled (status-literal grep hits at multiple points; not individually catalogued here).
- `backend/features.py` — legacy/shared grab-bag module still holding some ride-status writes (`RideStatus.IN_PROGRESS`/`SCHEDULED`/`CANCELLED`/`SEARCHING` at lines 461, 1174, 1205, 1877, 1893) alongside the newer `routes/rides/` package — a duplication/legacy-migration signal.

## Dispatch / Matching

- `backend/services/dispatch_service.py` (502 lines, fully read) — pure + DB-bound matching:
  - `dispatch_geo_bounds` — lat/lng bounding box pre-filter before haversine.
  - `_is_dispatchable_driver`, `_ride_brings_driver_closer_to_destination` (destination-mode gating), `filter_and_rank_drivers` (WAV requirement enforced here per Saskatchewan Transportation Act s.22, line ~187), `select_driver_by_algorithm` (`nearest`/`rating_based`/`round_robin`/`combined`).
  - `DispatchService.find_candidate_drivers` — online+available+verified+present query, layered with a Redis presence filter (fail-open on Redis error, emits `spinr_dispatch_presence_filter_failed_total`) and a Spinr Pass subscription/quota filter (fail-open on error).
  - `DispatchService.assign_driver_to_ride` — flips `searching`→`driver_assigned` (a **string literal** `"driver_assigned"`, line 448, not `RideStatus.DRIVER_ASSIGNED` — inconsistent with the enum used elsewhere).
  - `claim_driver`/`claim_any_driver` — atomic `is_available=True→False` claim race guard.
- Consumed by `routes/rides/matching.py` (orchestration: WS fan-out, push notifications, offer timeout task) and by `utils/offer_expiry_reaper.py` for re-dispatch.
- External: Redis (presence + Spinr Pass quota reads), Supabase `drivers`, `service_areas`, `driver_subscriptions`, `rides` tables.

## Pricing / Fare

- `backend/services/fare_service.py` (457 lines) — `_d`/`_round`/`_f`/`_fd` Decimal helpers (local re-definition, not imported from `utils/money.py` — see findings.md); `calculate_fare`, `build_fare_breakdown_lines`, `recalculate_fare_for_distance`, `build_default_fares`, `merge_vehicle_pricing_with_vehicle_types`.
- `backend/utils/surge_engine.py` (400 lines) — `SURGE_CAP = 2.5` (line 65) matches CLAUDE.md's documented hard cap; auto-mode tiers keyed off demand/supply ratio.
- `backend/utils/money.py` (55 lines, fully read) — `to_decimal`, `dollars_to_cents`, `cents_to_dollars`; explicitly documents the `Decimal(str(x))` vs `Decimal(x)` float-drift pitfall it exists to prevent. **Not used by `fare_service.py` or `routes/rides/_shared.py`**, which define their own local `_d`/`_round` (functionally similar but a second source of truth — see findings.md).
- `routes/rides/_shared.py` and `routes/rides/estimates.py`/`queries.py`/`matching.py` contain many `float(...)` conversions on fare/tip/incentive/tax fields at serialization boundaries (acceptable per money.py's own stated design — "if a float is needed at a serialization boundary, the caller converts explicitly" — but some occur mid-calculation rather than purely at the boundary; flagged individually in findings.md).

## Payments

- `backend/services/payment_service.py` (1032 lines) — `settle_wallet`, `settle_corporate`, `auto_settle_guest_corporate`, `_settle_against_hold`, `settle_card`, `send_ride_receipt`, `record_payment_event`, `record_refund_event`. Local `_d`/`_round`/`_f`/`_money_str` helpers (again, not `utils/money.py`).
- `backend/routes/payments.py`, `backend/routes/webhooks.py` — Stripe webhook intake; CLAUDE.md's `claim_stripe_event` idempotency convention expected here (not individually re-verified line-by-line this pass).
- `backend/utils/payment_retry.py`, `backend/utils/stripe_charge.py`, `backend/utils/stripe_reconcile.py`, `backend/utils/t4a_annual_job.py` — background retry/reconciliation/tax-reporting loops.
- External: Stripe (charges, webhooks, KYC via `services/stripe_kyc_sync.py`), `stripe_events` table (idempotency claim table per CLAUDE.md).

## Corporate Billing

- `backend/services/corporate_wallet_service.py`, `corporate_allowance_service.py`, `corporate_membership_service.py`, `corporate_policy_service.py`, `company_booking_service.py` — layered on top of consumer ride/payment logic without touching ride/driver core logic (per CLAUDE.md's stated design intent — consistent with what was read).
- `backend/routes/corporate_*.py` (accounts, company, company_bookings, company_kyb, rider, signup, wallet) — route surface.
- `backend/services/guest_user_service.py`, `guest_notification_service.py` — guest-rider booking-without-account flow, tied to corporate company bookings.
- DB: `corporate_wallet_apply_delta` Postgres function (row-level locking/idempotency per CLAUDE.md — not independently re-verified this pass, trust the doc + naming match in migrations).

## Notifications

- `backend/routes/notifications.py`; FCM/Firebase push via `features.send_push_notification` (referenced throughout ride lifecycle files); `backend/utils/live_activity.py` (iOS Live Activity updates on ride state changes, `send_live_activity_update` called at nearly every status transition point found in this audit).
- `backend/socket_manager.py` (522 lines) — `ConnectionManager`, in-process WS registry keyed `"driver_{id}"`/`"rider_{id}"`, delegates to Redis pub/sub (`spinr:ws:dispatch` channel per CLAUDE.md) when active; `broadcast_ride_status`, `send_personal_message`, `broadcast_to_admins` used pervasively by the ride-lifecycle files above.

## Maps / Location

- `backend/routes/maps_proxy.py` — Google Maps proxy (keeps the API key server-side).
- `backend/geo_utils.py` (imported by `dispatch_service.py` as `calculate_distance`) — haversine distance.
- `backend/utils/gps_filtering.py`, `distance_integrity.py`, `route_reconstruction.py`, `route_finalizer.py`, `breadcrumbs.py` — GPS trace processing, anti-spoofing/route-deviation checks (`route_validation` verdicts `suspicious`/`likely_spoofed` seen referenced in `routes/drivers/_shared.py`).

## Admin / Ops

- `backend/routes/admin/` (24 files) — analytics, staff, settings, monitoring, maintenance, messaging, support(_tickets), incentives, promotions, subscriptions, vehicle_fleet, venues, wallet, service_areas, faqs, legal_documents, users, drivers, documents, ai_console, safety, auth. `rides.py` here is the largest file in the whole route tree (3430 lines).
- `backend/core/lifespan.py` (612 lines) — startup/shutdown; spawns the 16 background loops named in CLAUDE.md (DB health check, subscription expiry, surge engine, scheduled dispatch, payment retry, document expiry, corporate auto-topup, low-balance nudge, allowance reset, safety check-in, retention purge, reconciliation, Stripe reconcile, T4A annual job, stuck-ride sweeper, push retry, loop watchdog — offer-expiry reaper also registered per its own docstring, so the loop count in practice is 16+).
- `backend/core/middleware.py` (757 lines) — CORS, security headers, SlowAPI+Redis rate limiting.
- `backend/core/config.py` (346 lines) — pydantic-settings `Settings`, fails fast on weak secrets in production.

## Safety

- `backend/routes/safety.py`, `backend/routes/rides/safety.py`, `backend/routes/admin/safety.py` — SOS flow, safety check-in loop (one of the 16 lifespan loops).
- SOS is one-tap-offer-911, never auto-dial, per CLAUDE.md (not independently re-verified against actual route code this pass — flagged as a follow-up item given its P0 regulatory/liability sensitivity).

## Shared Utilities

- `backend/db_supabase.py` (314 lines) — ~66 helper functions wrapping `supabase-py` via `run_sync()` (thread pool, one retry on H2 GOAWAY per CLAUDE.md).
- `backend/utils/redis_client.py` — falls back to in-process dict when `REDIS_URL` unset (rate-limit/OTP lockout state lost on restart in that mode, per its own module contract).
- `backend/utils/audit_logger.py`, `sentry_scrub.py`, `pii.py` — compliance-adjacent logging/scrubbing utilities.
- `backend/utils/metrics.py` — Prometheus/OpenMetrics `spinr_<domain>_<metric>_<unit>` naming, `inc()` helper used pervasively (`spinr_dispatch_presence_filter_failed_total`, `spinr_stuck_ride_sweeper_cancelled_total`, `spinr_insurance_period_*`, `spinr_bgloop_errors_total`, etc — all confirmed by direct grep hits in files read).
- `backend/utils/insurance_periods.py` (164 lines, fully read) — `record_period_transition(driver_id, new_period, ride_id=None)`; validates period ∈ {0,1,2,3}, requires `ride_id` for period 3 (raises `ValueError` — a deliberate pre-DB programmer-error guard, not swallowed); the actual DB write goes through the `record_insurance_period_transition` Postgres RPC (migration 64) which owns the close-old/open-new atomicity via a partial unique index; write failures are logged at ERROR and swallowed by design (documented compliance trade-off: a missed audit row beats blocking the driver state machine) — this is the codebase's own explicit, reasoned exception to the "don't swallow errors" rule, not an oversight.
