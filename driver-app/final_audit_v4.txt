[2-1] CRITICAL | Duplicate /auth/refresh endpoint — old one will crash at runtime
File: backend/routes/auth.py:347-401 and 475-534
Finding: Two functions both register on POST /auth/refresh. The first (lines 347-401) is silently
overwritten by the second (FastAPI only keeps the last registration). The dead first function
calls _store_refresh_token() on line 399 — a function that doesn't exist anywhere in the codebase
— so if it ever ran it would NameError crash immediately. The second (lines 475-534) is correct.
Fix: Delete the old refresh_token() function at lines 347-401 entirely. Keep only
refresh_access_token() at lines 475-534 which correctly uses issue_refresh_token().

[2-2] CRITICAL | MongoDB-style DB calls will crash with AttributeError
File: backend/routes/auth.py:355, 378, 387, 393
Finding: The dead first endpoint uses db.refresh_tokens.find_one() and db.users.find_one()
MongoDB attribute-access syntax. The actual db_supabase API exports plain functions:
db.find_one(table, filters). Calling db.refresh_tokens.anything raises AttributeError.
Fix: Remove the dead function (per [2-1]). If any similar calls exist elsewhere, replace with
db.find_one('refresh_tokens', {'token_hash': hash}) pattern.

[2-3] CRITICAL | Wrong DB field name in revocation check ('revoked' vs 'revoked_at')
File: backend/routes/auth.py:355
Finding: The dead endpoint queries {'revoked': False} but the DB schema (migration 25) defines
revoked_at TIMESTAMPTZ — a timestamp, not a boolean. utils/refresh_tokens.py correctly checks
row.get('revoked_at') is None. The mismatch would silently return wrong results.
Fix: Removed by deleting the dead function per [2-1]. utils/refresh_tokens.py:131 is already correct.

[2-4] HIGH | Undefined function _store_refresh_token called on line 399

[4-1] HIGH | Phone Validation Accepts Any Country — Does Not Enforce Canada (+1)
File: backend/validators.py:52-57
Finding: validate_phone() prepends +1 to bare 10-digit numbers but never checks whether the
area code belongs to Canada (NANP). A US, Caribbean, or other +1 number passes as valid.
Service is Saskatchewan-only; a Washington DC number should be rejected at validation time.
Fix: After normalization, verify area code belongs to Canadian NANP allocations, or require
the user to supply an explicit +1 prefix and reject non-Canadian area codes.

[4-2] HIGH | GPS Null Island (0,0) Detected but Not Rejected
File: backend/validators.py:161-163
Finding: validate_coordinates() logs a warning for (lat=0, lng=0) but returns True. These
are default/error GPS values from a device that has no fix. Storing them creates phantom
locations, wrong route calculations, and dispatch matches to the ocean.
Fix: Change to raise HTTPException(400, "Invalid coordinates: null island") when lat == 0 and lng == 0.

[4-3] HIGH | All Monetary Fields Are float — Floating-Point Precision Errors in Finance
File: backend/schemas.py:123-127 (FareConfig), 204-210 (Ride)
Finding: base_fare, per_km_rate, total_fare, tip_amount, driver_earnings etc. are typed as
float. Float arithmetic causes precision errors: 0.1 + 0.2 = 0.30000000000000004 in Python.
validate_monetary_amount() correctly uses Decimal internally, but schema enforces float at
the API boundary, silently discarding precision.
Fix: Change all monetary field types to Decimal with Field(max_digits=10, decimal_places=2).
Use from decimal import Decimal and add model_config = ConfigDict(use_enum_values=True) for
Pydantic v2 Decimal support.

[4-4] MEDIUM | OTP Schema Fields Have No Length or Pattern Constraints
File: backend/schemas.py:10-16
Finding: VerifyOTPRequest.code is a plain str — no min_length, max_length, or digit-only
pattern. Backend would accept a 100-char string as an OTP code. Client enforces 4 digits but
a direct API call bypasses that.
Fix: code=Field(..., min_length=4, max_length=4, pattern=r'^\d{4}$')
    phone=Field(..., min_length=5, max_length=15, pattern=r'^\+[1-9]\d{6,14}$')

[4-5] MEDIUM | CreateProfileRequest Has No Field Constraints
File: backend/schemas.py:19-24
Finding: first_name, last_name, email, gender accept any string length. Empty strings, 1000-char
names, and arbitrary unicode all pass.
Fix: first_name=Field(..., min_length=1, max_length=100)
    last_name=Field(..., min_length=1, max_length=100)
    gender=Field(..., pattern=r'^(Male|Female|Other|Prefer not to say)$')

[4-6] MEDIUM | Driver & Ride Model Fields Missing Validators
File: backend/schemas.py:151-184, 187-233
Finding: Driver.phone, license_plate, vehicle_make, vehicle_model and Ride.pickup_address,
dropoff_address are plain str with no sanitization calls or Field constraints. These skip
the sanitize_string() / validate_phone() functions in validators.py.
Fix: Annotate fields with max_length bounds and attach validators via @field_validator to
call the existing sanitize_string() and validate_phone() functions.

[4-7] MEDIUM | Suspicious Pattern Detection Logs Only — Does Not Block Injection
File: backend/validators.py:342-352
Finding: sanitize_string() detects "SELECT", "SCRIPT", "ALERT", onclick etc. but only logs
a warning and returns True. Input like "SELECT * FROM users; --" is stored in the DB.
Fix: Either (a) raise HTTPException(400, "Invalid input") for detected injection patterns,
or (b) install bleach and use bleach.clean() for true HTML sanitization. SQL injection
is already prevented by Supabase parameterized queries, but XSS via stored data is a real risk.

[4-8] MEDIUM | Client Email Regex Too Permissive Compared to Backend
File: driver-app/app/driver/profile.tsx:149
Finding: Client regex /^[^\s@]+@[^\s@]+\.[^\s@]+$/ accepts "a@b.c" but backend uses
Python's EmailStr (RFC 5322). Inconsistency means bad emails can produce confusing error
messages that originate from the server rather than client-side UX.
Fix: Use the same email pattern on both sides, or remove client-side email regex entirely
and rely on backend validation with clear API error messages surfaced in the UI.

[4-9] MEDIUM | OTP Code Not Validated at Backend Schema Level
File: backend/schemas.py:10-16 (VerifyOTPRequest.code)
Finding: See [4-4]. Client enforces 4 digits; direct API calls can send any string. Backend
should reject non-4-digit codes before reaching business logic.
Fix: Add pattern constraint per [4-4].

[4-10] MEDIUM | Address Minimum Length Too Short (3–5 chars)
File: backend/validators.py:463 and schemas.py:258-264
Finding: Addresses as short as 3 characters pass validation. "123" is a valid address string.
These won't geocode and cause silent routing failures.
Fix: Raise minimum to 10 characters. Add regex requiring at least a number and a word:
