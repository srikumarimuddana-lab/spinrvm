Resolve ACTION_ITEMS.md B15(c) — the still-open sub-finding that `trigger_emergency` (`backend/routes/rides/safety.py`) requires an active `ride_id` and 404s without one, leaving a rider/driver who feels unsafe outside an active ride with no in-app SOS path, only a client-side prompt to call 911 directly.

## Stage 3-4: Design & Architecture

**Scope of this stage:** Plan & Design + Architecture only, per the task instructions — decide additive-vs-destructive, decide the flag mechanism, name every file/function that will change, and run the blast-radius check *before* any code is written. No diff was produced in this stage; Development (Stage 5) is a separate, later run.

### 1. Additive vs. destructive

Fully additive, on every axis:
- `trigger_emergency` (`backend/routes/rides/safety.py`) is not modified at all — the ride-less path is a new sibling function/route, not a refactor of the existing one. I considered extracting a shared helper so both endpoints call one side-effect bundle, and rejected it (see `decisions.md`): it would touch the body of a live, tested safety endpoint for no requirement that actually needs it, widening blast radius on the one function CLAUDE.md most wants left alone. Some duplication in Stage 5 is the accepted cost.
- The new `app_settings` flag is a new column with a safe default, not a repurposed one.
- The new `safety_incidents.category` value (`sos_button_rideless`) is a new free-text value — confirmed no CHECK/enum constraint exists on that column (grepped every migration touching `safety_incidents`/`category`), so this needs no schema change at all.
- The two new `SOSButton` props (`ridelessSosEnabled`, `onTriggerRideless`) are optional and additive — every existing caller that doesn't pass them is byte-identical.

### 2. Feature flag decision

Required — confirmed, not just assumed. `app_settings`/`settings` is a **fixed-flat-column** table (migration 313's own header: "there is no JSON catch-all"; PostgREST 500s the *entire* PATCH if the request model references a column the table doesn't have yet — this is the exact failure mode migration 313 was written to fix, and `trigger_emergency`'s own idempotency-key code has a defensive fallback for the identical failure shape). So a new flag is not just a pydantic default — it needs a real migration adding the column, or the admin PATCH endpoint 500s the moment anyone tries to set it. This was flagged as an open Stage-3/4 question in the Stage 1-2 report; it's answered now.

Decision: new boolean `rideless_sos_enabled` in the `settings` table (via new migration), default `false`, following the exact three-touchpoint pattern already used for `driver_discreet_sos_enabled` (`backend/schemas.py` → `backend/routes/admin/settings.py` → `backend/routes/settings.py`'s `GET /settings`), just mirrored to the rider side. Not added to `_SUPER_ADMIN_ONLY_FIELDS` in `admin/settings.py` — it's a rollout gate, not a destination credential (matches `driver_discreet_sos_enabled`'s own precedent, which also isn't in that set).

Additionally: the new backend endpoint checks this flag itself and 404s when off (not just "the client won't call it") — fail-closed defense in depth, matching the precedent in `schemas.py`'s own comment on the legacy-consent dark-launch gate ("POST /accept 404s" when its flag is off). Relying only on the client not calling a live endpoint is not fail-closed.
