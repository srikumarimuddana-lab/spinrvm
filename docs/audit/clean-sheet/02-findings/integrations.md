## §1 Steelman — what this codebase gets right about vendor risk

1. **The Supabase circuit breaker (`backend/repositories/_base.py:70-155`) is the best-built resilience
   primitive in the whole vendor layer.** Half-open, single-probe recovery, explicit `release_probe()`
   guard against a leaked probe permanently wedging the breaker open — a level of care the other
   vendor clients don't match. VERIFIED.
2. **Stripe is configured correctly at the SDK level**: `backend/utils/stripe_config.py` pins
   `STRIPE_API_VERSION = "2025-04-30.basil"` explicitly (so a Stripe-side API default-version bump
   never silently changes Spinr's request/response shape), sets `stripe.max_network_retries = 2`, and
   a 30 s HTTP timeout, all set once at startup (`configure_stripe()` from `lifespan.py`). VERIFIED.
3. **Email has a real two-vendor fallback chain, not just a retry**: `backend/utils/email_provider.py`
   tries AWS SES (pinned to `ca-central-1` for residency) first, falls through to Resend on any SES
   exception, and every non-`accepted` outcome feeds `utils/outbox_worker.py` for backoff + dead-letter
   — the module's own docstring states the design intent (never silently drop a receipt) and the code
   matches it. VERIFIED.
4. **The Maps ETA path (`backend/utils/maps_eta.py`) has a genuine three-tier fallback**: self-hosted
   OSRM (zero metered cost) → Google Distance Matrix (metered, traffic-aware) → haversine at a fixed
   30 km/h, each documented with why, and the caller contract (`int` or `None`, never an exception) is
   explicit. This is the one vendor client in the codebase that treats "vendor down" as an expected,
   designed-for state rather than an edge case. VERIFIED.
5. **FCM push never raises and degrades gracefully**: `firebase_admin` 7.5.0's own `HttpClient` default
   (120 s timeout, 4 retries on 500/503 with backoff — VERIFIED-SDK, read from the installed package)
   is materially more defensive than Twilio's, and `features.py`'s `send_push_notification` wraps every
   outcome (including stale-token) so the caller always gets a bool — paired with the `push_retry.py`
   loop as a backstop. VERIFIED.
6. **Vendor keys live in `app_settings` (DB), not `.env`**, with a 60 s in-process TTL cache
   (`backend/settings_loader.py:19`) — a key can be rotated from the admin dashboard and every replica
   picks it up within a minute, no redeploy. This is the right pattern and it's applied consistently
   (Stripe, Twilio, Maps, Zoho all read through it). VERIFIED.
7. **Zoho Desk's own client (`services/zoho_desk_service.py`) is competently built**: 15 s timeout,
   automatic single-retry-on-401 (access-token refresh), Canada-DC default, and it raises a typed
   `ZohoDeskError` rather than swallowing transport failures. The gap this lane found (§2) is one layer
   up, in how a *caller* handles that exception, not in the client itself. VERIFIED.
8. **The Fly-primary/Railway-standby/Cloudflare-DNS-failover topology (CLAUDE.md Deployment section)
   is now verified healthy** (2026-09-24, PR #5608) — a real infrastructure resilience story, even
   though C1 (an actual failover drill under traffic) remains unverified. Cited, not re-derived.
9. **Cost governance exists where the spend risk is highest**: `utils/maps_budget.py`'s Redis-backed
   daily breaker (already the subject of A3-004) fails open on Redis error specifically so a caching
   outage doesn't take Maps offline for riders — a deliberate, documented trade-off, not an oversight.

## §2 Findings

### INT-001 — Twilio's REST client has no HTTP timeout configured; an OTP send can hang the request thread indefinitely during a slow/hung (not just down) Twilio outage
- Hierarchy: L2 Auth › L3 OTP delivery › L4 SMS send › L5 Twilio slow/hung (not a clean 5xx)
- Severity: **CRITICAL**   Priority score: S×B×L = 5×4×3 = 60
- Status: VERIFIED (code) + VERIFIED-SDK (installed `twilio==9.11.0`, matches `requirements-locked.txt:3476`)   Existing item: grep of ACTION_ITEMS.md for "twilio" + "timeout" → none; **new**
- Adversary: vendor outage (Twilio degraded, not hard-down — the harder case, since a hard-down 5xx/refused-connection fails fast, a hung TCP connection does not)
- Evidence: `backend/sms_service.py:42` — `client = Client(twilio_sid, twilio_token)` constructs the SDK client with **no** `http_client=` argument. Read `twilio.http.http_client.TwilioHttpClient.__init__` from the installed package: `timeout: Optional[float] = None` is the default, and `TwilioHttpClient.request()` (`if timeout is None: timeout = self.timeout`) passes that `None` straight to `requests.Session.send(..., timeout=None)` — which per `requests`' own contract means **no timeout at all**, bounded only by the OS TCP stack (can be minutes). `send_sms()` (`sms_service.py:38-45`) runs this inside `asyncio.to_thread(_send)` — the **default** asyncio thread-pool executor (not the app's own `bounded_executor.py`), which is process-wide and shared by every other unguarded `to_thread` call in the codebase. `routes/auth.py:513` `await send_otp_sms(...)` is directly on the OTP-request critical path — a hang here hangs the HTTP request handling that call (no `asyncio.wait_for` wrapper found around it).
- What happens (plain language): if Twilio's API is up but slow-to-respond (a real, common outage mode — not just "down"), every `/send-otp` request blocks on that one HTTP call with no ceiling. A burst of signups/logins during that window each consumes a default-executor thread that never returns; once the default executor's thread cap is exhausted, *any other* code in the process using bare `asyncio.to_thread()` (grep shows several: `email_provider.py`'s SES call, others) queues behind it too, since they share the same pool. Riders/drivers see a spinner that never resolves rather than a fast, clear "SMS delivery is delayed" error.
- Root cause: `sms_service.py`'s Twilio client was built for the happy path (real API key → send; missing key → console fallback) and the exception handler (`except Exception as e:` at line 48) only catches an exception the SDK call *raises* — a hang never raises, so that handler never helps.
- Recommendation: pass an explicit `http_client=TwilioHttpClient(timeout=10)` (or similar, matching the existing Maps/Zoho ~10-15 s convention) into `Client(twilio_sid, twilio_token, http_client=...)`. Separately, wrap the `asyncio.to_thread(_send)` call in `asyncio.wait_for(..., timeout=N)` as defense in depth so a future SDK change can't reintroduce the same gap silently, and audit other bare `asyncio.to_thread()` call sites (SES, Cloudinary if ever wired up) for the same default-executor-pool-exhaustion risk.   Alternative considered: route Twilio sends through the app's existing `bounded_executor.py` instead of the default pool — rejected as a partial fix; it isolates the *blast radius* to Twilio (good) but does not fix the *unbounded* per-request hang itself, which is the actual OTP-availability bug.
- Blast radius: `backend/sms_service.py` (only call site of `Client(...)`, grep confirms); consumers are `routes/auth.py:513` (OTP send — the main path) and `services/guest_notification_service.py:69` (`send_sms` directly). Both are on synchronous request paths, not background loops, so a hang is user-visible immediately, not just an internal metric miss.
- Rollout: additive constructor argument + a `wait_for` wrapper — no schema/flag needed, safe same-day fix.   Rollback: revert the two lines; no data involved.
- Verification to close: a test that mocks a Twilio call that never returns (e.g. `httpx`/`requests` mock with an infinite `time.sleep` in a thread) and asserts `send_otp_sms` returns within the configured timeout instead of hanging; manual check of `Client(...)`'s constructed `http_client.timeout` value in a unit test.

### INT-002 — Zoho Desk transport/API failures are downgraded to `logger.warning` and silently dropped in the fire-and-forget ticket-creation path, including the SOS-linked ticket — no retry, no metric, no Sentry signal
- Hierarchy: L2 Trust & Safety › L3 SOS / support ticketing › L4 Zoho ticket creation › L5 Zoho outage during an active incident
- Severity: **HIGH**   Priority score: S×B×L = 4×4×3 = 48
- Status: VERIFIED   Existing item: related to but distinct from TSF-001 (`02-findings/trust-safety-fraud.md:85-89`, which covers the *dark paging webhook* and a *stale runbook*) — this finding is the **Zoho-ticket** channel specifically, one of the "real" channels TSF-001's own recommendation names as what *does* still work (`admin WS broadcast, safety-team email, logger.critical, Zoho urgent ticket`); this lane's read is that the Zoho leg of that list is weaker than TSF-001 assumed. **New**, filed here rather than re-filed as TSF-001 to avoid duplication — cross-reference it.
- Adversary: vendor outage (Zoho down/slow for the hour that matters most — during an active SOS)
- Evidence: `backend/services/zoho_desk_integration.py:79-82` — `_link_ticket()`'s `except ZohoDeskError as e: logger.warning(...)` (not `.error`) — this is exactly the class of transport/HTTP-level failure `zoho_desk_service.py` raises `ZohoDeskError` for (502 on transport error, `zoho_desk_service.py:139`; propagated 4xx/5xx from Zoho itself). Per CLAUDE.md's own Observability Convention table, `warning` means "recoverable anomaly" and is explicitly "never Sentry — noise"; a Zoho outage on the SOS path is not a recoverable anomaly to shrug off, it's a lost safety-team ticket. Call path: `routes/rides/safety.py:279` `_deps.spawn(create_ticket_for_safety(incident))` — fire-and-forget, correct for not blocking the SOS response itself, but nothing downstream retries or re-queues a failed attempt; `create_ticket_for_safety` (`zoho_desk_integration.py:130-146`) calls `_link_ticket` and any failure just logs and returns `None`.
- What happens: during a real SOS while Zoho Desk is degraded, the emergency alert still reaches `safety_incidents` (DB write, `safety.py`'s own try/except raises loud on that path — good), still broadcasts to the admin WS, and still `logger.critical`s — but the one channel meant to land the incident in the safety team's actual day-to-day triage queue (the stated purpose of `_deps.spawn(create_ticket_for_safety(...))` per its own comment, `#4599 Finding 2`) silently vanishes with a warning-level log line and no operational signal that it happened. If the admin dashboard and Sentry/log tooling both happen to be unstaffed at that moment (the exact gap TSF-001 already names for the paging webhook), this is the second of three "who notices" channels quietly failing the same way.
- Root cause: `_link_ticket`'s `except ZohoDeskError` branch predates a Zoho-outage scenario being considered specifically for the safety-critical caller; it was written as a generic "don't crash the caller if Zoho is unreachable" catch that's appropriate for a routine complaint/lost-item ticket but not for an SOS-linked one.
- Recommendation: for `create_ticket_for_safety` specifically (not the other three `create_ticket_for_*` callers, which are fine as routine best-effort), escalate a `ZohoDeskError` to `logger.error` + a Sentry capture tagged `domain=safety`, and enqueue a retry (the codebase already has a retry-loop pattern — `push_retry.py`, `payment_retry.py` — a `zoho_ticket_retry` table/loop following the same shape would let a transient Zoho outage self-heal instead of permanently losing the ticket).   Alternative considered: make `create_ticket_for_safety` synchronous and block the SOS response on it succeeding — rejected, correctly, by the existing fire-and-forget design; blocking a safety-critical user action on a third-party vendor call is worse than the current gap.
- Blast radius: `backend/services/zoho_desk_integration.py`'s `_link_ticket` is shared by all five `create_ticket_for_*` callers (complaint, flag, safety, lost-and-found, dispute) — escalating the log level for all of them would be noisy (the routine ones are correctly best-effort); the fix should special-case the safety caller, not the shared helper, to avoid the "surgical change" rule pulling in an unrelated severity change for complaint/dispute tickets.
- Rollout: additive (new retry loop + one log-level branch) — no flag needed, no data migration.   Rollback: revert the log-level/retry addition.
- Verification to close: a test that mocks `zoho.create_ticket` raising `ZohoDeskError` from `create_ticket_for_safety` and asserts a Sentry capture (or the retry table gets a row) instead of only a log line; TSF-001's runbook rewrite (already recommended by R11) should list this as a known-degraded channel until fixed.

### INT-004 — Google Maps proxy routes (autocomplete, place details, geocode, legacy Directions) have a cost-based circuit breaker (`maps_budget.py`) but no failure-rate breaker — every request during a sustained Maps 5xx outage still pays the full timeout before failing
- Hierarchy: L2 Rider booking › L3 Address search / destination pin › L4 Maps proxy › L5 sustained Google-side 5xx/degradation (not a full outage, and not a budget exhaustion — a third failure mode distinct from both A3-004 and the accepted 3.5 s Directions-wait exception)
- Severity: **MEDIUM**   Priority score: S×B×L = 3×3×3 = 27
- Status: VERIFIED   Existing item: distinct from A3-004 (`rapid-baseline-2026-09-24/A3-transmission-capacity.md`, cost breaker) and the documented fare-estimate SLA exception (CLAUDE.md Performance SLAs section, latency-not-failure) — this is the third, uncovered failure mode: **repeated 5xx from Google itself**. New.
- Adversary: vendor outage (Google Maps Platform degraded, not budget-exhausted, not just slow-on-one-call)
- Evidence: `backend/routes/maps_proxy.py:163-178` (autocomplete), `:220-232` (details), `:264-...` (geocode), `:382-...` (legacy Directions) — each wraps its own `httpx.AsyncClient(timeout=_HTTP_TIMEOUT)` call in a `try/except httpx.HTTPStatusError`/`except Exception`, converting to a 502, but there is no shared failure-count state across calls (unlike `maps_budget.py`'s Redis-backed daily-spend counters, or the Supabase breaker's in-process failure window) — a second, third, tenth consecutive call during a Google-side incident each independently waits out `_HTTP_TIMEOUT` before 502ing, rather than fast-failing after N recent failures the way the Supabase client does.
- What happens: during a real Google Maps Platform incident (not hypothetical — this class of vendor outage is explicitly in this audit's adversary list), every rider doing an address search pays the full proxy timeout on every keystroke-triggered autocomplete call before getting an error, rather than the proxy recognizing "Google is down" after the first few failures and short-circuiting to an immediate, clear failure state. The Maps ETA path (`maps_eta.py`) already does the right thing here via its OSRM-first fallback chain (§1 Steelman #4) — but Places/Autocomplete/Geocoding have **no fallback provider at all** (OSRM doesn't do address search), so a Maps 5xx incident is a hard "can't search for a destination" outage for the rider app with no graceful degrade, only a slow one.
- Root cause: `maps_budget.py`'s breaker was built to solve the *cost* problem (the incident that motivated it) and the per-call try/except was assumed to be "good enough" for the *availability* problem; nobody built the failure-rate case symmetrically.
- Recommendation: extend `maps_budget.py`'s existing Redis-backed pattern (or add a sibling module) with a short-window (e.g. 10 failures/30 s) failure-rate breaker per SKU, mirroring the Supabase breaker's shape, so a real Google-side incident fails fast (immediate 503 with a clear "address search is temporarily unavailable" message) instead of a slow timeout-per-request degrade. This is not proposing a Places/Autocomplete alternate provider — there isn't a self-hosted one — only proposing the proxy recognize the outage quickly rather than each request re-discovering it.   Alternative considered: rely on Google's own SLA (Maps Platform is a large, generally reliable vendor) and treat this as low-priority — accepted as the reason this is MEDIUM not HIGH, but a documented gap given the explicit "each vendor down for 1h" adversary scenario this audit tests.
- Blast radius: `routes/maps_proxy.py`'s four proxy endpoints; the rider-app address search screen and admin's venue/service-area tools that call through it.
- Rollout: additive Redis-backed breaker, no flag needed (fails open on Redis error, matching `maps_budget.py`'s own convention).   Rollback: remove the breaker check, calls resume their current per-request timeout behaviour.
- Verification to close: a test simulating N consecutive Google 5xx responses and asserting the (N+1)th call short-circuits without a network round-trip.
