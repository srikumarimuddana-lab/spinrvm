# 2026-09-02 — C53 findings 1–3: stale SET-helper test removed, presence→H3 wiring, admin force-rebuild endpoint

## Issue/gap identified

Three small, unrelated gaps in the dark-shipped H3 dispatch-geo-index feature
(`fc6f922`), surfaced by ACTION_ITEMS.md C53 once C52 unblocked
`tests/test_h3_location_index.py`/`test_h3_index_reconciler.py` collection:

1. A test expected a Redis SET-based helper trio (`redis_sadd`/`redis_srem`/
   `redis_sunion`) nothing in the codebase calls.
2. `utils/driver_presence.py` never told the H3 index a driver went offline.
3. No admin endpoint could force an H3 index rebuild — none existed at all.

## Root cause

Same as C52/C53: `fc6f922` shipped this feature dark, behind
`dispatch_geo_provider=legacy`, and was never independently verified after
landing (confirmed via `docs/audit/2026-09-02-pgbouncer-direct-pool-migration-plan.md`
§7). Each finding is an inconsistency between what its own test expected and
what the surrounding code actually did.

## Fix/remediation

**Finding 1 — removed, not built.** `git log --follow` on
`tests/test_h3_location_index.py` shows exactly one commit ever touched the
file (`fc6f922`) — there is no "SET design later replaced by ZSET" history,
so this was authored inconsistently in the same commit, not evolved. Worse:
the test used the real `spinr:h3:cell:{res}:{cell}` key format the ZSET code
already writes to — had `redis_sadd`/`redis_srem`/`redis_sunion` ever been
built and called against real Redis, a write to the same key from both a SET
and a ZSET code path would be a `WRONGTYPE` collision. Removed the test
(`test_redis_set_helpers_union_members`) rather than building dead,
potentially-conflicting functions.

**Finding 2 — wired.** Added a call to `h3_location_index.on_driver_offline(driver_id)`
inside `driver_presence.py::clear_presence()` — the single choke point all 7
existing explicit sign-out/go-offline/force-offline call sites
(`document_expiry.py`, `spinr_pass.py`, `routes/drivers/status.py`,
`routes/websocket.py`'s disconnect handler, `routes/rides/matching.py` ×2)
already funnel through, so one change covers all of them. Matches
`on_driver_offline`'s own docstring intent ("Always drop the driver —
go-offline must not leave a stale index hit").

**Finding 3 — built.** Added `POST /admin/monitoring/dispatch-geo/rebuild`
to `routes/admin/monitoring.py`. Force-runs `h3_index_reconciler._tick(force=True)`
(bypassing the reconciler's 2-minute leader lock, since an operator
explicitly asked for the rebuild rather than a background tick racing other
replicas for it), audit-logs success/failure via this file's existing
`log_admin_action` convention, and surfaces a reconciler failure as an
HTTP 503 rather than swallowing it. Mounted under the existing
`monitoring_router`, which is already gated on the `dashboard` admin module
at `routes/admin/__init__.py` — no new per-endpoint auth code needed.

## Risk & impact on existing functionality

- **Finding 1:** test-only change. No application code touched.
- **Finding 2:** `clear_presence()` is called from 7 sites across
  document-expiry, subscription/pass, driver status, WebSocket disconnect,
  and dispatch matching. Grepped all 7 to confirm none of them special-case
  `clear_presence`'s return value or timing (it returns `None`, always has)
  — the new call is purely additive inside the function body, after the
  existing presence-key delete, and `on_driver_offline` itself never raises
  (catches its own exceptions, logs, returns). Net runtime effect while the
  H3 feature stays dark: one extra `redis_hgetall`-shaped read (returns
  empty, since no driver has ever been written to the index) plus one
  cheap `redis_delete` of a nonexistent hash key, per call, across all 7
  sites — same in-process-fallback path as everything else in dev/test.
  This is deliberately unconditional (not gated on `h3_index_writes_enabled()`),
  matching the existing docstring's stated intent that offline-purge must
  never be skipped even if writes were dark when the record was made.
- **Finding 3:** brand-new endpoint, additive only — no existing endpoint's
  behavior changed. Reads/writes: Postgres `drivers` (read-only, via the
  existing reconciler), Redis H3 keys (via existing `set_ready`/
  `on_location_written`), and the `admin_audit_log` table (via the existing
  `log_admin_action` helper, same as every other admin action endpoint in
  this file). Gated by the same `dashboard` module + `get_admin_user`
  dependency as every other `monitoring.py` endpoint.
- None of these three changes touch the dispatch hot path
  (`routes/rides/matching.py`'s actual candidate-selection logic) or change
  `dispatch_geo_provider`'s default — the feature remains fully dark.

## User experience effect

None for riders/drivers. For internal admins: a new "force rebuild" action
becomes available (not yet surfaced in the admin-dashboard UI — this is the
backend endpoint only; a UI button is a separate, not-yet-scoped follow-up).

async def clear_presence(driver_id: str) -> None:
    if not driver_id:
        return
    try:
        await redis_delete(_key(driver_id))
    except Exception as exc:
        logger.error(...)
    try:
        from .h3_location_index import on_driver_offline
    except ImportError:
        from utils.h3_location_index import on_driver_offline  # type: ignore
    await on_driver_offline(driver_id)

## Rollback plan

`git revert` is safe for all three — pure additive/test-only changes, no
migration, no data mutation, no flag. Reverting finding 3 removes the admin
endpoint (404s on the route, nothing else affected). Reverting finding 2
stops the extra offline-purge call (returns to the pre-existing, already-
shipped-dark state). Reverting finding 1 restores the stale test (it would
fail again, exactly as it did before this change — no functional regression
either way since nothing calls those functions).
